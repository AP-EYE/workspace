# AP-EYE 아키텍처

2026-10-02 피드백으로 재구성했다. 지적 사항: 게이트웨이(내부자 관점)와 BOLA 스캐닝(외부자 관점)의 위치가 섞여 있다.
재구성 전 설계는 [`2026-09-29 게이트웨이 아키텍처.md`](2026-09-29%20게이트웨이%20아키텍처.md). 자세한 설명은 [`BOLA 판정 구조 제안.md`](BOLA%20판정%20구조%20제안.md).

## 관점

내부(운영자) 관점. 서비스 운영자가 자기 앱 앞에 gateway를 두고, 자기 테스트 계정으로 BOLA를 검사한다. 외부 공격자 관점 스캐너는 범위에서 뺀다.

## 구성 요소

- gateway (직접 구현): 요청·응답 기록, 객체 주인 정리
- Akto: API 목록 생성, 다른 계정으로 재전송 (Test Role)
- AP-EYE 판정: 객체 단위로 정상 / 보류 / BOLA 판정
- 한국어 개인정보 분류 (선택): BOLA로 판정된 응답의 노출 정보 종류 표시

## 데이터 흐름

1. 사용자·테스트 계정 요청이 gateway를 거쳐 앱으로 간다. gateway가 요청·응답을 기록한다.
2. gateway가 기록에서 객체 ID와 만든 계정을 뽑아 객체 목록을 만든다.
3. Akto가 기록된 요청을 다른 계정의 인증 정보로 다시 보낸다.
4. AP-EYE가 객체 목록과 다시 받은 응답을 비교해 판정한다.
5. 판정과 근거를 보고서로 낸다.

## akto와의 관계

수집 뒤 재전송은 Akto 기존 기능을 쓰고, Akto의 응답 유사도 판정을 객체 단위 판정으로 대신한다. 판정을 Akto 안에 넣을지(fork) 바깥 프로그램으로 둘지는 [#5](https://github.com/AP-EYE/workspace/issues/5)의 기여·fork 결정을 따른다.
