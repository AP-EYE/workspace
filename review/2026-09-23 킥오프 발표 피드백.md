## 피드백 요약

2. 운영 관찰(인벤토리)과 승인된 테스트 환경의 진단을 어떻게 나눌지
3. 결제 등 상태 변경 요청과 민감정보의 처리 범위
4. 게이트웨이 자체 보안 요구사항과 시험 방법

## 조재현 교수님 질문 및 피드백
- SNS처럼 다른 사람의 데이터를 정상적으로 보여주는 API와 BOLA 취약점을 어떻게 구분할지 논의했는가?
- 운영 API에 진단 요청을 재전송할 때 결제 같은 부작용이 생길 수 있는데, 이를 어떻게 막을지 고민했는가?
- 결제·카드 정보가 포함될 수 있으므로 외부 LLM API 사용은 부적절할 수 있다. 테스트 데이터와 진단 범위를 명확히 정하고, 그 범위 안에서 시스템을 실행하는 방안을 검토.
- 게이트웨이는 요청·응답과 토큰 등 민감한 정보를 많이 알게 되므로, 게이트웨이 자체가 취약점이 되지 않도록 고민해야 한다
- 프로젝트가 얼마나 효과가 있는지 보여줄 정량 목표를 세우라고 했어. 예를 들어 스코어링으로 어떤 효과를 몇 퍼센트 이상 달성할지 기준을 정하고, 중간·최종 발표에서 목표에 얼마나 도달했는지 제3자가 확인할 수 있어야 한다.
