## 멀티테넌트 API 보안 게이트웨이 (Preprints 2025)
- **제목:** Research on API Security Gateway and Data Access Control Model for Multi-Tenant Full-Stack Systems
- **저자:** Yu Mao, Xiangjun Ma, Jiawen Li
- **형태:** Preprints.org 프리프린트 (2025.12, 심사 전)
- **코드/데이터:** 비공개
- **링크:** [https://www.preprints.org/manuscript/202512.1849](https://www.preprints.org/manuscript/202512.1849)
### 한 줄 요약
멀티테넌트 SaaS 환경에서 API 게이트웨이에 제로 트러스트 인증과 OPA 정책 엔진을 붙여, 다른 테넌트의 데이터 접근을 실시간으로 차단하는 아키텍처 제안
### 문제의식
- 멀티테넌트 플랫폼에서 API 남용과 권한 없는 데이터 접근 증가
- 기존 경계 기반 보안으로는 고동시성·동적 자원 접근 환경의 세밀한 권한 통제가 어려움
### 방법
- **게이트웨이 구성**
	- Envoy Gateway + OPA(Open Policy Agent) 정책 엔진
	- OAuth 2.1 + JWT로 테넌트 단위 신원 관리
	- GraphQL 스키마 주입 방식의 정책 상속 → 필드 단위 권한 검증
- **역할 활성화:** 테넌트 ID, 세션 토큰, 타임스탬프 3요소로 역할을 조건부 활성화
- **2단계 결정 흐름**
	- 역할 활성 여부 실패 → 즉시 거부
	- 정책 매칭 실패 → 대체 스코프·정책 상속 등 폴백 시도 후 모두 실패하면 거부
- **인가 함수:** 사용자 속성·자원 레이블·환경 컨텍스트에 가중치를 곱해 합산 → 시그모이드로 인가 확률 산출 (임계값은 과거 로그로 보정)
- **테넌트 격리:** 128개 격리 도메인, 도메인별 독립 정책 풀·인증 캐시
### 결과
- **환경:** Kubernetes 노드 3대, 테넌트 3,200개 시뮬레이션, API 호출 110만 건, 최대 18,000 QPS
- **성능:** QPS 12,000에서 평균 지연 74.2ms, P99 85ms 이내
	- 모듈별: API 파싱 12.6ms / JWT 검증 18.2ms / OPA 정책 평가 24.7ms(전체의 33%) / GraphQL 필드 매칭 9.4ms
- **보안:** 교차 테넌트 접근 차단율 99.1% 이상, 오탐률 1.9%
- **공격 유형별 탐지율:** GraphQL 필드 과다 조회 94.1% / 권한 상승 92.8% / 고빈도 조작 91.7% / 토큰 위조 89.5% / 은밀한 탐색 86.3%
### AP-EYE 활용 포인트
- **아키텍처 유사 사례:** 클라이언트와 API 서버 사이 게이트웨이 구조 동일 → 단, 이 논문은 "차단", AP-EYE는 "진단"이라는 차이 명시
- **지연 측정 방식:** 모듈별 평균/P99/최대 지연 표 → "mitmproxy 때문에 느려지지 않냐"는 질문 대비용 측정 틀
- **공격 유형 대응:** 권한 상승 ≈ BFLA, GraphQL 필드 과다 조회 ≈ BOPLA(과도한 데이터 노출) → 개인정보위 "불필요한 필드 응답 제외" 권고와 연결
- **배경 근거:** 테넌트 간 접근 차단 = BOLA와 같은 문제 → "멀티테넌트 SaaS에서도 핵심 문제"라는 배경 설명
- **결과 정리 형식:** 공격 유형별 규칙 수·탐지율 표
### 한계 / 주의
- 심사 전 프리프린트, 코드·데이터 비공개로 재현 불가
- "탐지율 28% 향상"의 비교 기준(베이스라인)이 본문에 없음

- 정책 규칙 수가 섹션마다 다름 (1,968개 / 1,024개)
- 참고문헌에 주제와 무관한 논문 포함 (관상동맥 영상 AI 리뷰)
- → 핵심 선행 연구보다는 **아키텍처 유사 사례·측정 방식 참고용**으로만 인용 권장

## Links2CPN (IJIS 2025)
- **제목:** Automated broken object-level authorization attack detection in REST APIs through OpenAPI to colored petri nets transformation
- **저자/소속:** Ailton Santos Filho, Ricardo J. Rodríguez, Eduardo L. Feitosa (브라질 아마조나스 연방대, 스페인 사라고사대)
- **형태:** 학술지 논문, International Journal of Information Security 24:83 (2025.02 게재, 심사 완료)
- **코드/데이터:** 공개 (GitHub: ailton07/openapi-links-to-CPNs)
- **링크:** [https://link.springer.com/article/10.1007/s10207-024-00970-5](https://link.springer.com/article/10.1007/s10207-024-00970-5)
### 한 줄 요약
OpenAPI 명세를 컬러 페트리넷(CPN)으로 자동 변환한 뒤, 웹 서버 로그를 재생해 "남에게 발급된 ID를 쓴 요청"을 BOLA 공격으로 탐지하는 연구
### 문제의식
- BOLA는 OWASP API Top 10 1위인데, 로그만 보고 공격을 탐지하는 연구는 거의 없음
- OpenAPI 명세는 텍스트라 형식 분석(formal method)에 바로 쓰기 어려움 → 수학적 모델로 변환 필요
### 방법
- **1단계: 모델 변환 (OpenAPI → CPN)**
	- 경로 × 메서드 × 응답 코드마다 전이(transition) 하나 생성 (예: `get-/rest/basket/{bid}-200`)
	- OpenAPI의 `links` 필드로 "A 응답의 값이 B 요청의 파라미터로 쓰임"을 연결
	- 예: 로그인 응답의 `bid` → 장바구니 조회 요청의 `{bid}`
- **2단계: 적합성 검사 (conformance checking)**
	- 요청/응답 본문 + Authorization 헤더를 담은 JSON 로그를 CPN 위에서 재생
	- 로그인 시 "사용자 X의 bid=6" 토큰이 생성되고, X가 bid=6으로 조회하면 정상 통과
	- 다른 값(bid=7)으로 요청하면 해당 토큰이 없어 전이 불가 → 데이터 흐름 위반 = BOLA 공격
- **도구:** Python 3 + SNAKES(페트리넷 라이브러리)
### 결과
- **대상:** OWASP Juice Shop(장바구니 조회/조작 취약점 2종), Memos(메모 보관 BOLA, 2022년 실제 신고 건 재현)
- **사용자 평가:** 학생 CTF(15명 중 12명 보고서 제출), 로그 약 4,000줄
- **공격 시도 기준:** 정확도·정밀도·재현율·F1 모두 1.0
- **공격 성공 기준:** 취약점1 F1 0.98, 취약점2는 정밀도 0.22 / F1 0.37
	- 원인: 시도와 성공을 구분 못 함 (응답 상태 코드를 보지 않음)
### AP-EYE 활용 포인트
- **문제 정의가 같음:** 권한표 없이 트래픽/로그로 BOLA 탐지 → 핵심 선행 연구로 인용
- **ID 출처 추적:** "응답으로 A에게 준 ID를 누가 요청에 썼나" → 인벤토리에서 객체 ID 파라미터와 소유자 자동 식별에 활용
- **수동 모드 아이디어:** PATCH/DELETE처럼 재전송이 위험한 요청은 관찰만으로 판정
- **차별화 근거 ①:** OpenAPI 명세 1,955개 중 `links` 사용은 9개뿐 → 명세 의존 방식의 한계, "트래픽만으로"의 정당성
- **차별화 근거 ②:** 시도/성공 구분 불가로 정밀도 0.22 → AP-EYE는 실제 응답 비교로 해결
- **로그 스키마:** 요청/응답 본문 + Authorization 헤더 JSON 형식 → PostgreSQL 저장 설계 참고
- **평가 설계:** 취약 앱 + 학생 CTF + 수동 라벨링 + 혼동행렬 / 실제 CVE 재현(Memos)
### 추가로 읽을 논문 (이 논문의 관련 연구에서 발견)
- **Barabanov et al.** (arXiv 2201.10833, 2022): OpenAPI 명세로 IDOR/BOLA 후보 엔드포인트를 휴리스틱 탐지, 공격 기법 체계화 → ID 파라미터 판별 규칙 참고

## BacAlarm (arXiv 2512.19997)
- **제목:** BacAlarm: Mining and Simulating Composite API Traffic to Prevent Broken Access Control Violations
- **저자/소속:** Yanjing Yang 외 (난징대, CSIRO Data61, 화웨이 클라우드)
- **형태:** arXiv 프리프린트 (2025.12, 심사 전)
- **코드/데이터:** 공개 (figshare)
- **링크:** [https://arxiv.org/abs/2512.19997](https://arxiv.org/abs/2512.19997)
### 한 줄 요약
여러 요청이 얽힌 접근 제어 위반을, LLM으로 만든 시뮬레이션 트래픽으로 학습한 탐지 모델로 잡는 연구
### 문제의식
- 인젝션은 요청 하나만 봐도 이상하지만, 접근 제어 위반은 개별 요청이 정상처럼 보임 → 여러 요청의 흐름을 봐야 함
- 실사용자 데이터로 공격 데이터를 만들 수 없어 학습 데이터 부족
### 방법
- **트래픽 생성기**
	- Drain3로 로그에서 엔드포인트 템플릿 추출 (ID·토큰 등 가변 필드 마스킹) → API 지식 베이스
	- LLM + RAG로 정상/악성 요청 시퀀스 생성 → 실제 실행
	- 상태 코드가 의도와 안 맞으면 환각으로 보고 제거
- **탐지기**
	- 정적 특징 13개 (요청 수, 경로 길이 등)
	- 시퀀스 특징: 다음 호출의 예측 불가능성(Transformer), 상태 코드·메서드·경로 엔트로피
	- CatBoost + MLP 게이트 앙상블
### 결과
- 대상: Humhub, Memos (실제 CVE 존재), API 세트 8개, 트래픽 45,765건
- 기존 방법 대비 F1 +21.2%, MCC +24.1%
- 엔드포인트 추출 정밀도·재현율 모두 95% 이상
### AP-EYE 활용 포인트
- **인벤토리:** Drain3 템플릿 마이닝 = "경로 변수 일반화"와 같은 작업 → 설계 근거 + 성능 목표치(95%)
- **차별화:** BacAlarm은 학습 기반(확률적) / AP-EYE는 계정 교차 재전송으로 응답 직접 비교(결정적, 학습 데이터 불필요)
- **LLM 사용:** 규칙 기반 환각 제거 = "LLM 단독 판단 금지" 설계의 근거
- **평가 지표:** 불균형 데이터 → F1과 함께 MCC 사용
- **평가 대상:** Memos 추가 시 Links2CPN, BacAlarm과 직접 비교 가능
### 추가로 읽을 논문 (이 논문의 관련 연구에서 발견)
- **BACscan** (CCS 2025): 블랙박스 접근 제어 취약점 자동 탐지 → AP-EYE 재전송 방식과 가장 유사
- **403 Forbidden?** (IEEE S&P 2025): 실서비스 대상 윤리적 접근 제어 평가 → 테스트 계정 기반 설계 근거
- **Kushnir et al.** (ICISSP 2021): HTTP GET 기반 접근 제어 취약점 블랙박스 탐지
- → 세 논문과의 차별점: 개인정보보호법 기반 영향도 산정
### 한계 / 주의
- 실험 CVE가 XSS·쿠키 탈취 기반 → 훔친 세션으로 접근하는 시나리오, ID 조작형 BOLA와는 다름

### 선행연구에서 참고할 점 (Links2CPN · BacAlarm)
#### 1. 참고할 기법
**① 엔드포인트 일반화** `BacAlarm`
- 내용: 트래픽의 URL에서 객체 ID처럼 바뀌는 부분을 변수로 바꿔, 같은 엔드포인트끼리 묶는다. 예: `/users/12/profile`, `/users/34/profile` → `/users/{id}/profile`. 도구는 Drain3(로그 템플릿 추출 라이브러리)
- 성능: 엔드포인트 추출 정밀도·재현율 95% 이상
- 쓸 곳: 인벤토리 단계의 경로 변수 일반화

**② 객체 ID의 소유자 추적** `Links2CPN`
- 내용: 서버가 응답으로 사용자 A에게 준 객체 ID를 A의 것으로 기록하고, 이후 다른 사용자가 그 ID로 요청하면 위반으로 판정한다
- 쓸 곳: 인벤토리 단계에서 어떤 파라미터가 객체 ID인지, 그 ID의 소유 계정이 누구인지 파악

**③ 관찰만으로 판정** `Links2CPN`
- 내용: 요청을 새로 보내지 않고 기록된 트래픽만 분석해 위반을 판정한다
- 쓸 곳: 수정(PATCH)·삭제(DELETE)처럼 다른 계정 토큰으로 재전송하면 실제 데이터가 바뀌는 요청의 판정

**④ LLM 결과 검증** `BacAlarm`
- 내용: LLM이 생성한 결과를 응답 코드 등 규칙으로 검사해, 의도와 맞지 않는 결과를 제거한다
- 쓸 곳: 개인정보 분류 단계에서 LLM 판정 결과를 규칙으로 재검증

#### 2. 참고할 설계
**로그 저장 항목** `Links2CPN`
- 내용: 요청 본문, 응답 본문, Authorization 헤더(토큰), URL, 메서드, 상태 코드, 타임스탬프를 JSON으로 저장
- 쓸 곳: PostgreSQL 저장소 스키마

#### 3. 참고할 평가 방법
**① 실험 절차** `Links2CPN`
- 내용: 취약 앱 배포 → 학생 CTF로 공격 트래픽 수집 → 사람이 로그를 보고 정답 표시 → 도구 판정과 비교해 혼동행렬 작성
- 쓸 곳: 논문 투고용 성능 평가

**② 평가 지표** `BacAlarm`
- 내용: 공격 요청 수가 정상 요청보다 훨씬 적은 데이터이므로 정확도 대신 F1과 MCC(불균형 데이터에서 쓰는 지표)를 사용
- 쓸 곳: 성능 평가 지표 선정

**③ 실험 대상** `공통`
- 내용: 두 논문 모두 Memos(실제 BOLA 신고 이력이 있는 오픈소스 메모 앱) 사용
- 쓸 곳: crAPI·VAmPI 외 평가 대상 추가 시 두 논문과 결과 비교

#### 4. 선행연구의 한계 (주의할 점)
- **Links2CPN:** OpenAPI 명세에 `links` 필드가 있어야 동작함(공개 명세 1,955개 중 9개만 해당). 공격 시도와 성공을 구분하지 않아 한 실험에서 정밀도 0.22
- **BacAlarm:** 학습 데이터가 필요함. 실험 취약점이 XSS로 탈취한 쿠키를 쓰는 유형이라 객체 ID를 바꾸는 BOLA와 다름. 심사 전 프리프린트

#### 5. 다음에 읽을 논문
- **우선:** BACscan (CCS 2025), 403 Forbidden? (IEEE S&P 2025) → 다른 계정으로 요청을 보내 접근 제어 취약점을 찾는 방식
- **인벤토리 관련:** RESTler, NAUTILUS, VOAPI, Barabanov et al.
- **미조사:** 개인정보보호법 기준 노출 영향도 점수화 연구

<summary>도움되는 점</summary>

**Links2CPN → 확실히 도움 됨**
- 심사를 거친 학술지 논문이라 인용에 문제가 없음
- "권한표 없이 트래픽/로그로 BOLA 탐지"라는 문제 정의가 AP-EYE와 같음
- ID 소유자 추적 방식은 인벤토리뿐 아니라, 방금 얘기한 "SNS처럼 남이 조회해도 되는 API" 문제의 대응(ID를 정상 경로로 받았는지 확인)에도 쓸 수 있음

**BacAlarm → 특정 부분에서 도움 됨**
- 인벤토리(Drain3로 경로 일반화)와 평가 지표(MCC), 관련 연구 목록 찾는 데는 확실히 유용
- 다만 탐지 방식(AI 학습 기반)과 실험 시나리오(XSS로 탈취한 쿠키 사용)가 AP-EYE와 달라서, 핵심 방법론의 선행 연구로 보긴 어려움
- 심사 전 프리프린트라 인용 시 표기 필요

**두 논문으로 채워지지 않는 부분**
1. **AP-EYE 방식과 가장 가까운 연구:** "다른 계정으로 요청을 보내 확인"하는 방식은 두 논문 모두 아님. 이건 BACscan(CCS 2025), 403 Forbidden?(IEEE S&P 2025)을 읽어야 함. 발표에서 "기존 연구와 뭐가 다르냐"는 질문이 나오면 비교 대상은 사실 이 두 논문이 됩니다.
2. **개인정보보호법 기반 영향도 산정:** AP-EYE의 가장 독창적인 부분인데, 두 논문 모두 다루지 않음. 별도 조사가 필요합니다.

### BACScan (CCS 2025)
- **제목:** BACScan: Automatic Black-Box Detection of Broken-Access-Control Vulnerabilities in Web Applications
- **저자/소속:** Fengyu Liu, Yuan Zhang, Min Yang 외 (푸단대, 홍콩중문대)
- **형태:** 학회 논문, ACM CCS 2025 (심사 완료, 우수 논문상)
- **코드/데이터:** 공개 (GitHub: LFYSec/BACScan)
- **링크:** [https://dl.acm.org/doi/10.1145/3719027.3744825](https://dl.acm.org/doi/10.1145/3719027.3744825)
#### 한 줄 요약
여러 계정으로 웹 앱을 직접 테스트해 접근 제어 취약점을 찾는 블랙박스 도구. 기존 도구가 못 잡던 수정·삭제형 취약점까지 잡음
#### 문제의식
- 기존 도구(Burp Autorize 등)는 다른 계정으로 요청을 다시 보내 응답이 비슷하면 취약으로 판정 → 조회는 잡지만 수정·삭제는 응답에 성공 여부가 안 나와 오판
- 기존 방식의 수정형 취약점 오탐률 70.97%, 미탐률 86.96%
#### 방법
- **페이지 간 연결 파악**
	- 피해자 계정으로 크롤링하며 수정 요청 파라미터에 무작위 문자열(토큰) 삽입
	- 조회 페이지에서 그 토큰이 보이면 "수정 페이지 ↔ 상태 페이지"로 연결
- **수정·삭제형 판정**
	- 공격자 계정으로 수정 요청 재전송 → 피해자 계정으로 상태 페이지 확인
	- 토큰이 생기거나(추가·수정) 사라지면(삭제) 취약
	- 삭제는 데이터를 다시 만든 뒤 재전송
- **조회형 판정**
	- 두 계정이 같은 내용을 받는 페이지는 공개로 보고 제외
	- 나머지는 응답 유사도 0.7 이상이면 취약
- **계정:** 일반 2명 + 관리자 1명 (공격자 1, 피해자 2)
#### 결과
- 대상: 오픈소스 웹 앱 20개 (Memos, OpenEMR, XMall 등)
- 취약점 89개 발견 (신규 54개, CVE 35개)
- 수정형 정밀도 100% / 재현율 92.98%, 조회형 81.82% / 87.80%
- Burp Autorize(수정형 정밀도 62.00%), EvoCrawl(51.52%)보다 높음
#### AP-EYE 활용 포인트
- **판정 방식:** AP-EYE의 "응답 비교"는 수정·삭제에 약함 → 조회 API로 결과를 확인하는 방식 추가 필요
- **공개 API 제외:** 두 계정이 같은 응답을 받으면 제외 → SNS 조회 문제 대응 근거
- **계정 구성:** BFLA까지 보려면 관리자 계정 포함 3개 필요할 수 있음
- **비교 실험:** Burp Autorize, EvoCrawl을 베이스라인으로 사용
- **평가 대상:** Memos 포함 → Links2CPN, BacAlarm과도 비교 가능
