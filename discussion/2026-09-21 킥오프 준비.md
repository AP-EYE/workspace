다만 솔직히 말하면, **현재는 좋은 문제를 묶은 기획이고, 기술적 우수성은 아직 증명해야 하는 상태**입니다. `mitmproxy + Presidio + LLM + 대시보드`를 연결하는 데서 끝나면 평가가 평범해질 수 있습니다. 그 연결 위에서 **어려운 인가 판정 문제를 어떻게 해결했고, 얼마나 정확하고 안정적으로 동작하는지** 보여줘야 합니다.

아래 평가는 구현 코드를 검토한 성적표가 아니라, 현재 그림과 조사 자료를 바탕으로 한 제 판단입니다.

| 평가 측면 | 현재 판단 | 이유 |
|---|---|---|
| 문제의 실무 관련성 | 높음 | API 권한 검증, 개인정보 노출, 수정 우선순위가 연결됨 |
| 전공 학습 가치 | 높음 | 공격 재현부터 방어 설계·개발·검증까지 경험 가능 |
| 4인 팀의 구현 가능성 | 범위를 제한하면 높음 | 제한된 REST/JSON 서비스에 대한 MVP는 현실적 |
| 기술적 깊이 | 구현 방향에 따라 크게 달라짐 | 도구 연결은 비교적 쉽지만 정확한 인가 판정은 어려움 |

| 취업 포트폴리오 가치 | 높일 여지가 큼 | 본인 기여·실험·실패 분석까지 남기면 강점 |
| 즉시 상용화 가능성 | 현재는 낮음 | 운영 안정성, 도입 비용, 오탐, 유지보수가 미검증 |

**좋게 보는 이유는, 보안 문제를 발견한 뒤 무엇을 해야 하는지까지 연결되어 있기 때문입니다.**

이 프로젝트를 제대로 수행하면 다음 이야기를 하나의 흐름으로 설명할 수 있습니다.
> API의 권한 문제를 재현했고, 정상적으로 허용된 접근과 구별했으며, 노출된 정보의 성격을 분석하고, 수정 우선순위를 제시한 뒤, 수정 후 정상 기능과 보안성을 다시 검증했다.

여기에 HTTP·세션·토큰·프록시·접근통제·데이터 처리·자동화·보고서 작성이 모두 들어갑니다. 실제 보안 업무와 연결되는 경험입니다. 토스의 공식 직무 설명에도 API 취약점 진단, 비즈니스 영향도 분석, 위험 우선순위, 자체 진단 도구 개발이 등장합니다. [토스 보안 직무 설명](https://toss.im/career/job-detail?job_id=4076085003)

또한 결과물을 시연하기 좋습니다. 공개 프로필은 정상 처리되고, 비공개 이메일이 추가되면 경고하며, 타인의 상담 내용을 읽으면 다른 유형의 위반으로 보여주는 데모는 문제와 효과를 이해시키기 쉽습니다.

**반면, 현재 그림에서 가장 중요하게 보완할 부분은 다섯 가지입니다.**
1. **인가 진단의 '정답'을 어디서 얻는지가 없습니다.**
	다른 계정 토큰으로 요청하는 것은 테스트 실행 방법입니다. 그것이 금지된 접근인지는 별도의 문제입니다. 소유자, 공개 범위, 공유 대상, 담당자, 관리자 권한, 조직 경계가 필요합니다.
	교수님이 지적한 공개 프로필은 작은 예외가 아니라, **이 프로젝트의 핵심 난점**입니다. 이 문제를 잘 해결하면 기술적 깊이가 생기고, 해결하지 못하면 대시보드가 아무리 완성돼도 결과를 믿기 어렵습니다.
	OWASP도 사용자 ID 단순 비교만으로 BOLA를 해결할 수 없다고 명시합니다. [OWASP BOLA 설명](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/)
2. **게이트웨이가 만드는 진단 트래픽의 통제가 필요합니다.**
	그림에서는 진단 요청이 결제 API로 직접 들어갑니다. 실제 구현에서는 중복 결제, 상태 변경, 알림 발송 같은 부작용을 고려해야 합니다.
	정상 트래픽을 관찰하는 기능과 능동 진단 작업자를 분리하고, 첫 버전은 스테이징·테스트 계정·승인된 조회 API에서 실행하는 것이 좋습니다. **무엇을 테스트하지 않을지 결정하는 능력도 보안 엔지니어링 역량**입니다.
3. **LLM의 실행 위치와 책임이 불분명합니다.**
	그림의 LLM API가 내부 추론 서버인지 외부 서비스인지, 정상 요청이 LLM 결과를 기다리는지 명확하지 않습니다. 개인정보 분석 시스템이 상담 원문을 다른 시스템으로 전달한다면 그 처리 경로 자체도 설계 대상입니다.
	LLM은 비동기 문맥 분류와 설명을 맡기고, 장애가 나더라도 서비스 전달과 기본 진단은 유지되게 만드는 편이 좋습니다. 최종 인가 판정은 승인된 정책과 재현 근거로 처리해야 합니다.
4. **'기존 서비스 수정 없음'은 적용 조건을 붙여야 합니다.**
	일부 서비스는 코드 수정 없이 프록시를 붙일 수 있습니다. 그래도 트래픽 경유 설정, 인증서, 테스트 계정, 권한 정책, 객체 관계는 필요합니다.
	"설치하면 알아서 모든 권한을 이해한다"는 기대를 주면 도입 단계에서 막힙니다. 오히려 **서비스 하나를 등록하는 데 필요한 시간과 설정량을 측정**하면 실용성을 보여줄 수 있습니다.
5. **'위험 점수'와 '실제 유출 범위'의 근거가 필요합니다.**
	민감한 필드에 높은 점수를 주는 기능은 만들기 쉽습니다. 그 점수가 실제 수정 순서를 더 잘 정하는지는 별도 검증이 필요합니다.
	또한 진단 중 객체 3개를 읽었다고 실제 사고 피해자가 3명인 것은 아닙니다. 테스트 노출, 관측된 비인가 노출, 잠재 영향 범위를 구분해야 합니다. 이 구분을 정확히 구현하면 개인정보보호 담당자에게도 설명 가능한 결과물이 됩니다.

**차별성에 대해서는 조금 냉정하게 봐야 합니다.**

Akto는 이미 민감정보 탐지와 노출·취약점에 기반한 위험 점수를 설명하고 있습니다. 따라서 "기존 제품은 취약점만 찾고 영향도는 계산하지 않는다"는 주장은 유지하기 어렵습니다. [Akto 공식 설명](https://www.akto.io/sensitive-data)

한국 법령 분류를 추가하는 것은 유용하지만, **분류명과 가중치만 추가하는 수준이면 강한 기술적 차별점은 아닙니다.** 기존 제품의 사용자 정의 규칙으로 일부 구현될 가능성도 있습니다.

저는 여러분의 핵심 기여를 다음처럼 잡겠습니다.
> 공개·공유·조직별 접근 정책을 반영해 인가 진단의 오탐을 줄이고, 한국어 비정형 개인정보의 노출 근거를 연결하여 검토 가능한 결과를 제공한다.

여기서 평가할 것은 명확합니다.
- 정상 공개·공유 요청을 잘못 경고하는 비율이 줄었는가?
- 실제 비인가 접근을 놓치지는 않는가?
- 한국어 상담 문장에서 LLM이 규칙 기반 탐지보다 도움이 되는가?
- 사람이 결과를 검토하고 수정 여부를 결정하는 시간이 줄었는가?

이 중 **한두 가지를 확실하게 증명하는 것만으로도 충분히 의미 있는 졸업작품**입니다.

**네 분의 역량을 전제로 하면, 기능을 더 늘리는 것보다 핵심 기능의 완성도를 높이는 편이 좋겠습니다.**

정보보호 지식이 뛰어나더라도 백엔드 개발, 비동기 처리, 테스트 설계, 배포 경험은 별개의 변수입니다. 네 분 중 적어도 한 명은 서비스 개발과 통합을 주도할 수 있어야 합니다.

기간이 아직 정해지지 않았으므로 추정이지만, 다음 정도로 생각합니다.

| 투입 조건 | 현실적인 목표 |
|---|---|
| 약 8주 | 범위를 엄격히 제한한 MVP와 기본 비교 실험 |
| 한 학기 12~16주 | 예외 처리·독립 평가·설치 문서까지 갖춘 포트폴리오 |
| 상용 운영 수준 | 추가 기간과 실제 사용자·운영 환경 검증 필요 |

그리고 **그림의 mitmproxy 선택 자체는 괜찮습니다.** reverse proxy와 addon으로 시작해 분석 알고리즘을 검증할 수 있습니다. 제가 앞서 제안한 APISIX로 반드시 바꿔야 좋은 프로젝트가 되는 것은 아닙니다. 게이트웨이 기반을 바꾸는 작업이 핵심 진단 연구 시간을 지나치게 잡아먹지 않게 하세요. [mitmproxy 공식 설명](https://docs.mitmproxy.org/stable/concepts/modes/)

**취업에는 도움이 될 가능성이 높지만, 직무별 효과는 다릅니다.**

| 목표 직무 | 연결성 | 보여줘야 할 성과 |

예를 들어 LINE Pay의 개인정보보호 관련 직무는 개인정보 처리 전 주기의 적정성 검토와 위험평가를 요구합니다. 따라서 법 조항을 화면에 붙이는 것보다, 수집·이용·보관·파기와 검토 절차까지 이해한 흔적이 중요합니다. 이 공고는 경력직으로, 여기서는 **직무 내용과의 연결성을 판단하는 자료**로 사용했습니다. [LINE Pay 공식 공고](https://careers.linecorp.com/ko/jobs/2991/)

제가 면접에서 이 프로젝트를 평가한다면 결과물을 대략 세 단계로 구분할 것 같습니다.

| 완성 수준 | 면접에서 판단할 수 있는 내용 |

| 취약한 실습 API 몇 개에서 탐지하고 대시보드에 표시 | 도구 활용과 기본 통합 능력 |
| 정상 예외·미탐·오탐·수정 전후를 비교하고 재현 자료 제공 | 보안 문제를 분석하고 검증하는 능력 |

**여러분은 두 번째 수준을 필수 목표로, 세 번째 수준을 도전 목표로 잡는 것이 좋습니다.** 외부 서비스에서 새로운 취약점을 발견하거나 CVE를 받아야만 좋은 프로젝트가 되는 것은 아닙니다. 허가받은 다른 팀의 서비스에서 정상 동작과 적용 비용을 검증해도 가치가 있습니다.

마지막으로, **팀 전체 결과가 네 명 모두의 취업 성과로 자동 연결되지는 않습니다.** 분업을 이렇게 잡는 편이 좋겠습니다.
- **인가 엔진 담당:** 정책 모델, 세션 처리, 오탐·미탐 분석.

- **개인정보·LLM 담당:** 정답셋, 한국어 문맥 분류, 근거 검증, 비교 실험.

플랫폼 담당도 화면 제작에만 머물지 않도록 해야 합니다. 각자 **설계 결정 하나, 어려운 실패 사례 하나, 본인이 만든 검증 결과 하나**를 책임지고 남기세요.
