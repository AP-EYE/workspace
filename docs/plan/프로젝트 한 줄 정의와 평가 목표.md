# 프로젝트 한 줄 정의와 평가 목표

## 1. 한 줄 정의

**AP-EYE는 Akto를 기반으로 읽기 BOLA의 판정 근거와 한국어 개인정보 분류·집계를 보완하고, 확인된 노출 사례를 사후 신고 검토에 필요한 증거 요약으로 연결하는 API 보안 프로젝트다.**

이는 전체 제품의 목표다.
BOLA 판정, 개인정보 분류, 신고 지원을 모두 묶어서 하나의 연구 기여라고 주장하지 않는다.
Akto 분석 이후 실제 공백이 확인되는 단계 하나를 연구 본체로 선택한다.
사후 신고 지원은 조사·검토용 정보 정리이며 신고 의무나 사고 규모의 자동 확정을 뜻하지 않는다.

이 작업은 기존 팀 자료를 종합한 평가 설계이며 새 논문의 원문 검증이나 탐지기 실행은 수행하지 않았다.

## 3. 연구 본체 후보와 선택 기준

### 우선 검토할 후보: 읽기 BOLA의 오탐 감소

**연구 질문:** Akto의 기존 설정으로 해결되지 않는 읽기 BOLA 판정 오류가 있는가? 있다면 객체별 읽기 허용 근거와 실제 반환 내용을 대조하여, 실제 위반의 탐지를 유지하면서 정상 조회의 오탐을 줄일 수 있는가?

출발 근거는 [10/2 목록 조회 판정 브리핑](../research/2026-10-02%20목록%20조회%20판정%20브리핑%20최종안.md)의 연구 후보다.
그 문서의 모의 서버 사례는 AuthzTrace에 대한 팀원 보고다. Akto의 결함이나 일반 성능을 증명하지 않는다.
공개·공유 객체 확인, 다중 계정 비교, 본문 대조 자체를 새로운 기법이라고 주장하지 않는다.

| 조사 결과 | 다음 결정 |
|---|---|
| Akto의 기존 기능과 적절한 설정으로 문제가 해결됨 | 해당 사례를 BOLA 연구 기여로 삼지 않는다. 설정 가이드나 회귀 사례로 남긴다. |
| 기존 설정 후에도 동일 조건에서 오류가 재현됨 | 원인, 수정 위치, 외부 평가셋을 확보해 BOLA 개선을 본체로 제안한다. |
| BOLA 개선 근거는 부족하고 한국어 분류 오류가 재현됨 | 팀에서 한국어 분류를 본체로 선택할지 검토한다. 자동으로 방향을 바꾸지 않는다. |
| 대상 앱의 권한 정답이나 실행 결과를 확보하지 못함 | 연구 본체 확정을 보류하고 필요한 근거를 기록한다. |

신고 지원의 공백도 별도로 검토하되, 확인 전에는 본체로 확정하지 않는다.
전체 제품 정의는 유지할 수 있지만 연구 주장과 평가 분모는 선택한 단계에 맞춰 좁힌다.

## 4. BOLA 평가 기준 초안

### 비교 조건

- A: 버전을 고정한 Akto 기존 설정.
- B: 같은 Akto에 기존 기능으로 가능한 설정 보완을 적용한 결과.
- C: B와 같은 권한 입력·대상·요청 예산에 제안한 개선만 추가한 결과.

연구 기여의 핵심 비교는 B와 C다.
입력 정보나 요청 수가 늘면 그 차이를 함께 기록한다.
A와 비교해서만 좋아졌다면 기존 설정을 빠뜨린 효과일 수 있다.

### 사례와 정답

평가 단위는 `(앱 버전, 요청 계정, 조회 요청, 대상 객체, 보호 내용 범위)` 한 조합이다.
목록의 일부만 누출되면 객체별 결과와 요청 전체 결과를 따로 집계한다.
같은 객체·응답의 반복 호출을 독립된 취약점 수로 세지 않는다.

정답은 앱 정책·권한 설정·공유 상태와 실제 반환 내용을 별도로 검토해 작성한다.
검사기의 출력이나 입력 권한표를 그대로 복사해 정답으로 삼지 않는다.
다른 계정의 객체라는 이유만으로 위반으로 판단하지 않는다.

외부 대상에서 가능한 사례를 먼저 확인한다.

| 사례 | 확인할 점 |
|---|---|
| 공개 객체 조회 | 원래 허용된 조회에 경고하는가 |
| 공유받은 객체 조회 | 공유 권한을 무시해 경고하는가 |
| 비공개 객체 정상 차단 | 내용이 반환되지 않았는데 경고하는가 |
| 200과 빈 목록 | 응답·대상·권한 근거가 부족하면 보류하는가 |
| 허용 객체만 있는 목록 | 각각의 허용 근거가 확인되는가 |
| 금지 객체의 보호 내용 반환 | 실제 누출을 확인하는가 |
| 허용·금지 객체가 섞인 목록 | 누출된 객체를 놓치지 않는가 |
| 응답 오류·대상 미발견·권한 불명 | 정상으로 숨기지 않고 원인과 미검사 범위를 남기는가 |

자체 합성 사례는 실패 조건 확인과 회귀 검사에 쓴다.
주성능 근거는 팀이 선정한 외부 기준셋과 재현 가능한 대상에서 낸다.
수정할 때 본 사례와 최종 평가 사례를 분리한다.

### 지표와 분모

정답이 확인된 고정 평가 집합에서 `P`는 실제 위반 수, `N`은 실제 정상 수다.
`TP`는 위반을 BOLA로 확정한 수, `FP`는 정상인데 BOLA로 확정한 수다.
보류와 미검사는 정답별로 따로 기록한다.

| 지표 | 계산·보고 방법 |
|---|---|
| 오탐률 | FP / N. 정상의 보류·미검사도 N에 남겨 놓고, 정상 확정률을 함께 보고한다. |
| 전체 위반 재현율 | TP / P. 실제 위반의 보류·미검사를 P에서 빼지 않는다. |
| 확정 판정 정밀도 | TP / (TP + FP). 확정 BOLA가 없으면 N/A다. |
| 정상 확정률 | 실제 정상 중 정상으로 확정한 수 / N. 보류만 늘려 오탐을 낮추는 효과를 확인한다. |
| 보류율 | 보류 수 / (P + N). 정답별 보류 수를 같이 기록한다. |
| 실행 범위 | 정상·BOLA·보류 결과를 산출한 수와 미검사 수를 전체 계획 사례 대비 보고한다. |
| 비용 | 권한·계정 설정 시간, 입력 항목 수, 추가 요청 수, 실행 시간, 사람 검토 시간을 분리한다. |

분모가 0이면 0%로 쓰지 않고 N/A로 표시한다.
정답 자체가 불명인 사례는 P와 N에 넣지 않고 별도 목록과 수를 공개한다.
같은 앱·객체에 묶인 결과를 독립 표본처럼 해석하지 않는다.
앱별 결과와 전체 결과를 함께 보고하고, 반복 실행은 안정성 확인으로 구분한다.

### 목표와 확정 절차

**제안 목표:** 같은 평가 사례·권한 입력·요청 예산에서 B보다 오탐률을 낮추고, 전체 위반 재현율과 정상 확정률은 낮추지 않는다.
보류·미검사가 늘어 목표를 충족한 것처럼 보이는 결과는 개선으로 결론 내리지 않는다.

| 항목 | 현재 상태 | 확정에 필요한 값 |
|---|---|---|
| 주평가 데이터셋·앱 | TBD | 출처, 버전, 라이선스, 재현 절차, 권한 정답 |
| 정상·위반 사례 수 | TBD | 앱별 P·N, 객체·계정 수, 평가/개발 분리 |
| Akto 기준선 A·B | TBD | 설정, 판정 규칙, 오탐률·재현율·정상 확정률·보류·미검사 |
| 최소 의미 있는 개선 폭 | TBD | 기준선과 사례 수에 맞춘 목표 폭과 비용 한도 |
| 최종 수치 목표 | TBD | 데이터셋과 개발용 기준선을 본 뒤, 최종 평가 전에 고정 |

“95% 정확도”나 “오탐 0%”를 근거 없이 목표로 확정하지 않는다.
관측된 차이와 표본의 불확실성을 함께 보고한다.
표본이 작은 경우 해당 사례에서의 결과로만 설명한다.

## 5. 한국어 분류·집계와 증거 요약의 보조 평가

BOLA 판정 결과를 개인정보 분류 결과로 뒤집지 않는다.
정상 API에 개인정보가 있다는 사실만으로 누출로 분류하지 않는다.
BOLA로 확인된 응답에서 한국어 유형을 분류하고 관측 범위를 집계한다.

| 영역 | 기준선·평가 | 목표 초안 |
|---|---|---|
| 한국어 분류 | Akto 기본 유형, 사용자 정의 규칙, 제안 방식 비교. 고정 합성 평가셋에서 유형별 precision·recall·F1과 macro F1을 보고한다. | 기존 규칙과의 차이를 유형별로 보이고, 잘못 잡은 예와 놓친 예를 기록한다. 수치 목표는 데이터셋 선정 후 고정한다. |
| 집계 | 같은 합성 기록에서 수작업 정답과 비교. 요청 수, 응답 레코드 수, 필드 발생 수, 고유 사실 수, 관측된 주체 수를 분리한다. | 중복 호출과 목록 반복 때문에 실제보다 크게 세지 않는지 확인한다. 식별 근거가 없으면 주체 수는 알 수 없음으로 둔다. |
| 증거 요약 | 선택한 신고 양식의 항목과 로그 근거를 대응시킨다. 양식 버전과 공식 출처는 선정 시 확인한다. | API, 관측 시각, 계정·권한 근거, 보호 내용 범위, 관측된 항목·주체 수, 미확인 범위를 추적 가능하게 남긴다. |

합성 개인정보는 팀 합의된 평가 경계다.
한국어 개인정보 데이터셋이 모두 합성이라는 일반 사실로 확대하지 않는다.
요청 개인정보와 실제 반환 개인정보를 분리한다.
수집한 로그의 관측량을 실제 사고 전체의 피해 규모라고 표현하지 않는다.
현재 법적 신고 항목과 의무 판단은 재검증하지 않았으므로 이 문서에서 법정 결론을 내리지 않는다.

## 6. 팀원 조사 결과를 받을 항목

| 받을 대상 | 필요한 내용 | 문서에 반영할 곳 |

| 성빈·유상, Akto 분석 | 버전·설정, 기존 동작과 재현 오류, 해결 가능한 설정, 수정 위치, 기여 관련 이슈 | 연구 본체 선택, A/B/C 비교 |
| 데이터셋 담당, 팀에서 확정 필요 | 원문에서 실제 사용한 평가셋, 공개 자료, 정상·위반 정답, 재현·라이선스 | 평가 분모, 외부 평가 대상 |
| 유상, 아키텍처 | 수집·능동 테스트·판정의 위치, 내부·외부 관점, 입력·출력 | 전체 제품 정의와 구현 경계 |

팀원에게 공유할 요청문:

> 5번 한 줄 정의와 평가 목표 초안 정리했습니다. Akto 조사에서는 버전·기존 설정·실행 결과·기존 기능으로 해결되는지·수정 위치를, 데이터셋 조사에서는 출처·정상/BOLA 정답·공개 여부·재현 방법을 같이 남겨주세요. 결과 받으면 비교 기준과 수치 목표까지 합치겠습니다.

## 7. 일정과 확정 조건

- 10/6 13시 온라인 회의: 조사된 범위까지 공유하고 본체 후보와 데이터셋 후보를 검토한다. CCIT 수업과는 별도 팀 회의다.
- 10/7~10/8: Akto·데이터셋 결과와 아키텍처를 반영해 한 줄 정의와 평가 목표를 확정한다.
- 조사 결과가 부족하면 같은 기간 안에 미확인 항목과 담당·후속 기한을 기록한다. 완성되지 않은 내용을 확정이라고 표시하지 않는다.

현재 완료한 것은 제품 정의 초안, 본체 선택 기준, 평가 지표와 분모, 취합 항목이다.
남은 의존 항목은 Akto 심층 분석과 데이터셋 선정, 아키텍처 결정이다.
