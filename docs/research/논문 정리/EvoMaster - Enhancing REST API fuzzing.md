# 한 줄 요약
REST API 퍼징에 접근 제어 검사와 SQLi·XSS 테스트를 더하고, 발견한 문제를 재현 가능한 테스트로 제공하는 연구

# 핵심 키워드
### API 및 테스트 기법
- **REST API fuzzing** — REST API에 자동으로 다양한 입력을 보내 결함을 찾는 테스트
- **사후 처리(Post-processing)** — 일반 퍼징을 마친 뒤, 생성된 테스트를 바탕으로 보안 시나리오를 추가 검증하는 방식
### 접근 제어 및 인증
- **접근 제어(Access control)** — 사용자·역할별로 리소스나 기능의 접근을 제한하는 정책
- **권한 우회(Authorization bypass)** — 접근 권한 검사가 누락되거나 잘못 적용되어 제한된 작업이 허용되는 문제
- **인증 누락(Missing authentication)** — 인증 없이 보호된 데이터나 기능에 접근할 수 있는 문제
### OWASP 주요 취약점
- **BOLA (Broken Object Level Authorization)** — 사용자가 권한 없는 특정 객체에 접근하는 취약점
- **BFLA (Broken Function Level Authorization)** — 사용자가 권한 없는 기능을 실행하는 취약점
### 입력 기반 공격
- **SQL Injection (SQLi)** — 입력값을 통해 SQL 명령이 의도치 않게 실행되는 취약점
- **Cross-Site Scripting (XSS)** — 입력된 스크립트가 저장·반환되어 클라이언트에서 실행될 수 있는 문제
### 탐지 및 검증
- **보안 오라클(Security oracle)** — 테스트 결과가 보안 결함인지 판정하는 규칙
- **HTTP 상태 코드** — 401, 403, 404 등의 응답을 활용해 인증·인가 동작이나 정보 노출 문제를 점검
- **실행 가능한 회귀 테스트** — 발견된 문제를 재현하고 이후 수정 여부를 확인하도록 생성하는 테스트

# 요약
## 3줄 요약
- 이 논문은 REST API의 보안 취약점을 탐지하기 위해 권한 부여 정책 위반 및 SQL Injection, XSS와 같은 기존 공격을 점검하는 7가지 새로운 자동화 오라클을 제안합니다.
- 제안된 기법은 최신 REST API 퍼저(fuzzer)인 EvoMaster에 통합되었으며, 52개의 다양한 API를 대상으로 한 실험을 통해 실제 환경에서의 보안 결함 탐지 성능을 입증했습니다.
- 이 접근 방식은 보안 오류 발생 시 개발자가 즉시 디버깅에 활용할 수 있는 실행 가능한 테스트 케이스를 자동으로 생성하여, 효율적인 보안 테스트와 유지보수를 지원합니다.

## 간략히 보기
### 요약
본 논문은 REST API의 보안 취약점, 특히 권한 부여 및 접근 제어 관련 결함을 탐지하기 위한 7가지 새로운 자동화된 오라클(Automated Oracles)을 제안하고, 이를 상태 기반(State-of-the-art) 퍼저(Fuzzer)인 EvoMaster에 통합한 연구입니다.
### 1. 연구 배경 및 목적
기존의 REST API 퍼징 기법들은 주로 500 HTTP 상태 코드와 같은 서버 오류 탐지에 집중되어 왔습니다. 그러나 OWASP가 선정한 주요 취약점인 BOLA(Broken Object Level Authorization) 및 **BFLA(Broken Function Level Authorization)**와 같은 권한 부여 결함은 기존 퍼저로는 탐지하기 어렵습니다. 본 연구는 이러한 보안 취약점과 SQL Injection 및 XSS와 같은 전통적인 공격을 효과적으로 탐지하기 위한 기술적 체계를 구축하는 것을 목표로 합니다.
### 2. 핵심 방법론: 7가지 보안 오라클
본 연구는 API의 명세서(OpenAPI)와 최소 두 명의 사용자 인증 정보를 활용하여 다음의 오라클을 통해 결함을 탐지합니다.
- Not recognized authentication (Section 3.1): 인증된 사용자가 401 오류를 반환받는 경우, 해당 인증 정보의 유효성을 다른 엔드포인트에서 검증하여 usability fault 또는 보안 결함을 판별합니다.
- Existence leakage (Section 3.2): 존재하지 않는 자원에 대한 404 응답과 접근 불가능한 자원에 대한 403 응답 간의 일관성을 검사하여 정보 노출 여부를 확인합니다.
- Missed authorization checks (Section 3.3): 자원 변경이 가능한 3가지 연산(PUT, PATCH, DELETE) 중 일부는 차단(403)되지만 다른 하나는 허용(2xx)되는 경우를 찾아 권한 부여 체크 누락을 탐지합니다.
- Anonymous modifications (Section 3.4): 인증 없이도 DELETE, PUT, PATCH가 허용되는지 검사하여 비인증 데이터 조작 취약점을 판별합니다.
- Ignore anonymous (Section 3.5): 인증 정보를 제공할 때는 401/403을 반환하지만, 아예 인증 정보를 생략할 경우 2xx를 반환하는 논리적 결함을 탐지합니다.
- Leaked stack traces (Section 3.6): 500 오류 응답 본문에 프로그래밍 언어의 stack trace가 포함되어 있는지 정규 표현식으로 분석하여 정보 노출을 확인합니다.
- Hidden accessible (Section 3.7): OpenAPI 명세에 정의되지 않은 엔드포인트가 실제 호출 시 응답을 반환하는지(특히 403, 405, 501 이외의 응답) 확인하여 숨겨진 취약점을 탐지합니다.
### 3. 공격 기법 통합 및 검증 프로세스
- SQL Injection & XSS: 기존의 악성 페이로드들을 API 입력 필드(query parameter, body)에 주입합니다. 특히 SQL Injection의 경우, Sleep payload(예: ' OR SLEEP(5)-- -)를 활용하여 응답 시간 변화를 $O(N \times P)$의 복잡도로 검사합니다.
- 사후 처리(Post-processing): 퍼징 세션이 완료된 후, 수집된 테스트 케이스들을 슬라이싱(Slicing)하고 조합하여 보안 테스트 시나리오를 자동 생성합니다. 이를 통해 개발자가 결함을 디버깅할 수 있도록 실행 가능한 JUnit 형태의 테스트 스위트를 출력합니다.
### 4. 실험 결과
- 실험 대상: 9개의 인공적인 API, 8개의 취약점이 의도된(Vulnerable-by-design) API, 36개의 WFD(Web Fuzzing Corpus) API 등 총 52개의 REST API를 대상으로 실험을 수행하였습니다.
- 성능: 인공적인 환경에서 9가지 모든 유형의 취약점을 완벽하게 탐지하였으며, 실제 환경(WFD)에서도 수백 개의 보안 결함 및 HTTP 프로토콜 오용 사례를 찾아냈습니다.
- 오버헤드: 대부분의 API에서 추가 보안 테스트 오버헤드는 수십 초에서 2분 내외로 나타나, 1시간 단위의 전체 퍼징 캠페인 내에서 실무적으로 충분히 허용 가능한 수준임을 입증하였습니다.
### 5. 결론
본 연구는 권한 부여 위반과 입력 기반 공격을 동시에 처리하는 통합적인 보안 퍼징 프레임워크를 제시하였습니다. 특히, 단순히 취약점을 발견하는 것에 그치지 않고, 자동으로 실행 가능한 테스트 코드를 생성하여 취약점 재현 및 패치를 지원한다는 점에서 실무적 가치가 큽니다. 제안된 기술은 EvoMaster에 통합되어 버전 5.2.0부터 기본 기능으로 제공되고 있습니다.

## BOLA 관점에서 본 연구의 한계와 해결 전략
### 1. 문제의 핵심: BOLA 탐지의 '맥락적 모호함'
BOLA는 사용자가 인증은 되었으나, 자신의 것이 아닌 리소스에 접근할 권한이 없을 때 발생하는 보안 결함입니다. 이 논문의 오라클은 이를 탐지하기 위해 "사용자 A는 거부(403)되고, 사용자 B는 성공(200)하는 패턴"을 찾습니다.
- **BOLA 관점의 거짓 양성**: 이 오라클이 탐지한 패턴이 **'보안 취약점(BOLA)'**인지, 아니면 **'정상적인 접근 제어 설계(예: 특정 리소스의 공유 허용)'**인지 퍼저는 알지 못합니다. 퍼저는 단순히 '상태 코드의 차이'만 관찰하므로, API 설계자가 의도한 권한 체계까지 '취약점'으로 보고하는 거짓 양성이 발생합니다. 이것이 BOLA 탐지 시 연구자가 겪는 가장 큰 고민입니다.
### 2. 논문의 접근: '사후 처리 및 수동 검증' (현재의 해결책)
논문은 이 한계점을 해결하기 위해 **'사후 처리(Post-processing) 방식'**과 **'사용자 피드백'**을 제안합니다.
- 퍼징 중 탐지된 모든 잠재적 BOLA 케이스를 무조건 취약점으로 확정하는 대신, 실행 가능한 테스트 케이스를 생성하여 개발자에게 제공합니다.
- 개발자는 이를 수동으로 검토하여, 만약 그것이 의도된 정책(거짓 양성)이라면 해당 엔드포인트를 오라클 대상에서 제외(Disable)시킵니다.
- 즉, '기술적 탐지'는 도구가 수행하고, '정책적 판별'은 사람이 수행하는 분업화된 구조를 취합니다.
### 3. LLM의 역할: '지능적 문맥 해석' (미래의 해결책)
질문하신 대로, 이 논문은 **"인간이 수동으로 수행하는 검토 과정을 LLM이 대체하거나 보조할 수 있다"**는 비전을 제시합니다.
- **BOLA 맥락 이해의 자동화**: LLM은 단순 상태 코드뿐만 아니라 API 문서(OpenAPI), 소스 코드, 에러 메시지(자연어)를 모두 읽을 수 있습니다.
- **분류(Classification)의 고도화**: LLM은 "이 리소스 접근이 왜 거부되었는가?"에 대한 코드 내의 권한 체크 로직을 파악하여, 이것이 실제 BOLA 취약점인지, 아니면 권한이 필요한 정상적인 비즈니스 로직인지 확률적으로 판별할 수 있습니다.

결과적으로 LLM은 퍼저가 뱉어내는 수많은 거짓 양성 BOLA 리포트 중에서, 진짜 위험한 취약점만 골라내는 '지능형 필터' 역할을 수행하게 됩니다.
### 요약 표

| 단계 | 역할 | BOLA 관점의 기여 |
|---|---|---|
| 현재의 한계 | 구조적 오라클 | 상태 코드 차이만으로 BOLA를 단정하여 '의도된 설계'도 취약점으로 오판함. |
| 현재의 대안 | 사후 처리 및 수동 검토 | 사람이 최종 확인하여 거짓 양성을 제거 (비효율적일 수 있음). |
| LLM 도입 시 | 의미적 문맥 분석 | 코드/문서 맥락을 읽어 BOLA 여부를 자동 판별하여 거짓 양성을 획기적으로 감소. |

### 결론
결론적으로, 연구자님께서 파악하신 대로 '거짓 양성'은 BOLA 탐지의 정확도를 낮추는 주범이며, LLM은 이 문제를 풀기 위해 '기술적 패턴'에 '비즈니스적 맥락'을 더해주는 핵심 도구로 제안된 것이 맞습니다. 이러한 맥락 이해는 단순히 BOLA를 찾는 것을 넘어, API의 보안 수준을 실질적으로 높이는 데 결정적인 차이를 만들 것입니다.
> 다음 연구로 **'LLM을 활용해 BOLA 탐지 시 발생하는 거짓 양성을 얼마나 줄일 수 있는지'**에 대한 정량적 분석을 제안해 보는 것은 어떨까요?

# 정리
BOLA 탐지에서는 다른 사용자의 리소스에 대한 접근을 일률적으로 비인가로 간주하기 어렵다. 관리자나 공유 사용자처럼 정당한 접근 권한을 가진 역할이 있을 수 있고, API의 접근 정책이 복잡하거나 공식적으로 명세되지 않은 경우 자동화된 퍼저가 의도된 접근과 취약한 접근을 구분하지 못해 거짓 양성을 낼 수 있다.
## 주요 인용문
### BOLA의 정의
> "Wrong authorization checks in the APIs can lead users to access resources they are not supposed to access (BOLA)"

**출처**: Şahin et al., 2027, p. 1 (서론 첫 문단)
### 단순한 접근 규칙의 한계
> "Simply stating that a user should not access or manipulate resources of other users would just result in many false-positive faults"

**출처**: Şahin et al., 2027, p. 6 (3.3절 첫 문단)

**의미**: 단순한 접근 규칙이 관리자 접근 등 의도된 설계까지 거짓 양성으로 판정할 수 있음을 지적
### 관리자의 예외적 접근
> "An administrator would likely be able to access and manipulate resources of other users"

**출처**: Şahin et al., 2027, p. 6 (3.3절 첫 문단)

**의미**: BOLA 탐지 시 역할별 권한 차이를 고려해야 함을 강조
### 접근 정책 명세의 부재
> "Unfortunately, we are aware of no existing formal specification for access policies in REST APIs which is widely used."

**출처**: Şahin et al., 2027, p. 6 (3.3절 두 번째 문단)

**의미**: 정형화된 정책 명세 부재로 인해 거짓 양성 판별이 어려운 현실을 지적
