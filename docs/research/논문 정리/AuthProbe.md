# AuthProbe: Specification-Driven, Multi-Identity Detection of Broken Object-Level Authorization in Recruitment APIs

# 한 줄 요약
AuthProbe는 OpenAPI 명세와 여러 계정을 활용해 API의 객체 단위 권한 취약점을 탐지하고, CI/CD 빌드에 연동할 수 있는 보안 스캐너입니다.

# 핵심 키워드
### BOLA와 IDOR
- **BOLA (Broken Object-Level Authorization)**: 로그인은 되었지만, 요청한 개별 객체를 볼 권한이 있는지 확인하지 않아 다른 사용자의 데이터가 노출되는 취약점입니다.
- **IDOR**: 사용자가 조작할 수 있는 객체 식별자를 통해 권한 없는 데이터에 접근하는 문제로, BOLA의 흔한 형태입니다.
### AuthProbe의 핵심 기술
- **다중 ID 기반 테스트**: 운영자가 관리하는 둘 이상의 계정으로 각 계정의 객체를 확인한 뒤, 한 계정이 다른 계정의 객체를 읽을 수 있는지 시험합니다.
- **OpenAPI 기반 탐지**: API 명세에서 목록·단건 조회 경로를 찾아 검사 대상을 자동으로 식별합니다.
- **소유권 탐색 및 응답 비교**: 각 계정의 목록 응답을 소유 객체의 기준으로 삼고, 타 계정의 객체를 조회한 응답과 실제 소유자의 조회 결과를 대조합니다.
- **ID 열거 및 존재 오라클**: 예측 가능한 식별자를 탐색하고, 존재하는 객체와 존재하지 않는 객체의 응답 차이로 객체 존재 여부가 드러나는지 확인합니다.
### 배포 및 자동화
- **CI/CD 보안 게이트**: 심각도 기준을 넘는 발견 사항이 있으면 빌드를 실패시키고, JSON·JUnit 등 기계 판독 가능한 보고서를 제공합니다.
### 검증 범위와 한계
- 합성 채용 API 실험에서는 심은 취약점을 탐지하고 강화된 대상에서는 오탐이 없었지만, 실제 서비스의 유병률이나 일반화 성능까지 입증한 것은 아닙니다.

## 3줄 요약
- AuthProbe는 OpenAPI 사양을 기반으로 하여 여러 사용자 ID 간의 권한 오류를 교차 검증함으로써, 기존 보안 도구가 탐지하기 어려웠던 BOLA 및 IDOR 취약점을 효과적으로 식별합니다.
- 이 도구는 공격자가 다른 사용자의 객체를 읽으려 할 때 응답 데이터를 비교하여 실제 데이터 유출 여부를 확인하며, 이를 통해 오탐률(false-positive)을 최소화하고 신뢰성 높은 보안 검사를 수행합니다.
- CI/CD 파이프라인에 통합 가능하도록 설계된 AuthProbe는 보안 검사 결과를 기계가 읽을 수 있는 리포트로 생성하고 심각도에 따른 자동화된 빌드 차단을 지원하여 배포 전 단계에서 취약점을 예방합니다.

## 간략히 보기
### 요약
본 논문은 recruitment API에서 발생하는 BOLA(Broken Object-Level Authorization) 취약점을 탐지하기 위한 오픈소스 블랙박스 스캐너인 AuthProbe를 제안합니다. BOLA는 OWASP API Security Top 10에서 지속적으로 1위를 차지하는 심각한 보안 결함으로, 적절한 인증을 거친 사용자가 권한이 없는 타인의 데이터 객체에 접근할 수 있는 취약점을 의미합니다.
### 핵심 방법론 및 기술적 구조
AuthProbe는 다음과 같은 기술적 과정을 통해 BOLA 및 IDOR(Insecure Direct Object Reference)를 탐지합니다.
#### 1. OpenAPI 기반 자원 탐색
API의 OpenAPI 명세(specification)를 분석하여 객체 식별자를 포함하는 경로(path)와 해당 객체를 반환하는 GET 연산(item operation)을 식별합니다.
#### 2. 소유권 탐색(Ownership Discovery)
운영자가 제어하는 두 개 이상의 Identity를 사용하여 각 Identity가 어떤 객체를 소유하고 있는지 파악합니다. 이는 각 Identity별로 collection 연산을 수행하여 얻은 결과를 바탕으로 수행되는 ground truth 수립 과정입니다.
#### 3. BOLA 탐지 및 검증
공격자 Identity $a$가 피해자 Identity $v$의 객체 $o$를 요청했을 때, 실제 객체 $o$가 반환되는지 확인합니다. AuthProbe는 다음과 같은 Leak Predicate를 사용하여 위양성(false positive)을 최소화합니다.

$$Leak(a, o) \equiv ok(r) \wedge obj(r) \wedge id(r) = id(o)$$

즉, 응답 상태($status$)가 성공이고, 응답 본문에 포함된 객체의 식별자가 요청한 식별자 $id(o)$와 일치할 때만 취약점으로 간주합니다.
#### 4. 추가 탐지 기능
- **Identifier Enumeration**: 식별자가 숫자형인 경우, 인접한 식별자를 호출하여 타인의 객체에 접근 가능한지 확인하는 IDOR 탐지 프로브를 수행합니다.
- **인증 및 오라클 탐지**: 인증이 누락된 요청에 대한 데이터 반환 여부와, 존재하지 않는 객체와 권한이 없는 객체에 대해 API가 서로 다른 상태 코드(status code)를 반환하는지(Existence Oracle)를 확인합니다.
### 성능 및 유효성 검증
AuthProbe는 실제 McHire 사건의 취약점 패턴을 재현한 합성 API를 대상으로 평가되었습니다.
- **성능**: 취약한 타겟에서는 설정된 모든 BOLA 취약점을 탐지하였으며, hardened(보안 강화) 타겟에서는 위양성 없이 0건의 결과를 보였습니다.
- **확장성**: 알고리즘의 복잡도는 $O(|I|^2 \cdot m)$으로, 여기서 $|I|$는 Identity의 수, $m$은 객체 샘플 수입니다. 검사 시간이 객체 수에 따라 선형적으로 증가하여 지속적인 CI(Continuous Integration) 파이프라인에서 빌드 게이트(build gate)로 활용하기에 적합합니다.
### 결론 및 기여
AuthProbe는 소스 코드 접근 없이도 API의 설계 명세와 블랙박스 테스트만으로 실질적인 권한 검증 누락을 찾아냅니다. 특히 결과 보고서의 severity-thresholded exit code 기능을 통해 배포 파이프라인에서 보안 회귀를 자동으로 차단할 수 있는 환경을 제공하며, recruitment technology와 같은 민감한 개인정보 처리 시스템의 보안성을 크게 향상시킬 수 있는 도구입니다.

# 우리 프로젝트와의 차이점
## AuthProbe vs 우리 연구: 핵심 차이 분석
### 한 문장 요약
**AuthProbe는 "누구 거냐"는 알아도 "봐도 되는 거냐"는 모릅니다.** 그래서 공개 글이나 공유받은 접근을 오탐으로 잘못 찍을 위험이 구조적으로 남아있어요. 우리는 테스트 객체를 만들 때 "봐도 되는 범위"까지 미리 정해둬서 그 오탐 부류를 원천 차단하고, 대신 라벨 없는 객체는 억지로 찍지 않고 보류로 빼서 그 비율까지 숫자로 공개합니다.

### 같은 점 (베이스)
- 둘 다 두 계정(다중 정체성)으로 교차 접근해서 BOLA를 확정
- 읽기(GET)만 다룸
- BFLA(함수 수준)는 미포함

### 다른 점

| 항목 | **AuthProbe** | **우리 연구** |
|---|---|---|
| **시드가 담는 정보** | 소유권만 ("이 객체는 A 거다") | 소유권 + 가시성 ("이 객체는 A 거고, 비공개다" 또는 "공개다" 또는 "C한테 공유했다") |
| **목록(listing) 없을 때** | 설정에 식별자를 수동으로 넣음(소유권 시드) | 애초에 테스트 객체를 직접 만들면서 상태를 지정 — 목록 의존 자체가 없음 |
| **공개 객체를 B가 봄** | 판단 못 함 — 소유권만 아니까 "A 거를 B가 봤다"로만 보임 → 오탐 위험 | 정상 처리 — 공개로 라벨했으니 오탐 구조적으로 제거 |
| **공유 대상(C)이 봄** | 범주 자체가 없음 | 정상 처리 — 공유 목록에 C 있으니 오탐 아님 |
| **라벨 없는 나머지 객체(미표시 객체)** | 시드 안 한 건 그냥 테스트 안 함 (조용히 빠짐) | 보류로 명시 분리 + 보류율을 결과로 측정 |
| **확정 근거** | 응답에 요청한 식별자가 그대로 들어있는가 | 비공개 필드 있음 + 공유 목록에 접근자 없음 |
| **평가 지표** | 탐지 결과 수(finding 개수) | 확정범위 + 오탐률 + 보류율 세 개를 같이 봄 |
| **평가 대상** | 합성 API 2개 | 실제 배포 앱(Gitea, Memos) |

### 핵심 차이: "시드로 뭘 아는가" vs "모르면 어떻게 하는가"
**AuthProbe의 접근**
- "누구 거냐"만 정의하고 시작
- 공개·비공개·공유 구분 없음
- 공개 객체나 공유받은 접근을 취약점으로 오판할 수 있음

**우리 연구의 접근**
- "누구 거냐" + "봐도 되는 범위"를 함께 정의
- 테스트 객체 생성 시점에 가시성을 설정
- 알 수 없는 객체는 보류로 명시하여 투명성 확보

### 실제 의미
쉽게 말해:
- **AuthProbe**: "소유자 확인"까지만 하는 도구
- **우리 연구**: "공개·비공개·공유까지 미리 알고 시작"하는 접근

→ 그 차이가 오탐을 줄이는 지점이고, 모르는 건 모른다고 인정하는 게 보류입니다.
