# AP-EYE 방향성과 태스크 2·4 독립 검토

검토일: 2026-10-06. 검토 대상은 `team_hub`의 최신 교수 피드백, 회의록, 아키텍처, 기존 평가 설계, 태스크 2·4 본문/실행 기록/스크립트와 이전 Akto 소스 조사다. 논문별 수치와 새 후보 조사와는 구분한 **프로젝트 정합성·실험 설계·재현 증거 검토**다. 아래 제안은 팀의 확정 결정이나 검증된 연구 성과가 아니다.

## 1. 판단

**현재 산출물은 근거를 구분한 좋은 조사 초안이지만, 최고의 연구 설계가 확정됐다고 말할 단계는 아니다.** 부족한 것은 논문 수 자체보다 ① 연구 본체의 단일화, ② 실제 Akto 기준선, ③ 외부 실제 앱의 정답 패키지, ④ 정상·공유·보류의 대표성, ⑤ 동일 정보와 입력 비용을 통제한 비교다. 이 다섯 항목을 채워야 자료의 양이 팀의 의사결정으로 이어진다.

방향을 새로 바꾸기보다는 **읽기 BOLA 판정을 연구 본체로 유지하고 Akto 안에서 검증 가능한 작은 개선을 찾는 방향**이 최신 교수 피드백에 가장 가깝다. 한국어 PII는 별도 평가하는 확장 기능이자 upstream 기여 후보로 둔다. PII가 포함되어야만 BOLA를 찾는 설계는 채택하지 않는다.

## 4. 한 줄 정의와 연구 질문 제안

**연구 본체:**

> 기존 Akto는 트래픽 기반 API 식별과 인증 교체형 BOLA 테스트를 제공한다. 우리는 공개·공유 객체와 금지 객체가 섞인 읽기 응답에서 객체별 권한 근거와 실제 반환 내용을 대응시키는 판정을 보강하고, 공개 도구의 재현 대상과 외부 실제 앱의 취약·수정 사례에서 종단 재현율·정상 유형별 오탐률·판정 커버리지·근거 입력 비용으로 평가한다.

**한국 특화 확장:**

> 한국어 개인정보 탐지는 확인된 응답의 노출 항목을 설명하는 별도 모듈로 개발하며, 외부 합성 데이터와 분리된 한국어 스트레스 세트에서 유형별 정밀도·재현율과 문자 경계 F1로 평가한다.

위의 ‘보강’은 검증할 목표이지 원본 Akto가 실제 사례에서 실패했다거나 개선판이 우수하다는 결론이 아니다. 대상 앱·버전이 확정되면 첫 문장의 일반 표현을 실명으로 바꾼다.

검증할 질문은 다음처럼 좁힐 수 있다.

- RQ1: 같은 요청·객체·권한 근거에서, 응답 전체 유사도에 객체별 연결 검증을 추가하면 공개/공유 오탐이나 혼합 목록 미탐이 줄어드는가?
- RQ2: 완전한 권한표 대신 검토된 소수의 근거를 쓸 때, 입력 비용과 확정 가능한 범위는 어떻게 달라지는가? 미지 객체로 전파할 수 없는 경우도 결과다.
- 확장 평가: 동일 입력에서 한국어 규칙/NER가 특정 유형의 미탐을 줄이는가? 그 결과가 BOLA 판정의 정답을 바꾸지는 않는가?

RQ1과 RQ2를 모두 입증해야만 프로젝트가 성립하는 것은 아니다. 예비 결과에서 외부 객체의 권한 근거를 거의 확보할 수 없으면 RQ2의 ‘자동 정책 추론’ 주장을 버리고 **입력 비용 대 확인 범위** 연구로 제한한다.

## 5. 공정한 비교를 위한 두 실험

### 실험 A: 판정 방법 자체

모든 방법에 동일한 요청/응답 묶음과 동일하게 허용된 정책 근거를 준다. 정답은 별도 평가 파일에 숨긴다. 고정 버전 Akto, 기존 설정을 적절히 적용한 Akto, 아래 단순 규칙, 제안 방식을 비교한다. 임계값만 바꾼 비교군도 포함한다.

단순 규칙은 `명시적 deny 근거 + 그 대상의 보호 내용 실제 반환 → BOLA`, `확인된 allow 또는 보호 내용 없음의 유효한 검사 → 해당 관측 정상`, `근거·검사 불충분 → 보류`다. 이 규칙과 성능이 같다면 복잡한 모델 자체의 추가 가치는 입증되지 않는다.

같은 입력이라고 해도 각 도구가 지원하지 않는 정책 형식을 억지로 넣을 수는 없다. 입력 능력/누락을 표에 적고, 도구 간 운영 비교와 **동일 정보를 사용하는 제안 방식/단순 규칙의 비교**를 따로 해석한다.

### 실험 B: 전체 도구 사용 절차

동일 초기 앱 상태와 요청 예산에서 각 도구의 정상 사용 절차대로 실행한다. Akto의 트래픽 seed, AuthProbe의 OpenAPI/목록 탐색, 사람의 객체 생성·공유 설정·테스트 역할 등록 비용이 다름을 기록한다. 단순히 ‘같은 계정 두 개를 사용했다’고 공정성이 보장되지는 않는다.

단계별 수치는 `gold 전체 → 발견 → 실행 → 유효 응답 → 판단 가능 → 정확한 확정`으로 남긴다. 탐색 실패와 판정 실패는 원인이 다르지만 종단 재현율에서는 모두 놓친 양성에 포함한다. Akto가 template 선택 단계에서 건너뛴 사례를 정상 확인으로 세지 않는다.

Akto에 이미 Test Role과 endpoint 조건이 있으므로 ‘권한을 입력할 수 없는 도구’로 비교하면 안 된다. 상용판 문서의 기능과 선택한 OSS 배포에서 실제 사용 가능한 기능도 구분한다. [공식 Test Role 문서](https://docs.akto.io/api-security-testing/how-to/create-a-test-role)

## 6. 정답·보류·표본 수를 고정하는 방법

인가 gold의 단위는 `(앱 및 버전, 요청자, 대상 객체, GET 연산, 정책 상태/시점)`이다. 같은 요청에서 여러 객체가 나오는 목록은 요청별 검출과 객체별 노출을 함께 집계한다. 보호 필드의 반환 여부도 기록하되 필드 단위 인가 문제를 객체 접근 문제와 혼동하지 않는다.

평가자 gold와 탐지기에 보이는 증거의 출처를 다르게 남긴다. 예를 들어 평가자는 DB fixture·공식 공유 설정·취약/수정 코드로 정답을 정하고, 탐지기는 승인된 설정 일부와 요청/응답만 본다. 같은 API의 `private=true` 응답만으로 금지를 확정하면 공유 대상 예외와 오염된 정책 필드를 놓칠 수 있다. 고친 버전의 응답만을 정답으로 쓰는 것도 다른 버그가 없다는 보장은 아니므로 정책 의도와 함께 확인한다.

보류는 **실제 보안 상태의 세 번째 정답이 아니라 도구의 지식 상태**다. 평가자가 정상/BOLA를 아는 사례도 도구에는 근거 부족으로 보일 수 있다. 평가자도 gold를 확정하지 못한 항목은 별도 분석군이다.

| 기록 | 계산과 용도 |
|---|---|
| 전체 재현율 | 확인한 BOLA / 모든 gold BOLA. 미발견·실패·보류인 양성을 분모에서 빼지 않음 |
| 전체 정상군 FPR | 정상인데 BOLA라고 확정한 수 / 모든 gold 정상 |
| 정상/양성별 보류율 | 각각의 gold 집합에서 보류 비율. 모든 정상을 보류해서 FPR만 줄였는지 확인 |
| 확정 집합의 오류 | 확정 판정만의 FP/FN, 해당 분모와 커버리지 동시 표시 |
| 정상 미확인 | 경고 없음/미실행을 정상 확인과 구분 |
| 위험-커버리지 관계 | 같은 커버리지 또는 같은 오류 예산에서 비교. 단일 threshold 한 점만 고르지 않음 |

권장 정상/양성 구분은 `소유자 정상`, `익명 공개`, `로그인 사용자 공개`, `명시적 공유`, `미공유 비공개`, `빈 목록`, `허용 객체만 있는 목록`, `허용·금지 혼합 목록`, `같은 소유자의 다른 객체`, `인증 만료/업무 오류`, `불완전 응답/페이지네이션`이다. 외부 앱에서 원래 지원하지 않는 유형을 넣으려고 앱을 대폭 바꾸지 않는다. 원래 앱의 평가군과 변형 스트레스군을 분리한다.

현재 AuthProbe의 양성 6건은 **1개 취약 GET 인가 경로에 대한 6개 요청**이고 VAmPI의 2건도 책 상세 조회 로직 하나에 대한 양방향 교차 요청이다. 요청 8건을 독립 취약점 8종으로 합산하면 안 된다. 개선이 대상 두 개의 패턴에만 맞는지도 구분해야 한다.

같은 객체에 대한 반복 요청을 bootstrap 독립 표본으로 사용하지 않는다. 원인/endpoint/app으로 묶어 보고하고, 앱이 몇 개뿐이면 좁은 사례 연구라고 적는다. 예를 들어 독립 정상 시험 30건에서 오탐 0건이어도 이항 가정의 단측 95% 상한은 `1-0.05^(1/30)≈9.5%`다. 현재 반복 요청들은 이 독립 가정도 충족하지 않으므로 그 숫자를 실제 FPR 신뢰구간으로 적용할 수 없다. 이 계산은 작은 ‘0건’의 의미를 설명하는 예시다.

PII에서도 같은 템플릿에 이름만 바꾼 필드 수를 독립 문맥 수로 세지 않는다. `앱/문서/원문/템플릿/도메인/엔티티 유형` 별 규모를 남긴다. 경계 일치 확인은 라벨 의미가 맞다는 검증과 다르다.

## 7. Akto 기여 전략과 반증 조건

기존 소스 조사에서 비교기는 경로별 값 집합으로 비교하여 객체 내부 연결이 사라질 수 있고, 원래 객체가 포함된 더 큰 목록의 점수가 내려가는 컴포넌트 사례가 있었다. 이는 객체 연결 보강을 검토할 이유지만 최종 BOLA 오탐·미탐이 관측됐다는 뜻은 아니다. 비교기는 공통 유틸리티이므로 전체 의미를 바꾸면 다른 테스트가 영향을 받을 수 있다. 우선 BOLA용 검증 옵션이나 제한된 템플릿 확장으로 회귀 범위를 좁히는 것이 합리적이다. [고정 비교 구현](https://github.com/akto-api-security/akto/blob/42e88a247fb2a0532ec8d7a8ba6261b794ee3f8d/libs/utils/src/main/java/com/akto/testing/Utils.java#L381)

| 결과가 이렇게 나오면 | 주장과 방향을 이렇게 바꾼다 |
|---|---|
| 실제 Akto에서는 추가 필터가 문제 사례를 막음 | 컴포넌트 위험을 전체 탐지 실패로 주장하지 않음. 해당 가설 축소/교체 |
| 기존 Test Role/YAML 설정만으로 동일 개선 | 새 탐지 알고리즘보다 설정·회귀 테스트·문서 기여로 설명 |
| 단순 객체 ID/표식 일치만으로 개선판과 동일 | 복잡한 NER/LLM을 판정 본체에 넣을 이유 없음 |
| 정상 오탐 감소가 보류 증가로만 발생 | 같은 커버리지·입력 비용에서 재평가, 우월성 주장 보류 |
| 외부 실제 앱에서 동일 문제가 재현되지 않음 | 합성 스트레스 조건의 결과로 한정, 실서비스 일반화 주장 금지 |
| 개선판만 객체별 정답을 추가로 제공받음 | 입력량별 성능 비교로 다시 설계, 순수 판정 성능 개선이라고 하지 않음 |
| PII 인식 성공 여부가 인가 위반 판정을 바꿈 | 두 모듈을 분리. 비PII 비공개 내용도 BOLA 검증에 포함 |
| 수정이 upstream에 받아들여지지 않음 | 기능 가치와 유지 비용을 검토한 후 제품 fork를 선택. PR용 GitHub fork와 독립 배포 제품은 구분 |

가장 작은 기여 후보는 `외부 실제 실패 재현 + 실패하는 회귀 시험 + 제한된 수정 + 기존 동작 회귀 없음`이다. 한국어 전화번호/정형 PII 규칙은 별도 작은 기여로 진행할 수 있지만, 정규식 추가만으로 새로운 연구라고 포장하지 않는다. 프로젝트의 포트폴리오 가치와 학술적 새로움은 다른 평가다.

## 8. Akto 전체 기준선의 로컬 실행 사전조건

2026-10-06 읽기 확인 결과다. 새 서비스 시작, 이미지 다운로드, 기존 컨테이너 수정·종료는 하지 않았다.

| 항목 | 관측 |
|---|---|
| Docker | Client/Engine 29.6.2, Linux backend 정상 응답 |
| Compose | v5.3.1 |
| 엔진 자원 | 총 메모리 16,515,796,992 byte(약 15.38 GiB), 14 CPU. 가용 메모리/실행 여유를 보장하는 수치 아님 |
| 기존 실행 | 조회 당시 7개 컨테이너. 다른 프로젝트/학습 환경이므로 변경 대상 아님 |
| Akto 관련 이미지 | 목록에 Akto dashboard/testing/Mongo 이미지 없음 |
| 소스 | Akto `42e88a247fb2a0532ec8d7a8ba6261b794ee3f8d`, tests-library `ce2267da7e28927876b41d944e63bdde10e41e00` |
| 로컬 설치 | Java 21 있음, PATH에 Maven 없음. 수동 source build가 바로 준비된 상태는 아님 |

고정 소스의 compose는 Mongo 7.0.4, dashboard `:local`, testing `:local`, puppeteer `:latest`를 지정한다. `local/latest`는 소스 SHA 고정과 다르다. 실제 평가에서는 선택한 이미지의 digest와 실행 버전, 테스트 라이브러리/설정을 기록해야 한다. 원본 compose는 공통 컨테이너명과 호스트 포트를 사용하므로 별도 프로젝트명·네트워크·볼륨과 loopback 포트 구성이 필요하다. Mongo의 외부 공개는 이 평가에 필요하지 않다. [고정 compose](https://github.com/akto-api-security/akto/blob/42e88a247fb2a0532ec8d7a8ba6261b794ee3f8d/docker-compose.yml)

실행 경로는 `격리한 대상 → 소유자 정상 요청/응답 HAR 또는 지원 수집 경로 → 인벤토리 → 대체 계정 Test Role → 지정 GET endpoint와 지정 BOLA test → 선택/실행/skip/판정 수집`이다. 공식 문서상 Test Role이 실행 전제이며 HAR 업로드는 수동 인벤토리 수집 경로다. 자기 객체 정상 조회 seed가 누락되면 검사 선택부터 달라질 수 있다. [Run Test](https://docs.akto.io/api-security-testing/how-to/run-test), [HAR 수집](https://docs.akto.io/traffic-connector/manual/har-file-upload)

**CLI만 실행해서 끝내면 안 된다.** 공식 CLI 문서는 context를 사용하는 테스트를 건너뛸 수 있다고 명시한다. 현재 `REPLACE_AUTH_TOKEN` 템플릿에도 `private_variable_context > 0`이 있다. 이 이름만으로 해당 테스트가 CLI에서 반드시 skip된다고 단정하지는 않되, 실제 선택/실행 기록을 확인해야 한다. 템플릿의 기본 method 조건은 `OPTIONS` 제외이므로 읽기 평가에서는 수집/선택 endpoint를 GET으로 명시적으로 제한한다. [CLI 한계](https://docs.akto.io/api-security-testing/how-to/run-tests-in-cli-using-akto), [고정 템플릿](https://github.com/akto-api-security/tests-library/blob/ce2267da7e28927876b41d944e63bdde10e41e00/Broken-Object-Level-Authorization/BOLAByChangingAuthToken.yaml)

완료 증거는 UI 접속 화면 하나가 아니라 `배포 이미지 digest + 대상/정책 fixture + 수집 seed + 테스트 설정 + 실제 재생 요청 수 + 응답/판정 대응 + skip 근거`다. 합성 인증 값은 공유 보고서에 싣지 않고 local secret 입력 경로를 사용한다. 현재 이 전체 기준선은 **NOT_RUN**이다.

## 9. 이번 독립 검토에서 실제로 보강·재실행한 것

AuthProbe 재현 스크립트의 기존 정답 확인은 성공 status와 owner를 검사했다. 같은 소유자의 다른 객체가 잘못 돌아오는 경우를 잡지 못할 수 있어, root의 허가 후 다음처럼 보강했다.

- 생성 요청의 name과 소유자를 미리 고정한 fixture와 응답 전체(id/owner/name/note)를 대조한다.
- 상세 조회마다 요청 id와 응답 id, 해당 fixture 본문 전체가 일치하는지 확인한다.
- 수정 버전의 차단은 지정한 오류 응답이며 보호 객체가 없음을 확인한다.
- 목록은 소유자가 동일한지뿐 아니라 정확한 fixture 객체 집합과 일치하는지 확인한다.
- BOLA finding과 gold 요청을 `(requester, owner, object_alias)`로 1:1 대응시키며 중복 finding이 없음을 확인한다.
- 원래 앱 소스/서버 로직/계정/객체 수/생성 입력은 변경하지 않았다.

강화한 검증으로 localhost HTTP 재실행을 완료했다. **취약: BOLA 6 + 열거/IDOR 2; 수정: finding 0; 버전별 14건, 총 28건의 정답 응답 확인**으로 이전 결과와 같다. 새 성공은 gold 확인을 강화했다는 의미이며 통계적으로 독립인 새 취약점이나 새 앱을 추가한 것이 아니다.

변경 파일:

- `team_hub/docs/research/evaluation-datasets-2026-10-06/scripts/reproduce_authprobe.py`
- `team_hub/docs/research/evaluation-datasets-2026-10-06/evidence/authprobe-reproduction.json`
- 같은 JSON의 기존 local evidence 경로

변경 전 파일은 이 디렉터리의 `reproduce_authprobe.before.py`, `authprobe-reproduction.before.json`에 보존했다. 새 evidence SHA-256은 `ae3fc113018771f845bfa5f5421d4a9bc5e4874aa78d0d2ac1d1f14a300d7047`이다. 통합 manifest는 최종 산출물 작성자가 갱신해야 한다.

이 검토의 완료 범위는 방향·평가 설계 검토, Akto 실행 전제의 읽기 확인, AuthProbe gold 보강과 재실행이다. Akto 전체 실행, 개선판 구현, 실제 앱 재현 및 추가 논문/한국어 데이터 조사 결과는 다른 작업과 합쳐 확인해야 한다.
