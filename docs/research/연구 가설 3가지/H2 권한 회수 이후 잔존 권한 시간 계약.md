# 권한 회수 이후 잔존 권한을 검출하는 시간 계약 기반 API 인가 진단(젤 ㄱㅊ)

> **1차** (노션 토글)
> # 권한 회수 이후 잔존 권한을 검출하는 시간 계약 기반 API 인가 진단
>
> **선정 결론:** 팀원의 BOLA 연구와 별도로, **“관리자 권한을 회수했는데 기존 세션으로 관리자 API를 계속 사용할 수 있는가?”**를 연구한다. 사용자의 신원과 호출 기능을 고정하고, 권한이 바뀌는 시점과 이후의 실제 응답을 검사하는 주제다.
>
> **현재 근거 수준:** 공식 취약점 공지와 논문 원문 구간을 확인했고, 현재 데모의 자동 시나리오 16개를 소스에서 조사했다. 별도로 만든 인공 반례 16개에 판정 규칙을 실행했다. **실제 제품의 취약점 재현, HTTP 기반 신규 진단기 실행, 제안 방법의 정확도 향상 검증은 아직 수행하지 않았다.** “최초 연구”나 “성능이 입증된 방법”으로 주장하지 않는다.
>
> > **가설**
> >
> > 유효한 계정의 역할·기능 권한을 회수할 수 있고, 해당 기능에 대한 회수 후 금지 정책과 권한 반영 기한을 확인할 수 있는 REST/JSON API에서, **권한 회수 전후의 동일 사용자 요청을 연결하고, 변경 완료 근거·기한·신규 보호 데이터 반환·대조 요청을 함께 검사하는 진단 방법**을 사용하면, 같은 요청 시퀀스와 요청 예산을 사용하는 상태코드 중심 검사보다 **정상적인 반영 지연과 오류 응답을 인가 취약점으로 잘못 확정하는 비율을 낮추면서, 기존 세션에 남은 권한으로 발생하는 실제 데이터 반환을 검출할 수 있다.**
> >
> > **필요한 이유**
> >
> > 정적 역할 검사는 “지금 이 역할이 이 기능을 사용할 수 있는가”를 확인하지만, 권한을 변경하기 전에 만들어진 세션·인가 캐시가 계속 사용되는 상황은 별도 상태 전이가 필요하다. 반대로 회수 직후의 성공 응답을 모두 취약점으로 보면 서비스가 허용하는 반영 지연까지 오탐할 수 있다.
> >
> > 이를 해결하려면 **어떤 권한이 언제부터 없어져야 하는지에 대한 작은 시험 계약**, 회수 상태를 확인할 독립적인 근거, 보호 기능의 실제 실행을 보여주는 응답 증거를 함께 사용해야 한다. 기한이나 권한 근거가 없으면 보류한다.
> >
> > **직접적인 선행 연구**
> > - Ruoming Pang 외, *Zanzibar: Google’s Consistent, Global Authorization System*, USENIX ATC 2019, pp. 33–46. [학회 원문](https://www.usenix.org/conference/atc19/presentation/pang)
> > - Nazanin Bayati Chaleshtari, Fabrizio Pastore, Arda Goknil, Lionel C. Briand, *Metamorphic Testing for Web System Security*, IEEE TSE 49(6), 2023, pp. 3430–3471. [저자 원고](https://arxiv.org/html/2208.09505v2)
> > - Chengcheng Xiang 외, *Testing Access-Control Configuration Changes for Web Applications*, arXiv:2505.12770v1, 2025. **아래 분석은 해당 프리프린트 버전 기준**이다. [원문](https://arxiv.org/html/2505.12770v1)
> > - Igor Santos-Grueiro, *When Does Authorization End? Effect Closure at Provider Boundaries*, arXiv:2609.02866v1, 2026. **동료심사 게재를 확인하지 않은 프리프린트**로 신규성 검토에 포함했다. [원문](https://arxiv.org/html/2609.02866v1)
> >
> > **차이점**
> >
> > 선행연구에는 이미 상태를 가진 요청 시퀀스, 접근제어 변경 전후 비교, 인가 일관성, 권한 회수의 완료 조건이 있다. 따라서 “시간을 고려한다” 또는 “보류한다”만으로는 새로운 기여가 아니다.
> >
> > 본 연구는 **AP-EYE가 관찰할 수 있는 HTTP 응답과 소수의 권한 변경 근거로, 기한 이후에 새로 시작한 보호 기능 호출을 어디까지 판정할 수 있는지**에 범위를 둔다. 기존 세션·새 세션·권한 유지 대조 계정을 함께 사용하고, 오탐률·재현율·보류율·근거 준비 비용·관측한 잔존 권한 시간을 평가한다. 이 구체적인 결합의 유용성은 강한 비교군과 실험으로 확인해야 한다.
>
> ## 1. 주제 정의
>
> **한 문장 설명**
>
> “권한을 회수한 사용자가 기존 세션으로 보호 기능을 계속 사용할 때, 정상적인 반영 지연과 실제 인가 실패를 구분할 수 있는가?”를 **권한 변경의 시간 계약과 응답 증거를 사용하는 상태 전이 검사**로 검증하는 연구.
>
> **연구 범위**
>
> > 합성 데이터가 있는 시험용 REST/JSON API에서, 정상 사용 중인 계정의 관리자 역할 또는 기능 권한을 회수한 뒤 보호된 읽기 기능을 다시 호출하는 방법을 개발한다.
> >
> > 회수 후 유효 금지 정책, 변경 완료, 반영 기한, 호출 주체와 응답 데이터의 대응이 확인되면 위반 또는 관측 범위 내 정상 결론을 낸다. 정책·기한·계정 유효성·응답 의미가 불명확하면 이유를 붙여 보류한다.
> >
> > 이후 통제 가능한 시험 서버와 버전을 고정한 공개 애플리케이션에서 정적 검사, 상태 전이 재호출, 수동 회귀 검사와 비교한다.
>
> | 구분 | 내용 |
> | --- | --- |
> | 연구 대상 | 역할·기능 권한 회수 이후에도 실행되는 보호된 읽기 API. 시작점은 관리자 전용 내보내기 기능 |
> | 포함 범위 | 동일 계정의 admin → member 전환, 특정 기능 권한 제거, 기존 세션과 새 세션 차이, 인가 결정 캐시, 선언된 반영 지연, 유한한 관찰 시점 |
> | 제외 범위 | 타인 객체 ID 교체를 이용한 BOLA, 필드 과다 반환 자체인 BOPLA, 비밀번호 탈취, 단순 로그아웃/토큰 만료, 비동기 작업의 최종 효과, 회수 전에 시작한 진행 중 요청, 쓰기·삭제 기능, 전체 분산 시스템의 회수 완료 증명 |
> | 필요한 입력 | 시험 계정과 별도 변경 관리자, 권한 유지 대조 계정, 보호 기능 1개 이상, 변경·확인 인터페이스, 회수 후 유효 금지 정책, 기한과 그 시작 사건, 합성 검증 표식, 초기화 방법 |
> | 최종 산출물 | 상태 전이 진단 모듈, 최소 시험 계약 형식, 근거별 판정 기록, 정상·취약·보류 반례 데이터, 재현 가능한 비교 실험 |
> | 현재 산출물 | 본 연구계획, 기존 소스 조사 코드·결과, 16개 인공 반례 및 판정 규칙 점검 결과 |
>
> ### 팀원 연구와의 관계
>
> | 항목 | 팀원의 BOLA 가설 | 이번 추가 가설 |
> | --- | --- | --- |
> | 핵심 변화 | 요청 계정과 객체의 소유·공유 관계 | **같은 계정의 권한이 시간에 따라 변경됨** |
> | 핵심 질문 | B가 A의 객체를 읽어도 되는가? | 방금 관리자 권한을 잃은 A가 기존 세션으로 관리자 기능을 계속 사용하는가? |
> | 필요한 근거 | 해당 객체의 공개·비공개·공유 상태 | 기능 권한의 변경 이력·반영 기한·기존 세션의 실제 동작 |
> | 대표 반례 | 공개·공유 객체를 타인 접근으로 오탐 | 허용된 반영 지연을 취약점으로 오탐하거나 401을 인가 정상으로 오판 |
> | 재사용 가능 부분 | 요청·응답 수집, 근거 저장, 보류 표시 | 기존 수집기를 활용하되 시간·변경·세션 문맥을 추가 |
>
> BFLA는 기능 권한 검사의 분류이고, 본 연구의 주제는 그중 **권한 회수의 시간적 적용**이다. 모든 잔존 권한 문제를 BFLA 하나로 강제 분류하지 않는다. [OWASP API5:2023](https://api-security.owasp.org/editions/2023/en/0xa5-broken-function-level-authorization/)은 기능별 인가 문제를 정의하지만, 이 연구의 신규성이나 성능을 입증하는 논문은 아니다.
>

>
> | 후보 | 선정 판단 |

> | 권한 회수 후 기존 세션·인가 캐시의 잔존 권한 | 실제 공지된 결함, 현재 데모의 구체적 공백, 시간·증거·보류를 함께 평가할 여지가 있어 선정 |
> | 장기 작업·메시지 큐의 회수 이후 최종 실행 | 의미는 크지만 현재 GET 중심 데모를 크게 벗어나며 EffectBound와도 비교 부담이 큼 |

> ## 2. 용어 정리
>
> | 용어 | 쉬운 설명 | 본 연구에서의 의미·기준 |
> | --- | --- | --- |
> | 인증 | 요청한 사람이 누구인지 확인하는 것 | 같은 시험 사용자의 유효한 로그인 문맥임을 확인하는 전제 |
> | 인가 | 그 사람이 해당 기능을 써도 되는지 결정하는 것 | 특정 tenant·subject·HTTP method·route의 기능 권한 |
> | 권한 회수 | 이전에 있던 권한을 없애는 것 | 계정 삭제가 아니라 살아 있는 계정의 역할·기능 권한을 제거 |
> | 잔존 권한 | 없어져야 할 권한이 계속 작동하는 상태 | 회수 반영 기한 이후 새로 시작한 요청에서 금지된 기능의 데이터가 반환되는 상태 |
> | 기존 세션 | 권한을 회수하기 전에 사용하던 로그인 문맥 | 회수 전 허용 동작을 확인하고 그대로 유지한 세션 |
> | 새 세션 | 권한을 회수한 뒤 같은 사용자로 다시 만든 로그인 문맥 | 별도의 클라이언트 문맥. 전역 로그아웃으로 기존 세션을 없애지 않아야 함 |
> | 시간 계약 | 권한 변경이 언제까지 반영되어야 하는지 정한 약속 | 기한 Δ와 기준 사건 t0를 시험 전에 명시. 평균 전파 시간을 최대 기한으로 바꾸어 쓰지 않음 |
> | 독립적인 변경 근거 | 검사 대상 응답과 별도로 권한 변경을 확인하는 자료 | 관리 인터페이스의 적용 버전·이력·유효 권한 확인. 변경 요청의 200/202만으로 대체 불가 |
> | 검증 표식 | 이번 시험의 보호 데이터임을 알아볼 수 있는 합성 값 | 회수 확인 뒤 권한 있는 관리자만 작성하고 시험 요청에는 넣지 않는 새 값 |
> | 위반 확정 | 금지된 기능의 실제 데이터 반환을 확인함 | 전제가 충족되고 기한 이후 요청에서 신규 보호 표식이 반환됨. HTTP 상태코드만으로 판정하지 않음 |
> | 정상 확인 | 정해 둔 검사에서는 권한 회수가 적용됨 | 예정된 관찰에서 인증은 유효하고 보호 기능이 명시적으로 거부되며 대조 요청은 정상. **연속 시간·모든 서버의 안전 보증은 아님** |
> | 판정 보류 | 확보된 근거로 위반·정상 중 하나를 확정할 수 없음 | 기한 없음, 변경 미확인, 재부여, 401, 서비스 오류, 응답 의미 불명확, 관찰 누락 등 |
> | 판정 오라클 | 시험 결과가 기대와 맞는지 판단하는 기준 | 검토된 계약과 관측 근거를 비교하는 결정 규칙. LLM의 추측으로 권한을 확정하지 않음 |

> ## 3. 근거 정리
>
> ### 3.1. 권한 변경 이후의 오래된 인가 상태는 실제 보안 문제다
>
> **선행 연구·공식 자료에서 확인한 내용**
>
> > “an already logged-in user can keep old (revoked) privileges until logout/session expiry”
>
> → 이미 로그인한 사용자가 로그아웃하거나 세션이 만료될 때까지 회수된 권한을 유지할 수 있다는 뜻이다.
> - **출처:** pyLoad 유지관리자의 GHSA-66hx-chf7-3332, CVE-2026-41133, 2026-04-13 공개, Summary·Details·Impact. [공식 공지](https://github.com/pyload/pyload/security/advisories/GHSA-66hx-chf7-3332)
> - **직접 확인되는 사실:** 로그인 때 저장한 역할·권한을 이후 검사에서 사용하고, DB의 권한 변경이 기존 세션에 반영되지 않는 경로를 공지가 설명한다. API 세션 경로도 명시한다.
> - **본 연구와의 연결:** 일반 사용자와 관리자를 처음부터 따로 로그인시키는 검사만으로는 기존 관리자 세션에 남은 권한을 드러내기 어렵다.
> - **해석의 한계:** 공지의 PoC는 소스 패턴 점검이라고 명시되어 있다. 이번 조사에서 해당 제품을 구동해 재현하지 않았다. 피해 규모나 실제 침해 사고 발생을 이 공지로 추정하지 않는다.
>
> **이를 뒷받침하는 시스템 연구**
>
> > “when we apply old ACLs to new content.”
>
> → 새 콘텐츠에 오래된 접근제어 목록을 적용하면 잘못된 접근이 생길 수 있다.
> - **출처:** Pang 외, Zanzibar, USENIX ATC 2019, §2.2, proceedings pp. 34–35. [PDF](https://www.usenix.org/system/files/atc19-pang.pdf)
> - **직접 확인되는 사실:** 권한 제거 이후 추가된 콘텐츠가 이전 ACL로 허용되는 “new enemy” 문제와, ACL·콘텐츠 변경의 순서를 지켜야 할 필요성을 설명한다.
> - **본 연구와의 연결:** 회수 후 만든 검증 표식은 과거에 받은 데이터를 다시 보았다는 설명과 신규 서버 반환을 구분하는 데 도움을 준다.
> - **해석의 한계:** Zanzibar는 인가 시스템의 일관성을 보장하는 설계다. AP-EYE의 외부 진단 성능을 평가한 연구는 아니며, 표식을 쓴다는 것 자체도 새로운 원리가 아니다.
>
> ### 3.2. 연구의 공백은 “요청 순서” 자체가 아니라, 판정 근거와 적용 범위를 검증하는 데 있다
>
> **선행 연구에서 확인한 내용**
>
> > “ACtest outputs the impact of configuration changes, in the form of access-control behavior comparison.”
>
> → ACtest는 접근제어 설정을 바꾸기 전후에 달라진 허용·거부 동작을 보여준다.
> - **출처:** Xiang 외, ACtests, arXiv:2505.12770v1, 2025, §3·§4·§4.3.1. [원문](https://arxiv.org/html/2505.12770v1#S3)
> - **직접 확인되는 사실:** 실제 프로그램·설정·데이터를 활용하는 작은 시험 환경에서 변경 영향을 비교한다. 결과가 의도한 것인지는 관리자가 검토한다.
> - **본 연구와의 연결:** 변경 전후 비교는 이미 있는 접근이다. AP-EYE에서는 서버 프로그램을 변환하지 않고 얻는 근거만으로 **세션을 유지한 회수 시험**을 구성할 수 있는지, 근거 준비 비용이 얼마나 드는지를 확인한다.
> - **해석의 한계:** 해당 논문이 모든 시간적 권한 회수 검사를 지원하지 않는다고 단정하지 않는다. 확인한 설계와 평가의 중심이 설정 변경 영향이라는 뜻이며, 원 도구와의 재현 비교는 미실행이다.
>
> **요청 시퀀스를 다루는 기존 검사**
>
> > “action sequences are necessary to describe interactions with complex systems.”
>
> → 복잡한 시스템의 상호작용을 검사하려면 동작의 순서를 다뤄야 한다.
> - **출처:** Chaleshtari 외, MST-wi, IEEE TSE 2023, 저자 원고 §XII Related Work의 metamorphic relation pattern 비교. [원문](https://arxiv.org/html/2208.09505v2)
> - **직접 확인되는 사실:** 변형 전후의 입력·출력 시퀀스 관계로 보안 성질을 검사한다. 상태를 고려하는 보안 시험은 선행연구에 이미 존재한다.
> - **본 연구와의 연결:** 역할 회수 시퀀스를 하나의 구체적인 보안 관계로 정의하되, 타이밍 계약·대조 요청·실제 데이터 증거가 추가하는 효과를 분리 평가해야 한다.
> - **해석의 한계:** 본문 검색에서 특정 단어가 발견되지 않았다는 이유로 “권한 회수 기능이 없다”고 결론 내리지 않는다. 전체 MR 부록·도구 구현과의 중복 확인은 남은 작업이다.
>
> **복잡한 순서와 서비스의 의도를 추가로 정의해야 하는 이유**
>
> > “complex attack scenarios cannot be considered”
>
> → 해당 논문에서 정한 작은 변이 연산자만으로 복잡한 공격 시나리오를 모두 다루지는 않는다.
> - **출처:** Sébastien Salva·Jarod Sue, *Security Testing of RESTful APIs With Test Case Mutation*, arXiv:2403.03701v1, 2024, §3.3의 C2. [원문](https://arxiv.org/html/2403.03701v1#S3.SS3)
> - **직접 확인되는 사실:** 기존 테스트·로그로부터 보안 테스트를 변이하는 방법과 적용 조건을 설명하며, pass/fail/inconclusive 상태도 사용한다.
> - **본 연구와의 연결:** 회수·완료 확인·대기·대조 호출의 전제를 가진 시험 계약을 별도로 정의할 필요가 있다.
> - **해석의 한계:** 작은 변이의 한계를 모든 API 검사 도구에 일반화하지 않는다. **보류 상태 자체도 본 연구가 처음 도입하는 개념이 아니다.**
>
> **정상적인 반영 지연도 존재한다**
>
> > “access changes, such as granting a role or denying a permission, are eventually consistent.”
>
> → 역할이나 권한의 변경은 시스템 전체에 즉시 반영되지 않을 수 있다.
> - **출처:** Google Cloud, *Access change propagation*, 첫 문단 및 전파 시간 표, 2026-10-01 확인. [공식 문서](https://docs.cloud.google.com/iam/docs/access-change-propagation?hl=en)
> - **직접 확인되는 사실:** 변경 종류에 따라 전파 시간이 다르고, 그동안 회수된 권한이 사용될 수 있다고 설명한다.
> - **본 연구와의 연결:** 모든 “회수 직후 성공”을 취약점으로 분류하는 오라클에는 문제가 있다.
> - **해석의 한계:** 문서의 “typically” 또는 “or longer” 수치는 엄격한 최대 지연 보증이 아니다. 이를 AP-EYE의 Δ로 가져오거나, 시간이 지났다는 이유만으로 Google IAM의 취약점을 확정해서는 안 된다.
>
> **최신 인접 연구가 신규성 주장에 주는 제약**
>
> > “Provider-local completion does not imply application-level closure.”
>
> → 공급자 내부의 작업 완료가 애플리케이션 관점의 모든 권한 효과 종료를 뜻하지는 않는다.
> - **출처:** Igor Santos-Grueiro, EffectBound, arXiv:2609.02866v1, 2026, §VI Discussion; §I·§II도 확인. [원문](https://arxiv.org/html/2609.02866v1)
> - **직접 확인되는 사실:** 이미 허용된 작업이 회수 이후 효과를 낼 수 있는 문제, 근거를 가진 계약, 부족한 근거에 대한 무판정을 다룬다.
> - **본 연구와의 연결:** “완료 응답을 신뢰하지 않고 계약을 검증한다”는 큰 아이디어도 독창성 근거로 독점할 수 없다. AP-EYE에서는 **기한 이후 시작한 읽기 요청**의 관측 가능한 위반 증거와 진단 비용에 집중한다.
> - **해석의 한계:** 프리프린트이며 논문의 실험·기계 검증을 이번에 재현하지 않았다. 본 연구는 진행 중 작업까지 포함한 전체 효과 종료를 보장하지 않는다.
>

> ## 5. 제안 방법과 검증 계획
>
> ### 제안 방법
> 1. **기능 단위 시험 계약을 작성한다.** 호출 주체·tenant·기능·회수 전후 유효 권한·시간 기준·대조 응답·검증 표식·초기화 범위를 담당자가 확인한다. “역할이 제거됨”만으로 금지라고 하지 않고 상속·다른 역할·예외 허용을 포함해 해당 기능의 유효 금지를 확인한다.
> 1. **정상 허용 상태와 기존 세션을 준비한다.** 시험 사용자 A의 기존 세션으로 보호 기능을 호출해 정상 허용과 캐시가 사용될 수 있는 경로를 만든다. 별도의 관리자 C는 변경을 수행하고, 권한 유지 사용자 B는 대조 요청을 담당한다.
> 1. **A의 기능 권한을 회수하고 적용 근거를 확보한다.** 변경 응답의 성공 여부와 별도로 버전·변경 이력·유효 권한 상태를 확인한다. A의 계정 자체는 유지한다.
> 1. **회수 확인 후 새 합성 표식을 기록한다.** C가 보호된 내보내기 데이터에 예측하기 어려운 새 표식을 넣는다. A의 요청에는 그 값을 보내지 않는다. B가 이를 받을 수 있는지 확인해 데이터 존재와 응답 경로를 검증한다.
> 1. **예정된 시점에 대조 요청을 실행한다.** 기한 전 관찰은 지연 특성으로 기록하고, 기한 이후에는 A의 기존 세션, A의 별도 새 세션, B의 권한 유지 세션을 같은 기능에 사용한다. 요청 순서를 교대하고, 서로의 세션을 갱신·폐기하지 않는지 확인한다.
> 1. **계약과 실제 응답 증거를 비교한다.** 기한 이후 A에게 새 보호 표식이 반환되면 코드가 200이든 403이든 위반 증거다. 빈 응답, 401, 서비스 오류, 근거 충돌은 원인별로 보류한다.
> 1. **유한한 관찰 결과와 근거를 저장한다.** 회수 사건·요청·응답·정책 버전·표식 확인·보류 이유를 연결한다. 시험 환경을 초기화하고 조건을 바꿔 반복한다.
>
> ```mermaid
> sequenceDiagram
>     participant R as 시험 실행기
>     participant C as 변경 관리자
>     participant P as 권한 상태 확인
>     participant A as 업무 API
>     R->>A: 기존 세션 S0로 보호 기능 정상 호출
>     C->>P: 시험 사용자의 기능 권한 회수
>     P-->>R: 적용 버전과 유효 금지 근거
>     C->>A: 회수 확인 뒤 합성 표식 작성
>     R->>A: 권한 유지 계정으로 표식 존재 확인
>     Note over R,A: 계약상 기한과 예정 관찰 시점 확인
>     R->>A: 회수된 사용자 S0로 동일 기능 호출
>     R->>A: 같은 사용자의 새 세션 S1로 호출
>     R->>A: 권한 유지 계정으로 대조 호출
>     A-->>R: 응답 본문과 명시적 거부 근거
>     Note over R: 계약·시간·본문 증거로 확정 / 정상 관찰 / 보류
> ```
>
> ### 시험 계약의 최소 필드
>
> | 필드 | 예시·역할 |
> | --- | --- |
> | 기능 식별 | tenant=alpha, subject=test-user-A, GET /admin/export |
> | 기대 권한 | 회수 전 allow, 회수 후 deny. 다른 허용 경로 없음 |
> | 변경 근거 | change_id, policy_version_before/after, 적용 확인 출처 |
> | 시간 기준 | t0가 어떤 사건인지, Δ의 단위와 근거 문서, 측정 오차 여유 ε |
> | 세션 문맥 | 회수 전 세션 S0, 회수 후 별도 세션 S1. 로그에는 비밀 대신 시험용 참조 ID |
> | 보호 데이터 증거 | 표식 작성 사건·버전·로컬 매칭 결과. 요청에 표식을 포함하지 않았다는 확인 |
> | 대조 조건 | 권한 유지 계정의 정상 결과, 시험 사용자 인증 유효성, 재부여·데이터 변경 여부 |
> | 응답 계약 | 403 또는 서비스가 정의한 거부 봉투. 보호 데이터가 포함되면 거부 코드보다 데이터 증거를 우선 |
> | 관찰·초기화 | 관찰 시점 집합, 총 요청 예산, 대상 인스턴스 범위, 반복 사이 초기화 절차 |
>
> **권한표가 필요 없다는 주장은 하지 않는다.** 전체 시스템의 행렬 대신 시험할 기능에 대한 작은 계약으로 범위를 제한하는 것이며, 그 계약을 준비·검토하는 비용도 측정한다.
>
> ### 시간과 관측 범위의 정의
> - t0: 계약이 정의한 권한 회수 효력 계산의 시작 사건.
> - Δ: 그 사건 이후 허용되는 최대 반영 지연. **엄격한 계약이 없으면 결함 확정용 Δ는 미정**이다.
> - tc: 독립적인 확인 경로에서 회수 적용 근거를 얻은 시각.
> - D = t0 + Δ: 계약상 반영 기한.
> - 주 판정 요청은 **시작 시각이 max(D, tc) + ε보다 뒤**인 요청으로 제한한다. 회수 전에 시작한 요청은 제외한다.
> - tc가 t0보다 늦다고 해서 기한을 tc + Δ로 조용히 이동시키지 않는다. 각 서비스의 기한 시작 사건을 그대로 따른다.
> - 한 시험 실행기의 단조 시계를 사용하고, 서버 시각과 비교해야 하면 시계 오차를 별도로 기록한다. 정확한 기준 사건을 관찰할 수 없으면 보수적 관찰 시각만 보고하고 기한 준수 결론은 보류한다.
> - 제어 서버의 적용 확인은 모든 복제본의 적용 완료가 아니다. 각 데이터 경로의 응답을 별도로 관찰한다.
> - 첫 403 이후 다른 서버에서 다시 데이터가 나올 수 있다. 따라서 **첫 거부 시각 = 전역 회수 완료 시각**으로 쓰지 않는다.
>
> 신규 표식이 없는 과거 보호 데이터도 실제 재노출일 수 있다. 본 1차 연구에서는 신규 호출 효과를 확실히 구분하기 위해 그 경우를 보류하고 별도 조사 대상으로 남긴다. 이 보수적 선택이 놓치는 위반 비율도 평가한다.

> ### 판정 기준
>
> | 판정 | 필요한 근거 | 관찰 결과 | 근거 부족·충돌 시 처리 |
> | --- | --- | --- | --- |
> | 권한 회수 위반 확정 | 유효 금지 정책, 적용 근거, 유효한 시간 기준·기한, 시험 주체·응답 대응, 회수 이후 표식 | 기한 이후 새 요청에서 보호 표식이 반환됨 | 빠진 전제가 있으면 보류. 위반 원인을 세션 캐시라고 자동 단정하지 않음 |
> | 관측 범위 정상 | 위 전제, 유효한 인증, 계획한 요청 완료, 권한 유지 대조의 정상 동작 | 모든 지정 관찰에서 보호 데이터 없이 명시적 인가 거부 | 관찰 누락·401·오류·대조 실패는 보류. 전체 시스템 안전을 뜻하지 않음 |
> | 판정 보류 | 위반·정상 중 하나에 필요한 증거가 없음 | 빈 200, 500, 기한 미정, 적용 미확인, 재부여, 오래된 본문 등 | 이유 코드와 확보한 증거를 기록. 정상 건수에 합치지 않음 |
>
> 기존 세션만 허용되고 새 세션은 거부되면 “세션 문맥에 따라 결과가 다름”까지 말할 수 있다. 두 세션 모두 허용되어도 계약을 위반한 신규 데이터 반환은 검출할 수 있다. **어느 캐시·복제·검사 코드가 원인인지는 별도의 서버 근거가 필요하다.**
>
> 역할 회수 시 기존 세션을 무효화하는 정상 구현도 있다. 이때 401은 “접근 차단 관찰”로 기록하지만, 유효한 인증 문맥에서 인가 경로가 올바르게 판정했다는 증거와는 구분한다. 새 세션으로 같은 사용자의 인가 결과를 추가 확인하며, 401 보류를 취약하다는 판정으로 해석하지 않는다.

> | 인가 판정 | 현재 승인 정책과 응답 증거의 비교 | 별도 temporal_oracle. 정적 TOKENS의 과거 역할을 현재 정답으로 사용하지 않음 |
> | 근거 저장·보고서 | events/findings/runs | 변경 사건·정책 버전·보류 이유·관찰 시간선을 연결 |
> | 개인정보 분류·로컬 LLM | 기존 후보 분석 기능 | 이번 오라클의 필수 요소가 아님. 성능 실험에서 사용 여부를 고정 |
>
> 기존 GET 프록시에 운영 권한 변경을 일반 기능처럼 섞지 않는다. 상태 변경은 **연구용 시험 실행기와 고정된 시험 환경**에서 제공하고, 관측 모듈은 결과를 기록한다. 자동 차단이나 실제 조직 계정의 권한 회수는 이번 연구 산출물의 범위에 없다.
>

> | 실험 조건 | 계정·tenant·기능·관찰 시점·요청 예산·서버 초기화 동일. 세션 캐시, 인가 캐시, 지연, 응답 모양을 통제. 요청 순서를 교대하며 테스트 세션 간 부작용 확인 |
> | 학습·조정과 최종 평가 분리 | 개발용 반례와 별도로 아직 보지 않은 결함·앱에 최종 평가. 이번 16개 설계 반례를 최종 시험셋으로 재사용하지 않음 |
> | 가설 지지·기각 기준 | 아래 H1·H2 사전 기준 적용. 정상·위반·보류를 모두 공개하며, 근거가 없는 대상들을 사후 제거해 성능을 높이지 않음 |
>
> **1단계 설정 구성 — 아직 미실행**
> - 권한 적용 방식 4개: 정상 매 요청 재검사, 기존 세션에 권한 고정, 전역 인가 캐시 미갱신, 일부 인스턴스만 미갱신.
> - 시험 계약상 반영 지연 3개: 0ms, 500ms, 2,000ms.
> - 데이터 응답 경로 2개: 단일 인스턴스, 두 인스턴스.
> - 응답 계약 2개: HTTP 403 거부, 문서화한 HTTP 200 거부 봉투.
> - 합계 **4 × 3 × 2 × 2 = 48개 설정**. 일부 인스턴스 미갱신의 단일 인스턴스 조건처럼 의미가 겹치는 설정은 동등 계열로 표시한다. 독립 결함 종류가 48개라는 뜻은 아니다.
> - 기한 없는 계약, 적용 근거 누락, 401, 장애, 재부여는 별도 강건성 집합으로 구성한다. 설정·실패 주입·기대 결과를 최종 실험 전에 확정한다.
> - 관찰 일정 예: t0 이후 0, 100, 500, 1,000, 2,000, 5,000ms의 참고 관찰과, D+ε·D+500ms·D+3,000ms의 판정 관찰. 중복 시점은 합치고 실제 시작 시각을 기록한다. 일정 자체가 보편적인 최적값이라는 주장은 하지 않는다.
>
> **최소 실행 범위와 확장 조건**
>
> 처음에는 기능 1개, 기존 세션·새 세션·대조 계정, 정상 모드와 잔존 세션 모드, Δ=0인 명시적 시험 계약으로 시작한다. 그다음 정상 지연과 전역 캐시를 추가한다. 두 인스턴스와 실제 공개 앱은 독립적인 범용성 확인 단계다. 실제 앱에서 기한을 확보할 수 없으면 잔존 사용 가능 시간은 관찰값으로 보고하되 취약점 확정 성능의 표본으로 억지 편입하지 않는다.
>
> ### 가설을 나누어 검증하기
>
> | 가설 | 사전에 정할 지지 기준 | 반증·미지지 조건 |
> | --- | --- | --- |
> | H1. 증거를 결합하면 오탐을 줄이면서 탐지 범위를 유지한다 | 완전한 시험 계약을 확보한 평가 집합에서 P의 FPR−B1의 FPR의 95% CI 상한이 0보다 작고, P의 recall−B1의 recall의 CI 하한이 −5%p보다 크며, P의 판정 비율이 80% 이상 | 오탐 감소가 없거나, 보류로 회피해 재현율·판정 범위가 기준을 충족하지 못함. 표본 부족으로 CI가 넓으면 결론 유보 |
> | H2. 상태 전이가 정적 검사보다 회수 결함을 추가 검출한다 | 같은 총 요청·시간 예산에서 B0가 검출하지 못한, 독립 정답으로 확인된 위반을 1개 이상 추가 검출하고 공개 앱에서도 재현 | 통제된 자체 서버에서만 차이가 나거나, B0 대비 요청·관찰 비용 증가만으로 설명됨 |
> | RQ3. 계약과 대조 요청이 실용적인가 | 계약 확보율, 준비 시간, 요청 수, 보류 원인을 기술 통계로 보고. 정량적 우월성을 미리 가정하지 않음 | 기한·유효 권한 확인을 제공하는 앱이 너무 적어 적용 범위가 작음 |
> | 신규성 검토 | B2와의 성능·준비 비용 차이 또는 기존에 충분히 분석되지 않은 실패·보류 경계를 실증 | 완전한 B2와 동일하고 별도 실증 가치도 없으면 새 탐지 알고리즘 기여는 지지되지 않음 |
>
> 5%p·80%는 **제안하는 사전 평가 기준**이며 문헌에서 도출한 상수가 아니다. 본 실험 전에 팀이 적용 목적에 맞게 확정하고, 결과를 본 뒤 유리하게 수정하지 않는다. 이번 인공 반례에는 통계적 유의성 검정을 적용하지 않는다.
>
> **공정한 비교와 불확실성**
>
> B1·B2·P에는 동일하게 수집한 시퀀스와 같은 계약 정보를 제공한다. P만 추가 요청을 써서 좋아지는 효과와 판정 규칙의 효과를 분리한다. B0와의 종단 비교는 설정·로그인·변경 확인·표식 작성까지 포함한 총 비용을 공개한다. 이때 지원하지 않는 상태 전이를 B0의 정상 판정으로 바꾸지 않고 “검사 범위 밖”으로 기록한다.
>
> 반복 요청은 독립 표본이 아니다. 주 분석 단위는 애플리케이션/결함 계열/설정이며, 설정의 쌍별 차이와 계층적 또는 군집 bootstrap 신뢰구간을 보고한다. 서비스가 두 개뿐이라면 서비스 모집단에 대한 통계적 일반화는 하지 않는다. 최초 분석 시드·재표집 횟수·최종 설정 명세를 함께 공개한다.
>
> ### 평가 지표
>
> N은 적격 후보 전체 수, V·S·U는 각각 독립 정답상 위반·정상·정답 미확정 건수다. D는 진단 보류 건수이며 U와 같지 않다. TP·FP·FN·TN은 정답이 확인된 위반·정상 대상에서 정의하되 **보류를 TN으로 넣지 않는다.**
>
> | 지표 | 측정 목적 | 계산식·분모 | 보류 사례 처리 |
> | --- | --- | --- | --- |
> | 위반 확정 정밀도 | 경보의 신뢰성 | TP / (TP+FP) | 분모에 자동 포함하지 않음. 확정 수 0이면 N/A |
> | 위반 재현율 | 실제 위반을 놓치는 정도 | TP / V | 실제 위반인데 보류하면 분모에 남아 미검출로 반영 |
> | 정상 대상 오탐률 | 정상 지연·거부를 취약점으로 오판하는 정도 | FP / S | 정상 보류도 S에 남김. 낮은 오탐을 보류로만 얻었는지 함께 확인 |
> | 판정 비율·보류율 | 적용 가능한 범위 | (위반 확정+관측 정상)/N, D/N | 전체 N 유지. 이유별 보류 수·비율 병기 |
> | 정상 오확정률 | 실제 위반을 정상이라고 선언하는 위험 | V 중 관측 정상으로 출력한 수 / V | 보류와 정상 오확정을 구분 |
> | 관찰된 잔존 허용 시간 | 권한이 남은 관측 시간 | 마지막 위반 응답의 요청 시작 시각−t0 | 끝까지 허용이면 우측 검열 표시. 첫 거부 뒤 재허용도 별도 기록 |
> | 시간 관찰 해상도 | 놓칠 수 있는 구간 설명 | 실제 연속 관찰 간격 및 최대 공백 | 정확한 회수 완료 시각으로 환산하지 않음 |
> | 계약 확보율 | 적용 전제 확보 가능성 | 필수 근거를 모두 확보한 앱·기능 수 / 검토 후보 수 | 미확보 대상과 사유를 분모에서 제거하지 않음 |
> | 요청·준비 비용 | 실제 적용 부담 | 전체 HTTP 요청 수/시험, 담당자 준비 분/기능, 실행 시간/시험 | 보류·실패한 시험의 비용도 포함 |
>
> 정답이 미확정인 U에는 이진 정확도를 계산하지 않는다. U/N과 U에서 방법이 확정을 내린 건수를 별도로 표시해 과도한 단정을 드러낸다. 위반 시간이란 관찰된 호출의 시간이며, 일정 사이에 있었던 모든 접근이나 전체 피해 건수를 추정한 수치가 아니다.

> ### 작은 명제로 정리할 수 있는 관측의 한계
>
> **설계 명제:** 역할 변경 후 동일한 성공 응답을 보더라도, 유효 금지 정책이나 반영 기한이 알려져 있지 않으면 그 응답만으로 시간 계약 위반을 유일하게 결정할 수 없다.
> - 세계 A에서는 Δ=2초이고 1초 후 반환은 허용된 지연이다.
> - 세계 B에서는 Δ=0이고 같은 1초 후 반환은 금지다.
> - 관찰자가 받는 요청·응답·시각이 같고 Δ가 숨겨져 있으면 두 세계를 구분할 수 없다.
>
> 이는 제한한 관찰 모델의 간단한 식별 불가능성 설명이다. 새로운 일반 불가능성 정리를 증명했다는 주장은 하지 않는다. 논문화한다면 계약·관찰 가능한 사건·대체 권한·진행 중 요청 제외 조건을 먼저 형식화해야 한다.
>
> **최종 연구 질문**
>
> > 소수의 기능별 시험 계약과 권한 변경 확인 인터페이스, 기존·새 세션의 HTTP 응답만으로 권한 회수 이후의 비인가 기능 실행을 어느 범위까지 판정할 수 있으며, 정상 반영 지연·인증 실패·관측 불완전성이 있을 때 오탐·미검출·보류·준비 비용은 어떻게 달라지는가?
>
> **예상 기여**
> - **방법:** 기능 권한 회수 시험의 전제·시간·응답 증거를 하나의 재사용 가능한 진단 계약으로 표현하고 AP-EYE에 연결한다.
> - **실증:** 정적 인가, 단순 상태 전이, 충분히 작성한 수동 회귀 검사를 같은 예산에서 비교하고 각 근거의 추가 효과를 분리한다.
> - **재현 자료:** 정상 지연, 잔존 세션, 전역 캐시, 일부 인스턴스 지연, 근거 누락을 구분하는 시험 환경과 판정 기록을 공개한다.
> - **한계 규명:** 회수 기준 사건·기한·유효 권한·응답 의미 중 무엇이 없을 때 결론이 불가능하거나 부정확해지는지 명시한다.
>
> **남은 불확실성**
> - 실제 서비스가 엄격한 회수 기한과 유효 권한 확인을 제공하는 비율은 아직 모른다.
> - 관리 API를 읽을 수 있어도 그룹 상속·외부 정책 때문에 전체 유효 금지를 확인하지 못할 수 있다.
> - 새 세션 생성이 기존 세션을 폐기하거나 캐시를 갱신해 결함을 숨길 수 있다.
> - 신규 표식이 없는 실제 노출, 매우 짧은 위반 창, 보지 못한 복제본은 놓칠 수 있다.
> - pyLoad 취약·패치 버전의 시험 가능 기능과 회수 의미를 실행으로 재확인해야 한다.
> - 관련 MR 목록·도구 구현 및 2026년 후속 연구에 같은 조합이 이미 있는지 추가 확인해야 한다.
> - 강한 수동 회귀 검사와 차이가 없으면 “새 알고리즘”보다 **재현 가능한 벤치마크와 관측 한계 연구**로 기여를 조정해야 한다.

# 가설

권한을 회수하기 전에 만든 세션으로 보호 API를 다시 호출하고, **권한 변경 근거·반영 기한·실제 반환 데이터를 함께 확인해 잔존 권한을 판정한다.** 필요한 근거가 없는 경우는 판정 보류로 분리한다.

이 방식은 같은 요청을 검사하면서 기한과 응답 코드만 사용하는 방식보다 정상 지연이나 거부 응답을 취약점으로 잘못 판단하는 비율을 낮출 수 있다. 다만 보류만 늘려서 오탐을 줄인 것은 아닌지, 실제 위반을 얼마나 찾는지도 함께 측정한다.

아직 검증한 결과는 아니다. 아래 내용은 추가 조사에 따라 수정한 연구 가설과 실험 계획이다.

# 필요한 이유

관리자 권한을 없앴어도, 이전에 로그인한 세션에 관리자 권한이 남아 있을 수 있다. 새로 로그인하면 차단되는데 기존 세션으로는 계속 데이터를 받는 경우다.

반대로 권한을 바꾼 직후의 성공 응답이 모두 취약점인 것은 아니다. 서비스가 허용하는 반영 시간이 있을 수 있고, 다른 역할이나 공유 권한으로 접근이 허용될 수도 있다. 응답 코드가 200이어도 실제 내용은 접근 거부 메시지일 수 있다.

따라서 **무슨 권한이 없어졌는지, 언제부터 막혀야 하는지, 그 이후에 무엇이 반환됐는지**를 연결해서 확인해야 한다.

# 차이점

기존 연구에도 요청 순서와 세션을 바꿔 검사하는 방법, 권한 설정 변경 전후를 비교하는 방법, 회수 완료에 필요한 근거를 정의하는 방법이 있다. 그래서 **“시간을 고려한다”거나 “근거가 없으면 보류한다”는 것만으로 새로운 연구라고 할 수는 없다.**

이번 연구에서는 기존 세션으로 수행하는 읽기 요청에 필요한 근거를 하나씩 추가한다. 시간, 응답 내용, 변경 확인, 대조 요청이 각각 오탐과 미검출을 얼마나 바꾸는지 같은 요청 기록으로 비교한다.

충분한 근거를 사용하는 수동 검사와 결과가 같다면, 탐지 성능이 더 좋다고 주장하지 않는다. 대신 검사 조건을 다시 작성하거나 다른 API에 적용하는 비용이 줄어드는지 별도로 확인한다.

---

“권한을 회수했는데 기존 세션으로 계속 데이터를 받을 수 있는가?”를 정상적인 반영 지연과 구분해서 검사하는 주제다.

## 주제 정의

> 시험 계정의 역할이나 기능 권한을 회수한 뒤, 기존 로그인 세션으로 보호된 읽기 API를 다시 호출한다. 회수 후 금지 정책과 반영 기한을 확인하고, 실제 보호 데이터가 반환됐을 때 위반으로 확정한다. 근거가 부족하면 보류하며, 확정 범위·오탐률·보류율·재현율과 검사 준비 비용을 측정한다.

사용자와 호출 기능은 고정한다. 다른 사람의 객체 ID를 넣어 보는 BOLA 검사와 달리, **같은 사용자의 권한이 바뀌기 전과 후**를 비교한다.

쓰기·삭제, 회수 전에 시작한 요청, 장기 작업의 최종 실행은 이번 범위에서 제외한다. 모든 서버와 미래 요청에서 권한 회수가 끝났다는 증명도 목표로 삼지 않는다.

## 용어 정리

**API**

앱이 서버에 데이터를 요청하거나 동작을 실행하는 창구.

**인증**

누가 요청했는지 확인하는 것. 로그인 세션이나 토큰으로 사용자를 확인한다.

**인가**

그 사용자가 해당 기능이나 데이터를 이용해도 되는지 판단하는 것.

**권한 회수**

계정은 유지하면서 관리자 역할이나 특정 기능 권한을 없애는 것.

**기존 세션**

권한을 회수하기 전에 로그인해서 사용하던 문맥. 회수 후에도 같은 문맥으로 요청한다.

**새 세션**

회수 후 같은 계정으로 다시 로그인한 문맥. 기존 세션과 별도로 보관한다.

**잔존 권한**

계약상 접근이 막혀야 하는 시점 이후에도 이전 권한으로 보호 데이터를 받을 수 있는 상태.

**반영 기한**

권한 변경 후 언제까지 접근이 차단돼야 하는지 정한 최대 시간. 평균이나 예상 반영 시간과 다르다.

**시험 계약**

대상 사용자·기능, 회수할 권한, 차단 기준 시점, 반영 기한, 보호 데이터와 판정 조건을 적은 작은 문서.

**독립적인 근거**

검사 대상의 성공 응답과 별개로 권한 변경과 금지 정책을 확인하는 자료. 예를 들어 관리자 조회나 감사 기록이다. 이 근거가 모든 서버에 반영됐다는 뜻은 아니다.

**보호 표식**

반환된 내용이 검사 대상 데이터인지 확인하려고 넣는 고유한 합성 값. 개인정보 대신 시험용 데이터를 사용한다.

**대조 계정**

권한을 유지한 시험 계정. 같은 API가 정상 동작하는지 확인한다.

**확정**

기한이 지났고 접근이 금지된 사용자에게 보호 데이터가 새 요청의 응답으로 반환됐다는 근거가 있을 때 위반으로 판단하는 것.

**판정 보류**

정책·시간·사용자·응답 의미 등의 근거가 부족해 결론을 내리지 않는 것.

**확정 범위·보류율**

검사한 실행 중 결론을 낸 비율과 근거 부족으로 남긴 비율. 전체 후보에서 계약을 확보할 수 있는 비율도 따로 측정한다.

**오탐률·재현율**

위반이 아닌 실행을 위반으로 잘못 확정한 비율과, 실제 위반 실행 중 위반으로 확정한 비율. 실제 위반을 보류한 경우도 재현율 계산에서는 미검출로 센다.

## 근거 정리

### 1. 권한을 줄여도 기존 세션에 권한이 남는 결함이 공지됐다

pyLoad의 유지관리자 공지는 로그인할 때 저장한 역할·권한이 이후 DB의 권한 감소를 반영하지 않는 문제를 설명한다. 권한 DB는 바뀌었는데 기존 세션은 예전 값을 사용하는 경우다. [pyLoad 취약점 공지](https://github.com/pyload/pyload/security/advisories/GHSA-66hx-chf7-3332)

그래서 회수 후 새 로그인만 검사해서는 충분하지 않다. **권한이 있었을 때 만든 세션을 그대로 유지한 요청**도 확인해야 한다.

다만 공지의 PoC는 소스 검사다. 이번 조사에서 실제 제품을 실행하거나 HTTP로 재현한 것은 아니며, 실제 악용 사고를 확인했다는 뜻도 아니다.

패치는 사용자 변경을 처리하는 WebUI 경로에서 세션 무효화를 추가했다. 코어 API의 권한 변경 경로와는 차이가 있으므로, 패치 전후 비교에서도 같은 경로로 권한을 변경해야 한다. 이 소스 차이만으로 다른 경로의 새 취약점을 확정할 수는 없다. [패치](https://github.com/pyload/pyload/commit/e95804fb0d06cbb07d2ba380fc494d9ff89b68c1)

### 2. 시간과 세션을 다루는 검사는 이미 있다

MST-wi는 요청 순서와 사용자 자격을 바꾸고 출력을 비교한다. 공개 검사 규칙에도 로그아웃 전후 세션과 세션 만료 후 출력을 확인하는 예가 있다. 논문의 대기 동작은 시스템 시각을 바꿔 시간 경과를 모사한다. [MST-wi, §IV](https://arxiv.org/html/2208.09505v2), [공개 세션 만료 규칙](https://github.com/MetamorphicSecurityTesting/CWE/blob/035b3fee8277a0af64bd7706a0f5404c401162e7/CWE_MRs/OTG_SESS_007.smrl#L26)

이번에 확인한 기본 규칙에서는 같은 계정의 역할 회수, 독립 변경 근거, 실제 반영 기한, 보호 데이터 반환을 모두 연결한 절차를 찾지 못했다. 그러나 규칙을 확장할 수 있으므로 **기존 도구가 이런 검사를 할 수 없다고 말하면 안 된다.**

따라서 비교군에는 같은 회수 시퀀스를 제공한 확장 규칙도 넣는다. 기본 규칙에 필요한 정보를 주지 않은 상태에서 제안 방법이 더 좋다고 결론내리지 않는다.

### 3. 권한 설정 변경 전후 비교도 선행연구에 있다

ACtests는 접근제어 설정을 바꾸기 전과 후에 어떤 요청의 결과가 달라졌는지 찾는다. 그 변화가 관리자의 의도에 맞는지는 사람이 검토한다. 같은 사용자/IP의 요청 의존성도 보존한다. [ACtests, Abstract·§4.3](https://arxiv.org/html/2505.12770v1)

이번 연구도 변경 전후 비교라는 점에서는 겹친다. 다만 기존 세션을 유지한 외부 HTTP 요청에 대해 **언제부터 어떤 반환이 금지되는지**를 작은 시험 계약으로 지정한다.

설정 변경 비교 자체의 신규성보다, 이 계약을 준비할 수 있는 범위와 필요한 근거·검토 비용을 확인하는 것이 중요하다.

### 4. 변경 성공 응답과 실제 회수 완료는 다르다

EffectBound는 새 권한 발급의 종료, 기존 권한의 효과 종료, 전체 권한 계보의 종료를 구분한다. 회수 완료를 말하려면 계약과 관측 경계를 정해야 한다는 점도 다룬다. [EffectBound, §II–III](https://arxiv.org/html/2609.02866v1)

이번 연구에서는 관리자의 변경 성공 응답만으로 완료를 판단하지 않는다. DB 변경이나 현재 유효 권한을 확인하고, 계약이 지정한 반영 기한 이후에 보호 API를 호출한다.

예를 들어 계약이 “DB 변경이 완료된 시점부터 최대 Δ초 안에 차단한다”라면, 그 기준 사건과 기한을 확인해야 한다. 단순히 관리 화면에서 버튼을 누른 시점부터 계산하지 않는다.

또한 새 HTTP 요청이 새로 발급된 권한을 사용한다는 뜻은 아니다. 기존 JWT나 세션을 다시 사용하는 요청일 수 있다. 한 번 거부됐다는 결과도 모든 서버와 미래 요청의 회수 완료를 증명하지 않는다.

### 5. 오래된 데이터가 새 요청에 다시 반환돼도 검사해야 한다

HTTP 캐시는 과거 응답을 사용해 현재 요청에 답할 수 있다. 따라서 회수 후 새로 만든 데이터만 찾으면, 과거 보호 데이터가 계속 재전송되는 문제를 놓칠 수 있다. [RFC 9111, §4](https://www.rfc-editor.org/rfc/rfc9111.html)

구분할 것은 데이터의 나이와 반환 시점이다.

| 상황 | 이번 검사에서의 처리 |
| --- | --- |
| 회수 후 만든 보호 데이터가 새 응답에 반환됨 | 기한·금지 근거가 있으면 위반 확정 가능 |
| 회수 전에 만든 보호 데이터가 새 응답에 다시 반환됨 | 그 데이터도 현재 금지 대상이면 위반 확정 가능 |
| 브라우저가 예전에 받은 화면을 다시 보여줌 | 새 API 반환의 증거로 사용하지 않음 |

표식이 본문에 있다는 것만으로는 부족하다. 보호 위치와 의미를 확인하고, 요청 문자열이 오류 메시지에 그대로 반사된 경우를 실제 조회로 오판하지 않아야 한다.

새 로그인이나 표식 작성 자체가 상태를 바꿀 수도 있다. 예를 들어 새 로그인으로 권한 캐시가 갱신되거나, 데이터 쓰기로 응답 캐시가 무효화되면 검사 과정에서 결함이 사라질 수 있다. 쓰기에 따른 캐시 무효화 가능성은 표준에도 설명돼 있다. [RFC 9111, §4.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.4)

그래서 기존 세션만 쓰는 경우와 새 로그인·표식 작성을 추가하는 경우를 각각 초기화한 환경에서 비교한다.

### 6. 역할 하나를 없앴다고 모든 접근이 금지되는 것은 아니다

ResidualAuth는 현재 권한이 같아도 권한이 부여된 경로에 따라 회수 결과가 달라질 수 있음을 다룬다. Root-Scoped Quiescence도 회수한 권한 경로와 별개의 권한을 구분한다. [ResidualAuth](https://arxiv.org/html/2609.08062v1), [Root-Scoped Quiescence](https://arxiv.org/html/2609.21284v1)

예를 들어 관리자 역할은 없어졌지만, 그룹이나 직접 부여로 같은 기능을 사용할 수 있을 수 있다. 이런 상태에서 성공 응답을 위반으로 보면 오탐이다.

따라서 제거한 역할뿐 아니라 **해당 기능을 허용하는 다른 경로가 남아 있는지** 확인한다. 이 논문들은 에이전트와 위임을 다루므로, 일반 API 진단기의 정확도를 입증한 결과로 가져오지는 않는다.

### 7. 실제 서비스에서 최대 반영 기한을 확보할 수 있는지는 아직 문제다

Google IAM 문서는 권한 변경이 즉시 반영되지 않을 수 있다고 설명한다. 정책 변경은 보통 2분이지만 7분 이상 걸릴 수 있으며, 그룹 변경은 더 오래 걸릴 수 있다. 이 값은 예상 시간이지 **7분 안에 반드시 차단된다는 최대 기한이 아니다.** [Google IAM 공식 문서](https://docs.cloud.google.com/iam/docs/access-change-propagation?hl=en)

Keycloak도 기존 access token의 유지 여부가 토큰·세션·검증 방식에 따라 달라진다. 공식 문서는 전체 세션 sign-out이 미만료 access token을 모두 폐기하지는 않는다고 설명한다. 이를 역할 회수와 같은 계약이라고 보거나, 기존 토큰이 허용된다는 이유만으로 취약점이라고 할 수는 없다. [Keycloak 관리 문서](https://www.keycloak.org/docs/latest/server_admin/)

현재 pyLoad와 Keycloak을 확인한 구간에서는 역할 회수의 수치 최대 기한을 확보하지 못했다. 그래서 **제품이 보장하는 계약과 연구자가 시험용으로 정한 계약을 분리**해야 한다.

기한이 없는 제품은 잔존 접근을 관측할 수는 있어도, 몇 초가 지났다는 이유만으로 시간 계약 위반을 확정할 수 없다. 이런 대상도 전체 후보 수에 남겨 적용 가능성이 얼마나 되는지 보고한다.

## 어떻게 검증할 것인가

### 1. 같은 요청 기록에서 필요한 근거를 하나씩 추가한다

| 검사 방식 | 사용하는 근거 | 확인할 내용 |
| --- | --- | --- |
| 상태코드 검사 | 권한 변경 후 응답 코드 | 단순 성공 판정의 오류 |
| 기한을 추가한 검사 | 응답 코드 + 반영 기한 | 정상 지연을 구분하는 효과 |
| 본문을 추가한 검사 | 위 조건 + 보호 데이터·거부 메시지 | 200 거부나 오류 본문의 구분 |
| 변경 근거를 추가한 검사 | 위 조건 + 변경 완료·현재 유효 금지 | 변경 실패·다른 허용 경로의 구분 |
| 제안 방법 | 위 조건 + 인증 관측·대조 요청·관측 누락 확인 | 판정 범위와 신뢰성 |
| 충분한 수동 검사 | 같은 전체 근거를 사용하는 직접 작성 규칙 | 단순한 방법으로 같은 결과를 낼 수 있는지 |

시간 정보의 효과를 보려면 기한 전 참고 요청도 수집한다. 다만 제안 방법의 위반 확정은 기한 이후 요청에 한정한다. 각 근거를 하나씩 뺀 결과도 비교한다.

제안 방법만 추가 요청을 보내서 얻은 정보를 기존 방식과 비교하면 정보량의 차이가 섞인다. 따라서 **같은 기록의 판정 비교**와 **실제 준비·호출·검토 비용 비교**는 따로 한다.

### 2. 검사 과정이 결과를 바꾸는지 확인한다

| 실행군 | 데이터 준비 | 회수 후 새 로그인 |
| --- | --- | --- |
| 1 | 회수 전 보호 표식만 준비 | 없음 |
| 2 | 회수 전 보호 표식만 준비 | 있음 |
| 3 | 회수 후 새 보호 표식도 작성 | 없음 |
| 4 | 회수 후 새 보호 표식도 작성 | 있음 |

각 군은 독립적으로 초기화한다. 기존 세션의 호출 일정과 결함 조건은 맞춘다. 기본 검사에서 캐시를 강제로 우회하지 않고, 캐시 우회 요청은 별도 실험으로 둔다.

### 3. 위반·정상·보류 사례를 함께 넣는다

예를 들어 정상 반영 지연, 기한 초과 반환, 200 거부 메시지, 403에 포함된 보호 데이터, 과거 데이터의 새 재전송, 다른 권한의 정상 허용을 넣는다. 변경 실패, 반영 기한 없음, 새 로그인·표식 쓰기로 결함이 사라지는 경우도 필요하다.

전체 24개 경계 사례는 [상세 연구계획의 5.5절](https://app.notion.com/p/RESEARCH-HYPOTHESIS-REVISED.md#55-%EC%9A%B0%EC%84%A0-%EA%B3%A0%EC%A0%95%ED%95%A0-24%EA%B0%9C-%EA%B2%BD%EA%B3%84-%EC%82%AC%EB%A1%80)에 정리했다. 아직 새 사례를 구현하거나 실행하지 않았다.

정답은 진단기와 같은 규칙으로 만들지 않는다. 별도의 서버 기록과 권한 변경 자료, 독립 검토를 사용한다. 통계의 기본 단위는 개별 HTTP 응답이 아니라 **독립 초기화한 시험 실행 하나**로 둔다. 계약이 유효한 관측 구간에서 금지 반환이 하나라도 있으면 위반 실행으로 본다.

권한이 다른 경로로 남은 경우나 변경 실패는 별도 사례 집합에서 과잉 확정 여부를 평가한다. 엄격한 계약을 확보한 실행의 탐지 성능과 섞지 않는다.

### 4. 오탐 감소와 실제 위반 검출을 같이 본다
- 오탐률이 줄었는지 확인한다.
- 실제 위반을 얼마나 찾았는지 확인한다. 위반을 보류한 경우도 미검출로 센다.
- 계약이 있는 실행의 판정률과 전체 후보 실행의 보류율을 따로 보고한다.
- 서비스별로 필요한 계약과 근거를 확보할 수 있는 비율도 측정한다.

같은 서버에 같은 요청을 많이 반복했다고 독립 표본이 많아지는 것은 아니다. 작은 시험에서는 먼저 어떤 사례의 판정이 바뀌었는지 보고한다. 허용할 미검출과 보류 수준은 실험 결과를 보기 전에 정한다.

### 5. 수동 검사와 결과가 같다면 비용을 비교한다

같은 자료와 요구 품질을 주고, 제안 방식의 계약 작성과 직접 검사 코드 작성에 드는 시간을 비교한다. 처음 만드는 비용뿐 아니라 새 기능·다른 서비스·정책 변경에 맞추는 비용도 포함한다.

문서 읽기, 관리자 확인, 로그인, 표식 작성, 초기화, 결과 검토를 모두 센다. 같은 사람에게 같은 과제를 두 번 주면 기억한 답을 사용할 수 있으므로, 비슷한 난도의 다른 과제를 배정한다.

품질 기준을 못 맞춘 채 빨리 끝난 결과를 비용 이익으로 계산하지 않는다. 같은 품질에서 재사용 비용이 줄었을 때만 별도 비용 가설의 근거로 삼는다.

## 현재까지 확인한 것

| 항목 | 현재 상태 |
| --- | --- |
| 선행논문·공식 문서·선정 소스 확인 | 조사 완료. 확인 구간과 버전은 상세 연구계획에 기록 |
| 현재 데모의 회수 전후 자동 시나리오 | 조사한 16개 시나리오에는 없음 |
| 기존 인공 반례 16개 | 자기작성 예상값과 일치한 기록이 있음. 독립 정확도 평가가 아님 |
| 수정한 진단 방법·24개 경계 사례 | 실험 계획. 아직 구현·실행하지 않음 |
| pyLoad·Keycloak HTTP 재현 | 미실행 |
| 오탐 감소·재현율·준비 비용 개선 | 아직 검증하지 않음 |

기존 인공 반례 결과를 새 판정 규칙의 성능으로 제시하지 않는다. 현재 데모의 진단기와 mock API는 같은 정책 함수를 쓰므로, 새 평가에서는 정답을 분리해야 한다. [기존 소스 조사](https://app.notion.com/p/SOURCE-AUDIT.md), [기존 예비 결과](https://app.notion.com/p/preliminary-results.json)

## 정리

### 선행연구와 겹치는 부분 및 남은 질문
- 시간·세션·요청 순서를 바꾸는 검사는 이미 있다.
- 권한 설정 변경 전후 비교와 회수 완료의 계약·근거도 선행연구에 있다.
- 기존 세션, 보호 데이터 재전송, 다른 허용 경로를 구분하려면 추가 근거가 필요하다.
- 그 근거를 실제 API에서 어느 정도 확보할 수 있고, 준비 비용이 얼마나 드는지는 함께 확인해야 한다.

**→ 같은 회수 전후 요청에 근거를 하나씩 추가하면 어디까지 위반을 확정할 수 있고, 오탐·미검출·보류·준비 비용이 어떻게 달라지는가?**

오탐이 줄어도 보류가 크게 늘거나 실제 위반을 놓치면 가설을 지지한 것으로 보지 않는다. 충분한 수동 검사와 결과도 같고 비용도 줄지 않으면, 제안 방법의 이익을 다시 검토해야 한다.
