# 정책·스키마 변경을 추적하는 API 응답 필드 인가 진단

> **1차** (노션 토글)
> # 정책·스키마 변경을 추적하는 API 응답 필드 인가 진단
>
> 작성 기준일: **2026-10-01**
>
> 연구 상태: **연구계획서 초안 — 예비 실험 및 성능 측정 미수행**
>
> 이 문서는 통합 보고서의 **H3: 정책 변경 이후 응답 필드가 따라 바뀌는지 진단**을 구체화한다. H1이 객체에 접근할 권한을 판단하는 문제라면, H3은 **객체 조회가 허용된 상황에서도 응답의 개별 정보까지 제공해도 되는지**를 다룬다. 계획 규모·제안 방법·예상 기여는 실험 결과가 아니다.
>
> > **가설**
> >
> > 역할별 정보 제공 정책과 API 구조가 변경되는 환경에서, **확인된 정책 변경 이력과 실제 배포 버전에 맞는 필드 의미 매핑을 응답 관측에 결합하는 방법**을 사용하면, 정적인 개인정보 패턴 검사나 화면 미사용 필드 검사보다 정책 변경 후 남은 금지 정보의 탐지 재현율을 높이면서 합법적인 응답의 오탐을 줄일 수 있다.
> >
> > 학문적 차별성은 추가 정책 정보를 제공한 효과와 구분한다. 같은 정책·스키마·검토 예산을 받은 최신 허용 목록 및 일반 스키마 매칭 방법과 비교해, **탐지 성능을 높이거나 같은 성능을 유지하는 데 필요한 규칙·매핑 갱신 비용을 줄일 수 있는지** 검증한다.
> >
> > **필요한 이유**
> >
> > 실제 전화번호 제공을 중단하고 안심번호만 제공하도록 정책을 바꿔도, 기존 API 응답에는 실제 전화번호가 남을 수 있다. 필드명이 바뀌거나 위치가 이동하면 예전 경로에 묶인 진단 규칙도 문제를 놓칠 수 있다.
> >
> > 반대로 전화번호처럼 생겼다는 이유만으로 경고하면 정책상 허용된 안심번호까지 오탐할 수 있다. 화면에서 사용하지 않는 필드라는 사실도 해당 정보를 보내면 안 된다는 정책 판단과 같지 않다.
> >
> > 이를 해결하려면 **누구에게, 어떤 업무 맥락에서, 어떤 정책 버전에 따라, 어떤 의미의 값을 보냈는지**를 연결하고, 오래되거나 확인되지 않은 매핑은 정상 판정의 근거로 사용하지 않는 접근이 필요하다.
> >
> > **직접적인 선행 연구**
> > - Divya Muthukumaran, Dan O’Keeffe, Christian Priebe, David Eyers, Brian Shand, Peter Pietzuch, *FlowWatcher: Defending against Data Disclosure Vulnerabilities in Web Applications*, ACM CCS 2015. [R1 원문](https://lsds.doc.ic.ac.uk/sites/default/files/ccsfp224-muthukumaran_0.pdf)
> > - Lianglu Pan, Shaanan Cohney, Toby Murray, Van-Thuan Pham, *EDEFuzz: A Web API Fuzzer for Excessive Data Exposures*, ICSE 2024. [R2 원문](https://arxiv.org/pdf/2301.09258v2)
> >
> > 필드 대응 관계를 찾는 방법의 비교 근거로 Hong-Hai Do, Erhard Rahm의 *COMA: A System for Flexible Combination of Schema Matching Approaches*, VLDB 2002를 함께 사용한다. [R3 원문](https://www.vldb.org/conf/2002/S17P03.pdf)
> >
> > **차이점**
> >
> > FlowWatcher는 개발자가 정의한 정책과 HTTP 데이터 추적을 이용하고, EDEFuzz는 응답 필드를 제거했을 때 화면 동작이 달라지는지를 이용한다. COMA는 여러 매칭 기법과 사용자 피드백으로 스키마 요소의 의미상 대응을 찾는다.
> >
> > 본 연구는 **정책 변경·배포 스키마·검토된 필드 의미·실제 반환 값을 동일한 요청에 연결하는 진단 절차**를 제안하고, 변경 유형별 탐지율, 정상 예외 오탐, 보류율, 잘못된 정상 판정, 매핑 갱신 비용을 함께 측정한다.
> >
> > 정책 검사, 필드 매칭, 사용자 확인, 판정 보류 자체를 새 개념으로 주장하지 않는다. 단순한 최신 허용 목록이 같은 비용으로 같은 결과를 내면 새로운 탐지 알고리즘의 우월성 주장을 기각한다.
>
> ## 1. 주제 정의
>
> **한 문장 설명**
>
> “정보 제공 정책이나 API 구조가 바뀐 뒤에도, 더 이상 보내면 안 되는 정보가 응답에 남아 있는가?”를 정책 버전·필드 의미·실제 응답의 대응 관계로 검증하는 연구.
>
> **연구 범위**
>
> > 통제된 다중 사용자 REST/JSON API 환경에서 검토된 정책 변경 이력, 역할과 업무 맥락, 배포별 스키마, 필드 의미를 확인할 자료, 실제 응답을 이용하여 **정책 변경 후의 금지 정보 반환을 진단하는 방법**을 개발한다.
> >
> > 정책이 해당 요청에 적용된다는 근거, 반환 값의 의미를 확인할 근거, 실제 전송된 응답이 있으면 위반을 판정한다. 적용 정책이나 값의 의미가 불명확하거나 응답 관측이 불완전하면 보류한다.
> >
> > 이후 정책·스키마 변경을 통제한 합성 서비스와 입력 조건을 충족하는 공개 테스트 애플리케이션에서 최신 허용 목록, 일반 스키마 매칭, 개인정보 패턴 검사, 적용 가능한 EDEFuzz와 비교한다.
>
> | 구분 | 내용 |
> | --- | --- |
> | 연구 대상 | 객체 조회 자체는 허용됐지만 응답 필드별 제공 범위가 달라지는 REST/JSON API |
> | 포함 범위 | 정책만 변경, 필드명 변경, 중첩·배열 경로 이동, 같은 필드명의 의미 변경, 역할별 예외, 여러 배포 버전의 병존, 정책·매핑 근거의 누락·충돌 |
> | 제외 범위 | 객체 접근권한 자체의 발견, 쓰기·삭제, 비동기 작업의 효과, 권한 회수의 전파 지연, 자연어 정책의 무검토 자동 해석, 암호화·임의 인코딩 해독, 여러 필드를 조합한 재식별의 일반적 증명 |
> | 필요한 입력 | 테스트 계정과 역할, 확인된 정책 버전·적용 범위, 배포·스키마 정보, 검토 가능한 데이터 사전·필드 매핑, 합성 데이터 또는 승인된 표본, 실제 응답과 관측 지점 |
> | 최종 산출물 | 정책·스키마·매핑 연결 절차, 진단 시제품, 변경 유형별 정상·취약 사례, 근거 기록 형식, 비교·제거 실험 결과 |
>
> **이해를 위한 예시**
>
> 다음은 설명용 가상 주문 서비스다. 실제 사건의 필드명이나 구현을 재현한 것이 아니다.
> - 이전 정책 P1: 배송기사에게 고객의 실제 전화번호를 제공할 수 있음.
> - 변경 정책 P2: 해당 배송 업무에는 안심번호만 제공할 수 있음.
> - 사전 조건: P2가 해당 역할·업무·배포에 적용된다는 사실이 확인됨.
>
> | 변경 후 응답 | 필요한 확인 | 판정 |
> | --- | --- | --- |
> | `safe_phone`에 안심번호만 있음 | 값의 의미와 허용 조건이 확인됨 | 해당 관측 범위에서 정상 |
> | `safe_phone`과 `real_phone`이 함께 있음 | `real_phone` 값이 실제 전화번호임이 확인됨 | 위반 |
> | 이름을 바꾼 `contact_value`에 실제 전화번호가 있음 | 새 경로와 값의 의미가 확인됨 | 위반 |
> | `phone`이라는 기존 필드에 안심번호가 들어감 | 필드명만 보지 않고 실제 의미와 정책을 확인 | 허용 조건을 충족하면 정상 |
> | `contact_value`의 의미를 알 수 없음 | 데이터 사전·표본·출처 근거 부족 | 보류 |
>
> **이 연구에서 중요한 것은 필드의 이름만이 아니라 그 필드가 실제로 담은 정보다.** 같은 숫자 형식만으로 실제 전화번호와 안심번호를 구분할 수 없다면, 별도 근거 없이 추정해 확정하지 않는다.
>
> ## 2. 용어 정리
>
> | 용어 | 쉬운 설명 | 본 연구에서의 의미·기준 |
> | --- | --- | --- |
> | 객체 수준 인가 | 주문 하나를 조회해도 되는지 확인 | 본 연구의 사전 조건. 확인되지 않으면 H3 판정을 보류하거나 별도 진단으로 분리 |
> | 필드 수준 인가 | 주문 안의 전화번호·주소까지 보여줘도 되는지 확인 | 역할·업무 맥락·적용 정책에 따른 개별 정보의 제공 허용 여부 |
> | 정책 버전 | 허용 규칙이 언제 어떻게 달라졌는지 표시 | 규칙 ID, 적용 대상, 적용 시점·조건, 허용 예외를 포함한 검토된 정책 |
> | 스키마 | JSON의 구조와 필드 형식을 적은 설명 | 필드명·경로·자료형·중첩 구조. 일반적인 구조 정보만으로 업무상 허용 여부를 확정하지 않음 |
> | 의미 매핑 | 필드가 어떤 정보를 뜻하는지 연결 | 배포·스키마 버전별 JSON 경로와 실제 정보 개념·표현 방식의 대응 |
> | 매핑 후보 | 같은 의미일 가능성이 있는 연결 | 이름·구조·자료형·설명으로 제안한 연결. 확인된 사실과 구분 |
> | 금지 정보 | 해당 요청자에게 보내면 안 되는 내용 | 검토된 정책이 금지한 정보와 표현 방식. 개인정보라는 이유만으로 자동 금지하지 않음 |
> | 화면 미사용 필드 | 관찰한 화면 동작에 쓰이지 않는 값 | 과다노출 후보 조건. 정책상 금지와는 별도 라벨 |
> | 위반 확정 | 금지된 정보가 실제 응답에 포함됨을 확인 | 적용 정책, 실제 값의 의미, 요청 맥락, 전송 관측을 모두 확보 |
> | 정상 확인 | 검사한 응답이 확인된 필드 정책과 일치 | 검사 범위의 응답·매핑이 충분하고 금지 정보가 없음을 확인. 서비스 전체 안전을 뜻하지 않음 |
> | 판정 보류 | 판단에 필요한 근거를 확보하지 못함 | 정책·버전·맥락·매핑·실제 값의 의미·응답 수집 중 필요한 근거가 누락되거나 충돌 |
> | 규칙 유지 비용 | 서비스 변경에 맞춰 검사를 고치는 수고 | 정책 정리, 필드 매핑 검토, 규칙 수정, 결과 검토에 든 시간과 수정 항목 수 |
>
> **업무 목적은 요청자가 임의로 적은 문자열만으로 인정하지 않는다.** 테스트 시나리오나 검토된 업무 흐름을 통해 맥락을 확인한다. 실제 목적을 검증할 수 없는 운영 환경에서는 그 적용 한계를 명시한다.
>
> ## 3. 근거 정리
>
> ### 3.1. 정책 기반 진단도 URL·필드 변경을 따라가지 못하면 탐지를 놓칠 수 있다
>
> **선행 연구에서 확인한 내용**
>
> > “UDA policies must be updated if an application changes URLs or fields referred to in a policy.”
>
> → 애플리케이션이 정책에서 참조하는 URL이나 필드를 바꾸면 정책 규칙도 갱신해야 한다는 뜻이다.
> - **출처:** Muthukumaran 외, *FlowWatcher*, CCS 2015, §3.5 Discussion, 확인한 PDF 6쪽. [R1](https://lsds.doc.ic.ac.uk/sites/default/files/ccsfp224-muthukumaran_0.pdf)
> - **직접 확인되는 사실:** 논문은 경로·필드 이름이 바뀌면 규칙이 발동하거나 일치하지 않아 갱신 전까지 미탐이 생길 수 있다고 설명한다. 한편 사용자·그룹·권한 상태의 동적 갱신은 이미 지원한다.
> - **본 연구와의 연결:** 오래된 매핑이 더 이상 현재 응답을 다루지 못한다는 사실을 감지하고, 새 대응 관계를 검토하는 절차를 평가할 필요가 있다.
> - **해석의 한계:** FlowWatcher가 모든 정책 변화에 대응하지 못한다는 뜻은 아니다. 기존 값 추적이 이름 변경의 영향을 받지 않는 경우도 있을 수 있으므로 실제 비교에서 확인해야 한다.
>
> 추가로 검증할 질문은 **변경 후 누락을 발견하는 데 필요한 갱신 비용을 줄일 수 있는가**, 그리고 **매핑이 불확실할 때 이를 안전한 응답으로 잘못 처리하지 않는가**이다.
>
> ### 3.2. 화면에서 쓰이지 않는 정보와 정책상 보내면 안 되는 정보는 구분해야 한다
>
> **선행 연구에서 확인한 내용**
>
> > “The final step of our approach is manually inspecting the results.”
>
> → 자동으로 찾은 후보의 최종 의미를 사람이 검토하는 단계가 필요하다는 뜻이다.
> - **출처:** Pan 외, *EDEFuzz*, ICSE 2024, §4.5 Result Inspection, PDF 7쪽. [R2](https://arxiv.org/pdf/2301.09258v2)
> - **직접 확인되는 사실:** 응답 변이와 화면 비교로 미사용 필드 후보를 찾고, 민감성은 추가로 검토한다. §5에서는 미사용 여부와 민감정보 노출 여부를 별도 평가 대상으로 구분한다.
> - **본 연구와의 연결:** 화면 미사용 여부와 별도로 역할·정책별 금지 여부를 정답으로 만들어야 한다. 화면에 사용되는 금지 정보도 포함해야 한다.
> - **해석의 한계:** EDEFuzz가 민감성을 전혀 고려하지 않았다고 해석하면 안 된다. 본 연구와 자동 후보 생성 기준 및 정책 변경 평가 범위가 다르다는 의미다.
>
> 본 연구에서는 다음 네 집단을 구분한다.
>
> | 화면 사용 여부 | 정책상 허용 | 정책상 금지 |
> | --- | --- | --- |
> | 화면에서 사용 | 정상 기능의 데이터 | 화면에서 사용돼도 위반 |
> | 화면에서 미사용 | 불필요할 수 있지만 이 사실만으로 인가 위반 확정 불가 | 화면에 보이지 않아도 위반 |

>
> ### 3.4. 의미 매핑과 사람의 확인은 이미 연구된 방법이다
>
> **선행 연구에서 확인한 내용**
>
> > “Schema matching is the task of finding semantic correspondences between elements of two schemas.”
>
> → 서로 다른 스키마에서 같은 의미를 가진 요소를 연결하는 것이 스키마 매칭이라는 뜻이다.
> - **출처:** Do, Rahm, *COMA*, VLDB 2002, 초록 및 §1 Introduction, PDF 1–2쪽. [R3](https://www.vldb.org/conf/2002/S17P03.pdf)
> - **직접 확인되는 사실:** 이름·구조 등 여러 매칭 방법을 조합하고 과거 결과를 재사용하며, 사용자가 후보를 확인하거나 거부하는 절차를 다룬다.
> - **본 연구와의 연결:** 별칭을 찾거나 사람이 확인하는 기능만으로 신규성을 주장할 수 없다. 일반 매칭 방법에 같은 자료와 검토 시간을 제공해 비교해야 한다.
> - **해석의 한계:** 스키마 요소의 의미 대응이 확인됐다고 해서 현재 요청자에게 해당 정보를 제공해도 된다는 결론이 따라오지는 않는다. 별도의 정책 적용이 필요하다.
>
> ### 3.5. 최신 허용 목록과 응답 검증은 반드시 포함해야 할 강한 비교군이다
>
> OWASP API3:2023은 객체의 개별 속성에 대한 접근을 확인하고, 응답 필드를 필요한 범위로 제한하며, 스키마 기반 응답 검증을 추가하도록 권고한다. [T1, How To Prevent](https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization/)
> - **직접 확인되는 사실:** 응답 필드 선별과 스키마 검증은 이미 제시된 실무 대응이다.
> - **본 연구와의 연결:** 개인정보 정규식처럼 정책 정보가 없는 약한 비교군만 이겨서는 충분하지 않다. 최신 정책에 맞춰 갱신한 역할별 허용 목록과 비교한다.
> - **해석의 한계:** 실무 권고가 특정 진단 도구의 성능을 입증하는 것은 아니다. 역할별 정책을 정확히 반영한 스키마 검증이 본 연구의 문제를 충분히 해결할 가능성도 열어 둔다.
>
> ## 4. 사전 조사 또는 예비 실험

>

> 1. 정책 변경의 적용 대상·시점과 API 배포 버전을 연결할 수 있는가?
> 1. 현재 필드의 실제 의미를 데이터 사전·검토된 예시 등으로 확인할 수 있는가?
> 1. 같은 모양의 값에 서로 다른 의미가 있을 때 정답을 독립적으로 만들 수 있는가?
> 1. 최신 허용 목록이나 단순 경로 변경 처리만으로 충분히 해결되는가?
>

> - **자료 출처:** AP-EYE용 합성 주문·지원서·문서 서비스, 검토된 정책 이력, 이전·이후 스키마. 외부 공개 프로젝트는 버전별 정책 정답을 확보할 수 있는 경우에만 추가한다.

> 1. 제공한 입력과 근거 제한을 기록하고, 동일 입력의 최신 허용 목록·일반 매칭 방법을 실행할 준비를 한다.

> ## 5. 제안 방법과 검증 계획
>
> ### 제안 방법
>
> **1. 정책 변경을 검토 가능한 규칙으로 정리한다.**
>
> 정책에는 수신 역할, 검증된 업무 맥락, 정보 개념, 허용 표현 방식, 적용 배포·집단, 적용 시점과 예외를 기록한다. 예를 들어 실전화번호 원문은 금지하지만 안심번호는 허용하는 규칙을 구분한다.
>
> 자연어 문장에서 규칙을 추출하더라도 사람이 확인한 규칙만 판정에 사용한다. 정책이 명시하지 않은 부분을 임의로 금지나 허용으로 채우지 않는다.
>
> **2. 해당 요청에 적용되는 정책·배포·스키마를 선택한다.**
>
> 요청의 역할·경로·배포 정보와 정책의 적용 조건을 연결한다. 가장 최근 문서라는 이유만으로 모든 응답에 적용하지 않는다. 반대로 구버전 API라는 이유만으로 폐기된 허용 정책을 계속 적용하지 않는다.
>
> 이번 실험은 정책 적용이 확인된 안정 상태를 우선 다룬다. 반영 기한이나 전파 지연이 문제인 조건은 H2에 해당하므로 분리한다.
>
> **3. 현재 매핑이 적용 가능한지 확인한다.**
>
> 이전 경로가 사라지거나, 새 필드가 생기거나, 배포가 바뀌었는데 매핑이 갱신되지 않았다면 추가 검토가 필요한 상태로 표시한다. 구조가 같아도 데이터 사전이나 표현 방식이 바뀐 경우를 확인한다.
>
> 단순히 스키마 차이가 없다는 사실을 의미 변화가 없다는 증거로 사용하지 않는다.
>
> **4. 변경된 필드의 의미 매핑 후보를 만든다.**
>
> 이전·이후 이름, 부모 경로, 자료형, 설명, 검토된 별칭과 제한된 표본으로 후보를 만든다. 초기 구현은 개별 정보 필드의 대응과 중첩·배열 경로를 다루며, 임의의 다대다 변환은 제외한다.
>
> 일반 이름·구조 매칭 및 COMA 계열의 조합·재사용 방식과 비교한다. LLM을 쓰는 경우에도 후보 제안 역할로 제한하고, 모델·입력·비용을 고정한 추가 비교로 다룬다. LLM 사용은 필수 전제가 아니다.
>
> **5. 후보와 실제 값의 의미를 확인한다.**
>
> 필드 설명이 안심번호라고 적혀 있다는 사실만으로 실제 값도 안심번호라고 확정하지 않는다. 검토된 데이터 사전, 통제된 원본 값과의 대응, 데이터 제공 경로 등 확보 가능한 근거를 확인한다.
>
> 모양이 같은 두 값의 의미를 구분할 근거가 없으면 보류한다. 이 경우를 해결한 것으로 세지 않는 것이 연구의 적용 범위를 명확하게 한다.
>
> **6. 수신 응답의 각 검사 대상과 정책을 대조한다.**
>
> 확인된 필드·값 의미를 역할별 허용 조건에 대입한다. 금지 원문, 허용된 대체 값, 필드 부재, `null`, 마스킹 문자열을 서로 다른 상태로 다룬다. `null`이나 마스킹의 허용 여부도 정책에서 확인한다.
>
> 필드 키의 존재 자체를 금지하는 정책과 실제 값의 제공을 금지하는 정책은 구분해 기록한다. 본 평가의 중심은 금지 정보가 실제로 전달됐는지이며, 표현 규칙 위반은 별도 유형으로 보고한다.
>
> **7. 판정과 재검토 항목을 남긴다.**
>
> 응답 안에 확인된 위반이 하나라도 있으면 해당 위반을 보고한다. 다른 필드가 보류 상태라고 해서 확인된 위반을 지우지 않는다. 정상으로 결론 내리려면 검사 범위의 응답과 필요한 의미 매핑이 충분해야 한다.
>
> 최소 기록 항목은 다음과 같다.
>
> | 항목 | 기록 목적 |
> | --- | --- |
> | 요청·응답 ID, 관측 지점 | 어느 전송을 판단했는지 확인 |
> | 역할·테넌트·검증된 업무 맥락 | 수신 조건 확인 |
> | 정책 ID·버전·적용 조건 | 사용한 허용·금지 규칙 확인 |
> | 배포·스키마·매핑 버전 | 서로 다른 버전의 혼용 확인 |
> | 실제 JSON 경로와 정보 개념 | 응답 위치와 의미 연결 |
> | 값 의미의 확인 근거 | 이름 추정과 검증된 사실 구분 |

> | 검토 시간·수정 항목 수 | 유지 비용 측정 |
>

>
> ### 평가 설계
>
> **정보를 더 받은 효과와 방법의 효과를 나누는 두 실험을 수행한다.**
> - **실험 A — 동일한 확인 근거에서의 판정:** 제안 방법과 단순 규칙에 같은 검토 완료 정책·매핑·응답을 제공한다. 같은 정답을 내는 것이 자연스러운 조건이며, 차이가 없으면 판정 알고리즘의 우월성을 주장하지 않는다.
> - **실험 B — 변경 이후의 갱신 과정:** 같은 이전 규칙, 새 정책·스키마·의미 자료, 동일한 검토 예산에서 시작한다. 매핑 갱신, 탐지 복구, 정상 예외 처리에 필요한 비용과 남은 오류를 비교한다. 이것이 H3의 주요 차별성 검증이다.
>
> | 항목 | 내용 |
> | --- | --- |
> | 검증할 연구 질문 | 변경된 금지 정보를 놓치는 비율과 합법 응답의 오탐을 줄이는가? 최신 규칙을 유지하는 비용을 줄이는가? 정보가 부족할 때 근거 없는 정상을 덜 선언하는가? |
> | 비교 대상 | 아래 비교군 표 참조. 최신 정책을 받은 단순 허용 목록과 일반 매칭을 필수로 포함 |

> | 정답 기준 확보 방법 | 진단기와 분리한 정책 정답, 테스트 데이터의 의미·출처 기록, 수신 응답, 두 검토자의 독립 검토. 정답 생성기를 진단기의 매핑 결과로 구현하지 않음 |
> | 고정할 조건 | 초기 정책·매핑, 변경 자료, 수신 응답, 확인 가능한 정보, 검토 예산, 테스트 요청 수, 사람의 추가 설명 범위 |

> | 가설 지지 기준 | 같은 검토 예산과 비교 가능한 판정률에서 강한 비교군 대비 재현율 개선과 오탐 비열등을 함께 확인하거나, 같은 성능 목표를 더 적은 갱신 비용으로 달성 |
> | 가설 기각·축소 기준 | 최신 허용 목록이나 일반 매칭이 같은 비용으로 동등 이상이면 추가 방법의 우월성을 기각. 불확실 사례를 대량 보류해서 생긴 성능 향상도 제외 |
>
> 재현율의 최소 개선폭, 오탐 비열등 허용폭, 판정률 목표, 검토 예산은 예비 실험을 통해 실행 가능성을 확인한 뒤 **독립 평가 전에 등록·고정**한다. 결과를 본 뒤 유리한 기준으로 바꾸지 않는다. 비용만 개선되면 기여도 규칙 유지 비용 감소로 한정한다.
>
> **비교군 구성**
>
> | 비교군 | 확인할 효과 | 비교 시 주의점 |
> | --- | --- | --- |
> | 개인정보 패턴·필드명 검사 | 정책 없이 정보 유형을 찾는 기준선 | 더 많은 정책 입력을 가진 방법과의 차이를 알고리즘 개선으로 혼동하지 않음 |
> | 변경 전 허용 목록을 유지하는 검사 | 규칙이 낡았을 때의 실패 조건 | 의도적으로 약한 기준선이므로 이것만 이겨 신규성을 주장하지 않음 |
> | 최신 정책의 역할별 허용 목록＋스키마 차이 검사 | 가장 중요한 단순 비교군 | 예외·미등록 필드 처리를 명시하고, 경고와 확정 위반을 구분 |

> | EDEFuzz＋동일한 정책 검토 | 화면 미사용 후보에서 시작하는 접근 | UI 재현이 가능한 부분집합에서 비교. 미사용 여부와 정책 위반의 지표를 따로 보고 |
> | FlowWatcher 방식의 정책·데이터 추적 | 기존 정책 기반 응답 검사의 효과 | 원 도구를 실행했는지 재구현했는지 구분. 추적 가능한 값·관측 조건을 맞춘 부분집합에서 평가 |
> | 통제된 원본 값과의 단순 대조 | 추가 값 정보만으로 해결되는지 확인 | 제안 방법이 원본 값 정보를 받는 조건에서만 동일 입력으로 추가 |
>
> 정책상 알 수 없는 새 필드를 발견한 경고를, 확인된 금지 정보 노출과 같은 정답으로 채점하지 않는다. 비교 도구가 지원하지 않는 입력도 자동으로 미탐에 넣지 않고, 적용 가능 비율과 범위 밖 사유를 따로 보고한다.
>
> **정상 반례와 제거 실험**
> - 이름은 같지만 실제 값이 허용된 대체 정보로 바뀐 사례.
> - 같은 필드를 다른 역할에는 정당하게 제공하는 사례.
> - 새로 추가된 무해한 메타데이터를 금지 정보로 오인하는 사례.
> - 새 스키마가 배포됐지만 실제 응답은 구버전 노드에서 나온 사례.
> - 정책상 허용된 `null`·마스킹·필드 제거와 금지 원문을 구분하는 사례.
> - 구조는 같고 의미만 바뀌어 외부 관측만으로 결론을 낼 수 없는 사례.
> - 정책 버전 연결, 매핑 유효성 확인, 의미 후보 생성, 실제 값 근거 확인을 각각 제거한 비교.
>
> 이 반례들은 해당 실패가 실제 서비스에 얼마나 흔한지 보여주는 자료가 아니라, 제안 방법의 주장 범위를 검증하는 통제 조건이다.
>
> **실험의 독립성과 비용 통제**
> - 같은 변경 사례군의 정상·취약·근거 변형은 같은 데이터 분할에 둔다.
> - 이름과 값만 바꾼 복제본을 서로 독립적인 표본으로 세지 않는다.
> - 모델·프롬프트·매칭 임계값은 평가 전에 고정하고, 사람이 검토할 순서는 무작위화한다.
> - 사람이 이전 조건의 정답을 기억하는 효과를 줄이도록 순서와 검토자 배치를 통제한다.
> - 최초 정책 정리, 매핑 작성, 변경 검토, 재실행, 보류 검토에 든 비용을 포함한다.
> - 사례군 단위의 짝지은 비교와 신뢰구간을 보고하고, 서비스별 결과도 분리한다.
>
> ### 평가 지표
>
> 주 지표의 단위는 **변경 후 응답 사례**다. 독립 정답에 금지 정보가 하나라도 있으면 위반 사례이며, 검토된 검사 범위에서 금지 정보가 없으면 정상 사례다. 여러 필드·배열 원소를 보고했다고 사례 수를 늘리지 않는다.
> - `TP`: 실제 위반 응답을 위반으로 확정.
> - `FP`: 실제 정상 응답을 위반으로 확정.
> - `FN`: 실제 위반 응답을 정상으로 확인.
> - `TN`: 실제 정상 응답을 정상으로 확인.
> - `UV`: 실제 위반이지만 보류.
> - `UN`: 실제 정상이지만 보류.
> - `N = TP + FP + FN + TN + UV + UN`.
>
> | 지표 | 측정 목적 | 계산식·분모 | 보류 사례 처리 |
> | --- | --- | --- | --- |
> | 전체 위반 재현율 | 금지 정보가 남은 응답을 얼마나 찾는가 | `TP/(TP+FN+UV)` | 보류된 실제 위반도 분모에 포함 |
> | 정상 응답 오탐률 | 합법적인 반례를 얼마나 잘못 경고하는가 | `FP/(TN+FP+UN)` | 정상 보류율과 같은 판정률 비교를 함께 보고 |
> | 위반 확정 정밀도 | 확정 보고의 신뢰성 | `TP/(TP+FP)` | 보류로 높아질 수 있으므로 재현율·판정률과 함께 보고 |
> | 잘못된 정상 확인 비율 | 누출이 있는데 안전하다고 결론 내리는 위험 | `FN/(FN+TN)` | `UV`를 별도 보고 |
> | 판정률 | 전체 중 결론을 낸 범위 | `(TP+FP+FN+TN)/N` | 보류는 분모에 포함 |
> | 금지 필드 위치 재현율 | 한 응답 안의 추가 누출을 놓치는지 확인 | 독립 정답의 금지 값 위치 중 정확히 보고한 위치 수 / 전체 금지 값 위치 수 | 보류·누락 위치도 분모에 포함. 정규화 경로와 배열 위치 기준을 사전 고정 |
> | 매핑 정확도와 매핑 범위 | 잘못된 의미 연결과 미연결 구분 | 정확한 확정 매핑 / 전체 확정 매핑, 확정 매핑 / 전체 평가 대상 매핑 | 후보만 제안한 매핑은 확정으로 세지 않음 |
> | 매핑 공백 경고 재현율 | 규칙이 낡았다는 사실을 발견하는가 | 독립 정답에서 갱신이 필요한 매핑 중 경고한 수 / 전체 갱신 필요 매핑 수 | 유출 탐지 재현율과 별도 지표로 보고 |
> | 갱신·검토 비용 | 같은 성능을 유지하는 수고 비교 | 사례군·정책 변경당 작업 시간, 수정 규칙 수, 검토 필드 수 | 보류까지 지출한 비용도 포함 |
> | 탐지 복구 시간 | 변경 후 목표 성능을 회복하는 속도 | 변경 자료 제공부터 사전 성능 목표 충족까지의 시간 | 목표 미달을 0으로 처리하지 않고 미달·관측 종료로 보고 |
> | 근거 없는 확정 비율 | 관측으로 판단할 수 없는 상황의 과신 확인 | 독립 검토상 근거 불충분 사례 중 위반·정상을 확정한 비율 | 우연히 맞은 결론도 따로 기록 |
>
> 분모가 0이면 0%가 아닌 **계산 불가**로 기록한다. 필드별 지표에서는 도구가 발견한 후보만 분모로 사용하지 않는다. 전체 정책 정답에서 평가할 필드·값 위치를 먼저 정한다.
>
> 정답을 확보하지 못한 외부 자료는 정확도 지표에 섞지 않는다. 대신 입력 확보 실패율과 사유를 별도 보고한다. 수집되지 않은 응답이나 검사하지 않은 경로까지 안전하다고 일반화하지 않는다.
>
> ## 6. 선행 연구 공백 및 한계 정리
>
> | 선행 연구·방법 | 해결한 부분 | 남아 있는 한계 | 본 연구에서 검증할 부분 |
> | --- | --- | --- | --- |
> | FlowWatcher [R1] | 정책 기반 HTTP 데이터 추적과 권한 상태 갱신 | 참조 URL·필드가 달라지면 규칙 갱신이 필요하다는 명시적 한계 | 현재 규칙의 적용 공백 감지와 갱신 비용, 여러 버전의 대응 관계 |
> | EDEFuzz [R2] | 응답 변이와 화면 비교로 미사용 필드 후보 탐지 | 민감성 검토는 별도이고, 본 연구의 버전별 금지 정책이 자동 후보 기준은 아님 | 화면 사용 여부와 독립적인 정책 위반, 정책 변경 후의 정상·취약 대조 |
> | COMA [R3] | 여러 매칭 기법, 과거 매핑 재사용, 사용자 피드백 | 스키마 대응을 찾는 것과 수신자별 제공 권한을 판단하는 것은 다른 문제 | 같은 매칭 입력·검토 비용에서 정책·배포 연결의 추가 효과 |
> | 최신 역할별 허용 목록·스키마 검사 [T1에 근거한 비교군] | 어떤 필드를 반환할지 명시적으로 제한 | 정확한 최신 규칙을 유지할 필요. 의미가 같은 형식으로 바뀌는 경우 별도 근거 필요 | 같은 성능의 규칙을 유지하는 비용을 실제로 줄이는가 |
> | 개인정보 패턴 검사 | 알려진 문자열·자료형의 후보 탐지 | 허용된 대체 값과 금지 원문, 역할별 예외를 패턴만으로 구분하기 어려움 | 유형 탐지를 넘어선 정책 판정의 정보 요구량 |
>
> 이 공백은 **확인한 선행연구의 가정·평가 범위와 목표 환경의 차이**다. 정책 버전 관리나 의미 매핑을 처음 제안한다는 의미가 아니며, 최신의 모든 관련 연구를 배제한 신규성 증명도 아니다.
>
> **최종 연구 질문**
>
> > 검토된 정책 변경 이력, 배포별 스키마와 제한된 의미 확인 자료만으로 정책 변경 후 남은 금지 정보를 어느 범위까지 진단할 수 있으며, 동일한 검토 예산에서 최신 허용 목록·일반 매칭보다 탐지 재현율·정상 오탐·보류·규칙 유지 비용은 어떻게 달라지는가?
>
> **예상 기여**
> - **방법:** 요청별 정책·배포·필드 의미의 적용 가능성을 확인하고, 변경된 매핑을 검토하며, 실제 금지 정보와 진단 범위의 공백을 구분하는 절차.
> - **평가:** 정책만 변경, 이름·경로 변경, 같은 이름의 의미 변경, 역할 예외, 배포 병존을 포함한 정상·취약 대조 데이터와 동일 입력·예산 평가.
> - **실증 결과:** 어떤 변경은 단순 허용 목록으로 충분하고 어떤 변경은 추가 의미 근거가 필요한지, 그 근거를 유지하는 비용이 어느 정도인지에 대한 재현 가능한 분석.
>
> 정책과 매핑을 모두 정확히 주었을 때 단순 규칙과 결과가 같다면 이를 정직하게 보고한다. 유지 비용에서도 이점이 없으면 별도 방법의 우월성 주장을 기각한다. 데이터셋이나 실패 조건 분석의 기여도 기존 평가를 실제로 개선했는지 따로 입증해야 한다.
>
> **남은 불확실성**
> - 실서비스에서 정책의 실제 적용 범위와 배포 정보를 독립적으로 확인할 수 있는가?
> - 필드 문서가 실제 값의 의미와 일치하는지 확인할 자료를 얻을 수 있는가?
> - 같은 형식의 실전화번호·대체 번호처럼 관측상 구분할 수 없는 경우가 얼마나 많은가?
> - 이름·구조를 결합한 일반 매칭과 최신 단순 규칙보다 추가 이점이 있는가?
> - 사람의 매핑 확인 비용이 자동화로 절약한 비용보다 커지지 않는가?
> - 정책 작성자가 빠뜨린 예외나 의미 분류 오류가 최종 판정에 어떤 영향을 주는가?
> - 적용되지 않는 UI·프로토콜·변환을 제외한 뒤에도 충분한 평가 범위가 남는가?

# 정책 변경 후 응답 필드 인가 진단

> **가설**
>
> 정책이나 API 구조가 바뀌면, 바뀐 내용에 영향을 받은 응답 필드를 다시 검토하고 뜻을 확인하지 못한 필드는 보류한다.
>
> **같은 정책 자료와 확인 기회를 제공했을 때, 이 방식은 최신 규칙을 사람이 고치거나 기존 증분 갱신 방법을 쓰는 경우보다 진단 품질을 유지하면서 사람의 총 작업 시간을 줄일 수 있다.**
>
> ## 필요한 이유
>
> 실제 전화번호를 보내지 않도록 정책을 바꿔도 API는 예전 정보를 계속 보낼 수 있다.
>
> 필드 이름이나 위치가 바뀌면 진단 규칙도 다시 맞춰야 한다. 그렇다고 매번 모든 필드를 다시 확인하면 작업이 커진다.
>
> 숫자 모양만 검사하면 정책상 허용된 안심번호까지 위반으로 오해할 수 있다.
>
> ## 직접적인 선행논문
> - Velegrakis et al., **Mapping Adaptation under Evolving Schemas**, VLDB 2003 — 구조가 바뀔 때 기존 의미 연결을 고치는 연구. [원문](https://www.vldb.org/archives/website/2003/papers/S18P02.pdf)
> - Muthukumaran et al., **FlowWatcher**, CCS 2015 — 정책과 실제 HTTP 데이터를 대조하는 연구. [원문](https://lsds.doc.ic.ac.uk/sites/default/files/ccsfp224-muthukumaran_0.pdf)
> - Liu et al., **Magneto**, PVLDB 2025 — 최근 모델로 필드 사이의 대응 관계를 찾는 연구. [원문](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
>
> ## 차이점
>
> 바뀐 부분만 검토하고 기존 연결을 재사용하는 것은 이미 연구됐다. 이 자체를 새 방법이라고 주장하지 않는다.
>
> 이 연구는 **누가 어떤 업무에서 어떤 배포의 정보를 받았는지**를 연결하고, 실제 값의 뜻을 확인하는 데 든 시간까지 포함해 갱신 비용을 비교한다.
>
> 비용과 함께 위반을 찾는 비율·정상 오탐률·판정 범위·보류율을 측정한다. 단순한 최신 규칙이나 기존 증분 방법으로 충분하면 새로운 방법의 우월성 주장을 줄인다.

“정보 제공 정책이 바뀐 뒤, 진단 규칙을 적은 작업으로 고치면서 금지 정보가 남았는지 확인할 수 있나?”라는 가설을 검증하는 주제다.

## 주제 정의

> 객체 조회 자체는 허용된 상황에서, 정책 변경 자료와 API 구조, 필드의 뜻을 확인할 자료를 이용해 **더 이상 보내면 안 되는 정보가 응답에 남았는지** 진단한다.
>
> 변경의 영향을 받은 연결은 다시 확인하고, 여전히 유효하다고 확인한 연결은 재사용한다. 근거가 없으면 보류한다.
>
> 같은 자료를 받은 수동 갱신·기존 증분 갱신·최근 필드 매칭 방법과 비교해, **진단 품질을 유지하며 초기 준비부터 수정·재검증까지의 사람 작업을 줄일 수 있는지** 측정한다.

**예시**

가상의 배송 API를 생각하면 된다. 실제 사건의 필드나 코드를 재현한 예시는 아니다.
- 이전 정책: 배송기사에게 고객의 실제 전화번호를 보내도 된다.
- 새 정책: 해당 배송 업무에는 안심번호만 보내야 한다.

| --- | --- | --- |
| `real_phone`에 실제 번호가 남음 | 새 정책 적용과 값의 의미 | 확인되면 위반 |
| 이름이 바뀐 `contact.value`에 실제 번호가 남음 | 새 위치와 실제 값의 의미 | 확인되면 위반 |
| 기존 `phone`에 안심번호를 반환 | 값이 안심번호이고 해당 업무에서 허용되는지 | 확인되면 관측 범위 정상 |
| `contact.value`의 뜻을 모름 | 데이터 사전·생성 경로·검토 자료 | 확인하지 못하면 보류 |

필드 이름이나 숫자 형식만으로 실제 번호와 안심번호를 구분하지 않는다. 무엇을 담은 값인지 확인할 자료가 필요하다.

## 용어 정리

**API**

앱이 서버에 데이터를 요청하는 창구.

**응답 필드**

서버가 돌려주는 데이터의 항목. `name`, `phone`, `address` 같은 것.

**필드별 인가**

객체를 볼 수 있는 사용자에게도 그 안의 각 정보까지 보내도 되는지 판단하는 것.

**정책**

누구에게 어떤 업무에서 어떤 정보를 보내도 되는지 정한 규칙.

**스키마**

응답에 어떤 항목이 있고 어디에 들어가는지 적은 구조 설명.

**배포 버전**

해당 응답을 만든 서버 프로그램의 버전. 최신 문서의 버전과 같다고 가정하지 않는다.

**필드 의미 연결**

`contact.value`가 고객 연락처인지, 실제 번호인지, 안심번호인지 근거와 함께 연결한 기록. 연구계획서에서는 의미 매핑이라고 부른다.

**의미 근거**

값의 뜻을 확인할 자료. 데이터 사전, 값을 만든 코드·변환 과정, 통제된 원본 데이터 등이 해당한다.

**갱신**

정책이나 API가 바뀐 뒤 진단 규칙과 의미 연결을 새 상태에 맞게 고치는 작업.

**증분 갱신**

전체를 처음부터 다시 만들지 않고, 변경의 영향을 받은 부분을 고치는 방법.

**확정**

실제로 받은 정보의 뜻과 해당 요청에 적용되는 금지 정책이 확인됐을 때 위반이라고 결론 내리는 것.

**판정 보류**

값의 뜻·정책·배포 연결 같은 근거가 부족해 위반·정상을 결정하지 않는 것.

**판정 범위**

전체 응답 중 위반 확인 또는 관측 범위 정상으로 결론을 낸 비율. 확인한 위반 옆에 미확인 필드가 남으면 별도로 표시한다.

**오탐률**

실제로 정상인 응답을 위반이라고 잘못 판정한 비율.

**재현율**

실제 위반 응답 중 위반으로 확인한 비율. 보류한 실제 위반도 전체 위반 수에 포함한다.

**보류율**

전체 응답 중 결론을 내리지 못한 비율.

**갱신 비용**

초기 규칙·의미 연결 준비, 자료 확인, 수정, 재실행, 결과 검토에 든 사람의 작업 시간. 실패한 질문과 보류 결과를 확인한 시간도 포함한다.

## 근거 정리

### 1. 정책을 바꿔도 실제 응답에는 예전 정보가 남을 수 있다
- **국내 공식 자료에 실제 전화번호 전송이 계속된 사례가 있다**

개인정보보호위원회가 2026년 7월 9일 공개한 자료에는, 실제 전화번호 대신 안심번호를 제공하도록 바꿨지만 API를 통해 실제 전화번호가 계속 전달된 사례가 나온다. 상대 시스템에는 약 13만 5천 명의 정보가 남았다고 설명한다. [공식 자료: 「개인정보도 함께 전송하고 있나요?」](https://www.korea.kr/news/policyNewsView.do?newsId=148967849)

정책 문서를 고쳤다는 사실만으로 실제 전송 정보도 바뀌었다고 볼 수 없다는 근거다.

다만 이 자료에는 필드 이름 변경, 캐시, 응답을 만드는 코드, 배포 전파 중 무엇이 기술적 원인이었는지 나오지 않는다. 아래 실험은 가능한 변경 조건을 만든 것이며, 이 사건의 원인을 재현했다고 쓰지 않는다.

### 2. 정책 기반 검사도 URL이나 필드가 바뀌면 규칙을 고쳐야 한다
- **FlowWatcher는 정책이 참조하는 URL·필드 변경에 맞춰 갱신해야 한다고 설명한다**

> “UDA policies must be updated if an application changes URLs or fields referred to in a policy.”
>
> → 애플리케이션이 정책에서 참조하는 URL이나 필드를 바꾸면 **그 정책도 갱신해야 한다.**
>
> (Muthukumaran et al., *FlowWatcher*, CCS 2015, §3.5, PDF 6쪽. [원문](https://lsds.doc.ic.ac.uk/sites/default/files/ccsfp224-muthukumaran_0.pdf))

정책이 있어도 그 정책과 실제 데이터의 연결이 오래되면 검사에 문제가 생길 수 있다.

FlowWatcher가 정책 변화를 전혀 처리하지 못한다는 뜻은 아니다. 사용자·그룹·접근권한의 동적 갱신도 지원한다. 이 연구에서는 **어떤 변경에서 어떤 연결을 다시 확인해야 하고, 그 작업에 얼마가 드는지**를 비교한다.

### 3. 바뀐 부분만 확인하는 방법은 이미 연구됐다
- **ToMAS는 구조 변경 때문에 잘못된 연결을 찾아 고치는 문제를 다룬다**

> “Mappings left inconsistent by a schema change have to be detected and updated.”
>
> → 스키마 변경으로 맞지 않게 된 연결을 **찾아서 고쳐야 한다.**
>
> (Velegrakis, Miller, Popa, *Mapping Adaptation under Evolving Schemas*, VLDB 2003, 초록, PDF 1쪽. [원문](https://www.vldb.org/archives/website/2003/papers/S18P02.pdf))

이 연구는 영향을 받은 연결을 고치고, 사람이 이전에 내린 의미 판단을 가능한 경우 재사용한다. 사람의 유지 작업을 줄이는 목적도 이미 제시했다.
- **접근 규칙을 바꾸는 연구에도 자동 처리와 사람 확인이 함께 있다**

> “the system then only reports the problem to the user and asks him for an adequate solution strategy.”
>
> → 자동으로 해결할 수 없는 경우에는 **문제를 사용자에게 알리고 해결 방법을 묻는다.**
>
> (Rinderle, Reichert, *On the Controlled Evolution of Access Rules in Cooperative Information Systems*, 2005, §4, PDF 13쪽. [원문](https://dbis.eprints.uni-ulm.de/136/1/RiRe05.pdf))

따라서 “바뀐 곳만 확인한다”, “예전 연결을 재사용한다”, “모르면 사람에게 묻는다”는 것만으로 새 연구라고 할 수 없다.

**기존 증분 방법에도 같은 정책·의미 자료를 주고 비교해야 한다.** 기존 방법으로 같은 비용에 같은 결과가 나오면 그 사실을 결과로 받아들인다.

### 4. 최근 필드 매칭 모델도 후보를 놓칠 수 있다
- **Magneto는 후보에 정답이 없으면 순위를 다시 매겨도 복구하지 못한다고 설명한다**

> “if the correct match is missing from the top-k, reranking cannot recover it.”
>
> → 올바른 연결이 상위 k개 후보에 없으면, **순위를 다시 매겨도 되찾을 수 없다.**
>
> (Liu et al., *Magneto*, PVLDB 2025, §8, 인쇄 2692쪽 / PDF 12쪽. 수식의 k를 일반 문자로 옮김. [원문](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf))

Magneto는 작은 모델로 후보를 찾고 큰 모델로 다시 정렬한다. 이름·자료형·값 표본을 이용하는 최근 비교군이다.

그러나 필드 대응을 찾는 것과 실제 값이 정책상 금지된 정보임을 확인하는 것은 다르다. `phone`이 연락처 항목이라는 사실만으로 이번 값이 실제 번호인지 안심번호인지 알 수는 없다.

그래서 **모델이 고른 연결을 정답으로 바로 쓰지 않고, 같은 확인 자료로 검토한다.** 확인할 자료가 없으면 보류한다. 이름과 구조가 그대로인 의미 변경도 따로 평가한다.

### 5. 검토할 후보 수와 사람이 실제로 쓴 시간은 다르다
- **TaDA 연구는 검증 부담을 확인할 후보 개수로 측정한다**

> “Verification effort: the count of matches that have to be inspected when combining two task scopes.”
>
> → 검증 부담은 두 비교 방식을 함께 쓸 때 **살펴봐야 하는 대응 후보의 개수**다.
>
> (Parciak et al., *Schema Matching with Large Language Models: an Experimental Study*, TaDA 2024, §3.2.2, Table 6, PDF 8쪽. [원문](https://www.vldb.org/workshops/2024/proceedings/TaDA/TaDA.8.pdf))

후보가 적어도 확인하기 어려운 자료라면 시간이 오래 걸릴 수 있다. 질문에 답이 없거나 잘못 고친 연결을 다시 확인하는 작업도 생긴다.

Matchmaker도 불확실한 결과를 오라클에 넘기는 평가를 한다. 하지만 그 수정·보류 비율을 실제 사람이 규칙을 고치는 시간으로 읽으면 안 된다. [Seedat, Van Der Schaar, ICML 2025, §5.3](https://proceedings.mlr.press/v267/seedat25a.html)

이 연구에서는 **사람이 자료를 확인하고 수정·재검증하는 실제 시간**을 기록한다. 모델 호출 수·토큰·연산 시간은 별도로 기록한다.

### 6. 화면에서 쓰지 않는 정보가 모두 금지 정보는 아니다

EDEFuzz는 응답 항목을 제거했을 때 화면 동작이 달라지는지 확인해 불필요한 공개 후보를 찾는다. 논문에는 후보를 사람이 확인하고 민감성을 판단하는 과정이 포함된다. [Pan et al., ](https://arxiv.org/pdf/2301.09258v2)[*EDEFuzz*](https://arxiv.org/pdf/2301.09258v2)[, ICSE 2024, §4.5·§5](https://arxiv.org/pdf/2301.09258v2)

화면에서 쓰지 않는다는 사실과 특정 사용자에게 보내면 안 된다는 정책은 같지 않다. 반대로 화면에서 쓰는 정보여도 그 사용자에게는 금지일 수 있다.

따라서 화면 미사용 검사와 개인정보 패턴 검사는 보조 비교로 두고, **최신 정책 검사와 기존 증분 갱신을 핵심 비교군**으로 둔다.

**현재까지 문헌과 기존 코드를 확인했으며, 새 방법의 구현·비교 실험·작업 시간 측정은 아직 수행하지 않았다.**

### 무엇을 시험할 것인가

작은 예비 실험은 **6개 변경 유형 × 4개 사례군 = 24개 사례군**으로 계획한다.

| 변경 유형 | 시험할 내용 |
| --- | --- |
| 정책만 변경 | API는 그대로인데 실제 번호 제공이 금지됨. 최신 허용 목록만으로 충분한 경우도 포함 |
| 필드 이름 변경 | 같은 정보의 이름이 바뀜. 이름이 비슷해도 뜻이 다른 경우도 포함 |
| 중첩·배열로 이동 | 금지 정보가 허용된 상위 항목 안이나 배열 원소로 들어감 |
| 구조는 같고 의미만 변경 | 같은 `phone` 항목이 실제 번호 또는 안심번호를 반환 |
| 역할·업무별 예외 | 같은 정보가 한 사용자·업무에는 허용되고 다른 경우에는 금지됨 |
| 여러 배포가 함께 동작 | 같은 API 주소에서 구·신 버전 응답이 나옴 |

각 사례군에 정상·취약 응답과 충분·누락·충돌 자료를 넣는다면 144개 관측 조건이 된다. **계획 수치이며, 144개의 독립 사례나 실험 결과가 아니다.**

알려진 정보가 바뀌는 사례뿐 아니라 새 정책이 새로운 금지 정보 개념을 요구하는 사례도 확장 조건으로 넣는다.

### 어떻게 비교할 것인가

모든 핵심 방법에 같은 이전 규칙, 정책 변경 자료, 스키마, 의미 확인 자료와 질문 기회를 준다. 확인한 자료를 재사용할 수 있는 조건과 보류 기준도 공통으로 둔다.

| 방법 | 하는 일 |
| --- | --- |
| 최신 규칙의 수동 갱신 | 사람이 자료를 확인해 허용 목록과 의미 연결을 고침 |
| 전체 재검토 | 변경마다 범위 안의 모든 연결을 다시 확인 |
| 기존 증분 갱신 | ToMAS 계열 원리에 따라 영향을 받은 연결을 고치고 유효한 연결을 재사용 |
| 최근 매칭 기반 갱신 | Magneto 등으로 대응 후보를 찾은 뒤 같은 자료로 확인 |
| 제안 절차 | 정책·필드·의미 근거의 변경 관계를 이용해 재검토·재사용 순서를 정함 |

기존 증분 방법에도 정책 변경 자료와 의미 근거의 관계를 제공한다. 같은 후보 생성기를 쓴 비교와 모델을 바꾼 비교를 분리한다. 같은 정책 우선순위를 준 단순 증분 방법도 대조한다.

원 도구를 실행하지 못해 논문 원리에 따라 만든 비교군은 **재구현**이라고 표시한다. JSON 필드를 표 형태로 바꾸거나 Magneto에 설명·배포 맥락을 추가하면 원논문의 직접 재현과 구분하고, 그 준비 비용도 기록한다.

제안 절차는 다음 순서로 진행한다.
1. 누구의 어떤 요청인지, 어느 정책·배포가 적용되는지 확인한다.
1. 바뀐 정책·구조·의미 근거에 연결된 필드를 재검토 대상으로 표시한다.
1. 현재 응답의 검사 대상 필드를 모두 열거하고 새 필드도 미확인 항목으로 남긴다.
1. 관련 근거가 현재 배포에서 여전히 유효하다고 확인된 연결만 재사용한다.
1. 같은 후보 생성기와 확인 자료로 남은 연결을 고친다. 모름·충돌·예산 소진은 보류한다.
1. 실제 정보와 정책을 비교하고, 작업 시간을 기록한다.

이름·자료형이 같다는 이유만으로 의미도 같다고 보지 않는다. 정책 변화에 연결된 항목을 먼저 확인하는 단순 순서를 쓰되, 이 순서만으로 이득이 생기는지도 비교한다.

### 무엇을 측정하나

| 지표 | 측정 내용 |
| --- | --- |
| 사람 작업 시간 | 초기 준비, 자료 조회, 실패 질문, 연결 수정, 재실행, 결과·보류 검토 |
| 누적 유지 비용 | 초기 구축 시간 + 여러 차례 변경에서 사용한 시간 |
| 재현율 | 모든 실제 위반 중 확인한 위반. 보류한 실제 위반도 분모에 포함 |
| 정상 오탐률 | 모든 실제 정상 응답 중 위반으로 잘못 판단한 응답 |
| 판정 범위·보류율 | 결론을 내린 범위와 근거 부족으로 남긴 범위 |
| 잘못된 정상 판정 | 실제 위반을 정상으로 확정한 건수. 전체 실제 위반 기준과 전체 정상 선언 기준의 비율을 구분 |
| 목표 품질 달성률 | 사전 기준을 최대 예산 안에 충족한 사례의 비율 |
| 모델·연산 비용 | 호출·토큰·실행 시간·비용. 사람 작업 시간과 별도 기록 |

최소 재현율·판정 범위, 최대 오탐률과 허용 차이는 본 평가 전에 고정한다. **비용 감소와 품질 유지가 함께 성립해야** 주가설을 지지한다. 많이 보류해서 오탐만 낮추거나 필요한 준비 비용을 빼서 저렴하다고 하지 않는다.

모든 방법은 같은 예산 지점에서 상태를 저장하고, 외부 평가자가 나중에 정답과 비교한다. 작업자가 시험 정답을 보면서 목표에 도달했다고 중단하지 않는다.

목표를 끝내 달성하지 못한 사례는 실패로 남긴다. 성공한 사례만 골라 평균 시간을 비교하지 않는다. 같은 사례군의 변형도 독립 표본으로 세지 않는다. 사람 실험에서는 방법 순서와 같은 사례를 기억하는 효과를 통제한다.

### 어떤 경우에는 해결할 수 없나

스키마·숫자 형식이 같고 실제 번호인지 안심번호인지 알려 주는 자료도 없다면, 외부 응답만으로 구분하지 못할 수 있다. 의존 관계나 모델의 자신감으로 이 한계를 해결했다고 하지 않는다.
- **자료를 조회하면 확인 가능한 경우:** 확인에 필요한 시간과 예산을 측정한다.
- **자료 자체가 없어 확인 불가능한 경우:** 보류와 적용 한계로 남긴다. 이런 사례도 전체 자료의 비율에 포함한다.
- **확인된 금지 정보와 미확인 필드가 함께 있는 경우:** 이미 확인한 위반을 보고하고 미확인 범위를 함께 남긴다.
- **정상이라고 결론 내리는 경우:** 검사 대상의 적용 정책·실제 값 의미·배포·관측 범위를 충분히 확인해야 한다.

## 정리

### 선행 연구 공백 및 한계
- 정책과 응답을 대조하는 방법에도 참조 URL·필드의 유지 작업이 필요하다. **FlowWatcher**가 이 문제를 설명한다.
- 변화에 따른 연결 수정·재사용과 사람 확인은 이미 **ToMAS·접근 규칙 진화 연구**에 있다. 이 자체는 신규성이 아니다.
- 최근 **Magneto**도 대응 후보를 놓칠 수 있다. 필드 대응 결과가 실제 값의 뜻과 수신자별 허용 여부를 증명하지는 않는다.
- **TaDA**의 후보 개수와 **Matchmaker**의 오라클 이관 비율은 실제 사람의 총 갱신 시간과 다르다.
- **EDEFuzz**의 화면 미사용 후보와 정책상 금지 정보는 구분해야 한다.

**→ 같은 자료와 확인 기회를 제공했을 때, 정책·배포·값 의미의 변화를 연결하는 절차가 진단 품질을 유지하며 사람의 총 갱신 작업을 줄일 수 있는가?**

### 연구의 가치가 생기는 조건

기존 증분 방법보다 이득이 확인되고, 추가 자료·더 좋은 매칭 모델·과도한 보류로 설명되지 않을 때 갱신 절차의 효과를 주장한다.

그렇지 않으면 방법의 우월성 대신 **어떤 정책·배포·의미 자료가 필요하고, 그 자료를 확보하는 데 얼마가 들며, 어디까지 판정할 수 있는지**를 밝히는 연구로 좁힌다. 공개 변경 사례와 독립 정답·비교 설정을 남기는 것도 후보 기여다.

합성 사례의 성공을 실서비스 전체의 성능으로 일반화하지 않는다. 상세 입력 계약·비용 처리·제거 실험·통계 설계는 [보완 연구계획서 v2](https://app.notion.com/p/H3-%EC%A0%95%EC%B1%85-%EB%B3%80%EA%B2%BD-%ED%9B%84-%EC%9D%91%EB%8B%B5-%ED%95%84%EB%93%9C-%EC%9D%B8%EA%B0%80-%EC%A7%84%EB%8B%A8-%EB%B3%B4%EC%99%84%EC%97%B0%EA%B5%AC%EA%B3%84%ED%9A%8D%EC%84%9C-v2.md)에 있다.
