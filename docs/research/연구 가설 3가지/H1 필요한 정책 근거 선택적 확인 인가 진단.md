# 필요한 정책 근거를 선택적으로 확인하는 API 인가 진단

> **1차** (노션 토글)
> # 제한된 정책 정보에서 필요한 근거를 선택적으로 확인하는 API 인가 진단
>
> > **가설**
> >
> > 공개·공유·관리자 예외가 존재하고 전체 권한표를 확보하기 어려운 API 환경에서, **판정에 필요한 정책 근거를 선택적으로 확인하고 근거가 부족하거나 충돌하는 사례를 보류하는 방법**을 사용하면, 동일한 정책 확인 비용과 판정률에서 응답 비교 및 일반적인 정보 선택 방법보다 인가 위반의 오탐과 미탐을 줄일 수 있다.
> >
> > 이때 실제 위반을 충분히 찾아내는지 확인하기 위해 위반 재현율의 하한을 함께 적용한다.
> >
> > **필요한 이유**
> >
> > 계정을 바꿔 같은 데이터를 받았다는 사실만으로는 인가 위반을 확정하기 어렵다. 해당 데이터가 공개됐거나, 소유자가 공유했거나, 요청자에게 관리 권한이 있을 수 있기 때문이다.
> >
> > 반대로 모든 대상의 권한을 사람이 미리 입력하도록 하면 정책 작성·확인 비용이 커진다.
> >
> > 이를 해결하려면 **현재 사례의 결론을 바꿀 수 있는 정보를 골라 확인하고, 확인된 정책과 실제 응답을 연결하는 접근 방식**이 필요하다.
> >
> > **직접적인 선행 연구**
> > - Chaoshun Zuo, Qingchuan Zhao, Zhiqiang Lin, *AuthScope: Towards Automatic Discovery of Vulnerable Authorizations in Online Services*, ACM CCS 2017. [원문](https://acmccs.github.io/papers/p799-zuoA.pdf)
> > - Jay Barach, *AuthProbe: Specification-Driven, Multi-Identity Detection of Broken Object-Level Authorization in Recruitment APIs*, arXiv 사전공개 논문, 2026, v1. [원문](https://arxiv.org/html/2607.20574v1)
> > - Omur Sahin, Man Zhang, Andrea Arcuri, *Enhancing REST API Fuzzing with Access Policy Violation Checks and Injection Attacks*, arXiv 사전공개 논문, 2026, v1. [원문](https://arxiv.org/html/2604.00702v1)
> >
> > **차이점**
> >
> > 위 연구들은 계정별 요청·응답 비교, 객체 소유 관계, 실행 중 관찰한 접근 허용·거부 패턴 등을 이용한다. 공개 자료를 오탐에서 제외하는 처리도 이미 존재한다.
> >
> > 본 연구는 **어떤 정책 사실을 추가로 확인해야 하는지, 그 근거를 현재 요청에 적용할 수 있는지, 확인에 얼마의 비용이 드는지**를 함께 다룬다.
> >
> > 판정 보류와 비용 기반 정보 선택 자체를 새로운 기법으로 주장하지 않는다. API 인가 환경에 적용한 절차가 기존 기법과 같은 입력을 받는 단순 규칙보다 나은지를 **오류율·판정률·위반 재현율·정책 확인 비용**으로 검증한다.
>
> ## 1. 주제 정의
>
> **한 문장 설명**
>
> “전체 권한표를 작성하지 않고도, 필요한 정책 정보만 확인해서 정상 접근과 권한 없는 접근을 정확하게 구분할 수 있는가?”를 선택적 근거 확인과 판정 보류를 통해 검증하는 연구.
>
> **연구 범위**
>
> > 다중 사용자 REST API 환경에서 테스트 계정, 객체 식별 정보, 요청·응답 기록, 확인 가능한 일부 정책 정보를 이용하여 **객체 조회에 대한 인가 진단 방법**을 개발한다.
> >
> > 현재 요청자에게 해당 객체의 조회를 금지하는 정책 근거와 실제 데이터 반환 증거가 있으면 위반으로 판정한다. 허용 여부나 응답의 대상 객체를 확인하지 못하면 판정을 보류한다.
> >
> > 이후 합성 API와 조건을 충족하는 공개 테스트 애플리케이션에서 응답 비교, 고정 순서 정책 확인, 일반적인 비용 기반 정보 선택, 동일 입력의 단순 규칙과 비교한다.
>
> | 구분 | 내용 |
> | --- | --- |
> | 연구 대상 | 여러 계정이 객체를 조회하는 REST API |
> | 포함 범위 | 객체 소유권, 명시적 공유, 공개 여부, 관리자·조직 권한, 테넌트 경계, 정책 근거의 누락·충돌 |
> | 제외 범위 | 쓰기·삭제의 실제 효과, 비동기 작업, 권한 회수의 시간 지연, 필드별 개인정보 분류, 유효한 권한을 가진 내부자의 목적 외 사용 |
> | 필요한 입력 | 테스트 계정, 조회 가능한 객체, 요청·응답, 계정·객체 연결 정보, 해당 서비스의 정책 규칙 종류, 추가 정책 사실을 확인할 경로 |
> | 최종 산출물 | 근거 선택 절차, 진단 시제품, 근거·판정 기록 형식, 정상 사례와 취약 사례를 포함한 평가 데이터, 비교 실험 결과 |
>
> 여기서 **전체 권한표가 없어도 된다는 것은 정책을 전혀 몰라도 된다는 뜻이 아니다.** 예를 들어 해당 서비스가 소유자·공유 대상·조직 관리자에게 조회를 허용한다는 규칙은 알아야 한다. 다만 모든 사용자와 객체의 관계를 미리 채우는 대신, 필요한 관계만 확인한다.
>
> **이해를 위한 예시**
>
> 지영이가 민수의 주문을 조회했고, 주문 정보가 반환됐다.
>
> | 추가로 확인한 사실 | 가능한 판단 |
> | --- | --- |
> | 민수가 지영이에게 해당 주문을 공유했고, 공유받은 사람의 조회가 허용됨 | 해당 조회는 정상 |
> | 공유되지 않았고, 공개·관리자 등 다른 허용 조건도 적용되지 않음 | 인가 위반 |
> | 공유 여부를 확인할 수 없고 다른 근거로도 허용·금지를 결정할 수 없음 | 판정 보류 |
>
> 이 연구는 세 경우를 구분하면서 **확인해야 하는 정보의 양과 사람의 수고를 줄일 수 있는지**를 묻는다.
>
> ## 2. 용어 정리
>
> | 용어 | 쉬운 설명 | 본 연구에서의 의미·기준 |
> | --- | --- | --- |
> | 인증 | 요청자가 누구인지 확인하는 것 | 테스트 계정과 요청의 자격증명이 대응하는지 확인 |
> | 인가 | 그 사람이 해당 일을 해도 되는지 확인하는 것 | 특정 요청자가 특정 객체를 조회할 수 있는지 판단 |
> | 객체 | API로 조회하는 대상 | 주문, 문서, 지원서 등 식별 가능한 업무 데이터 |
> | 정책 근거 | 허용·금지를 판단하는 데 필요한 사실 | 객체 소유자, 공유 관계, 공개 설정, 역할, 조직 관계 등 |
> | 독립적인 근거 | 검사 대상의 응답을 그대로 믿지 않고 별도로 확보한 자료 | 검토된 정책 문서, 테스트 초기 설정, 별도로 검증한 관리 기록 등 |
> | 최소 근거 | 해당 결론에 필요했던 작은 정보 집합 | 본 연구에서는 비용을 줄이는 목표를 뜻하며, 전역 최솟값을 보장한다는 의미는 아님 |
> | 위반 확정 | 금지된 조회가 실제로 성공했음을 확인 | 적용 가능한 금지 근거와 보호 객체의 실제 반환 증거가 모두 존재 |
> | 정상 확인 | 검사한 조회가 확인된 정책과 일치 | 허용된 조회가 정상적으로 반환되거나, 금지된 조회가 차단됐음을 관측 범위에서 확인 |
> | 판정 보류 | 근거가 부족하거나 충돌해 결론을 내리지 못함 | 관계 미확인, 정책 버전 불일치, 응답 누락, 객체 연결 불가 등 |
> | 판정률 | 전체 사례 중 도구가 결론을 낸 비율 | 위반 확정 또는 정상 확인의 비율. 정책 확인에 사람이 참여한 비용은 별도 집계 |
>
> **정상 확인은 해당 요청에 대한 결론이다. 서비스 전체가 안전하다는 의미로 사용하지 않는다.**
>
> ## 3. 근거 정리
>
> ### 3.1. 타인의 객체에 접근했다는 사실만으로는 인가 위반을 확정하기 어렵다
>
> **선행 연구에서 확인한 내용**
>
> > “Simply stating that a user should not access or manipulate resources of other users would just result in many false-positive faults.”
>
> → 다른 사용자의 자원에 접근하거나 수정하면 무조건 문제라고 판단하는 방식은 많은 오탐을 만들 수 있다는 뜻이다.
> - **출처:** Sahin, Zhang, Arcuri, 2026, §3.3 *Missed Authorization Checks*. [R3 원문](https://arxiv.org/html/2604.00702v1#S3.SS3)
> - **직접 확인되는 사실:** 논문은 관리자와 특정 게시판의 운영자처럼 다른 사용자의 자원에 정당하게 접근할 수 있는 사례를 설명한다.
> - **본 연구와의 연결:** 계정이 다르다는 사실에 더해 공유·역할·조직 관계 중 무엇을 확인해야 하는지 판단할 필요가 있다.
> - **해석의 한계:** 기존 도구가 모든 교차 접근을 취약점으로 처리한다는 뜻은 아니다. 해당 논문도 접근 패턴을 이용해 오탐을 줄이는 오라클을 제안한다.
>
> AuthScope 역시 공개 자원이 오탐을 만들 수 있음을 설명하고, 로그인하지 않은 실행을 추가해 공개 자원 후보를 제외한다. 따라서 **공개 자료를 고려하는 것 자체는 신규성이 아니다.** [R1, §4.3](https://acmccs.github.io/papers/p799-zuoA.pdf)
>
> 본 연구가 추가로 검증할 부분은 공개 여부뿐 아니라 공유·관리 권한 등을 포함해 **어떤 사실을 어떤 순서로 확인하는 것이 유리한가**이다.
>
> ### 3.2. 진단에 사용하는 소유 관계 자체도 검증이 필요한 입력이다
>
> **선행 연구에서 확인한 내용**
>
> > “a target whose collection operation does not faithfully reflect ownership could distort that construct”
>
> → 목록 조회 API가 실제 소유 관계를 올바르게 나타내지 않으면 진단의 판단 기준이 왜곡될 수 있다는 뜻이다.
> - **출처:** Barach, *AuthProbe*, 2026, §VIII-A *Threats to validity*. [R2 원문](https://arxiv.org/html/2607.20574v1#S8.SS1)
> - **직접 확인되는 사실:** AuthProbe는 목록 조회 또는 명시적으로 제공한 초기 객체 정보를 활용한다. 논문은 목록 조회에 근거한 소유 관계의 타당성을 한계로 명시한다.
> - **본 연구와의 연결:** 검사 대상 API에서 얻은 관계 정보와, 별도로 검증된 관계 정보를 구분할 필요가 있다.
> - **해석의 한계:** 실제 서비스에서 목록 API가 자주 틀린다는 발생률을 보여주는 결과는 아니다. 별도 초기 정보를 제공하는 사용 방식도 존재한다.
>
> 예를 들어 목록 API와 상세 조회 API에 같은 권한 누락이 있으면, 목록에 나타난 객체를 모두 정상 접근 대상으로 믿는 진단은 문제를 놓칠 수 있다. **이 상황은 위 한계에서 도출한 실험 가설이며, 본 연구에서 재현·검증할 대상이다.**
>

>
> McHire 사례는 **연구자가 확인한 취약점과 실제 대규모 악성 반출을 구분**한다. 회사는 내려받은 채팅 기록 7개 중 개인정보가 포함된 기록이 5개였으며, 해당 테스트 계정의 제3자 사용은 확인되지 않았다고 설명했다. [I2](https://www.paradox.ai/blog/responsible-security-update)
>
> 이 사례들은 객체 인가 진단의 필요성을 뒷받침한다. 다만 **제안 방법이 해당 사고를 예방했을 것이라는 성능 증거는 아니다.**
>
> ### 3.4. 판정 보류와 비용 기반 정보 선택은 기존 연구에서 가져오는 방법이다
>
> **선행 연구에서 확인한 내용 — 선택적 판정**
>
> > “optimized over the covered domain”
>
> → 모델이 판정을 내리기로 선택한 대상 집합에서 성능을 최적화한다는 뜻이다.
> - **출처:** Geifman, El-Yaniv, *SelectiveNet*, ICML 2019, 초록. [R4](https://proceedings.mlr.press/v97/geifman19a.html)
> - **직접 확인되는 사실:** 분류와 판정 거부를 함께 학습하고, 오류와 판정 비율의 관계를 평가한다.
> - **본 연구와의 연결:** 판정 보류를 늘려 오류만 낮추는 결과를 방지하기 위해 같은 판정률에서 비교한다.
> - **해석의 한계:** 해당 논문이 API의 실제 업무 권한이나 정책 근거의 충분성을 검증한 것은 아니다.
>
> **선행 연구에서 확인한 내용 — 정보 획득 비용**
>
> > “optimize a trade-off between the expected classification error and the feature cost”
>
> → 분류 오류와 정보를 얻는 비용 사이의 균형을 최적화한다는 뜻이다.
> - **출처:** Janisch, Pevný, Lisý, *Classification with Costly Features Using Deep Reinforcement Learning*, AAAI 2019, 초록. [R5](https://ojs.aaai.org/index.php/AAAI/article/view/4287)
> - **직접 확인되는 사실:** 필요한 정보를 순서대로 요청하거나, 현재 정보로 분류를 종료하는 문제를 다룬다.
> - **본 연구와의 연결:** 모든 정책 사실을 수집하지 않고 필요한 사실을 선택하는 비교 방법의 근거가 된다.
> - **해석의 한계:** 정보 선택에 비용을 적용하는 것만으로 본 연구의 신규성을 주장할 수 없다.
>
> 따라서 차별성 검증은 **API 인가에 특화한 근거의 출처·적용 범위·일관성 검사가 일반적인 정보 선택보다 어떤 이점을 주는지**에 집중한다.

> ## 5. 제안 방법과 검증 계획
>
> ### 제안 방법
>
> **1. 정책의 적용 범위를 먼저 정한다.**
>
> 어떤 조건에서 조회가 허용되는지 규칙의 종류를 확인한다. 예를 들어 소유자·공유 대상·동일 조직 관리자만 허용하는 서비스인지 정한다.
>
> 허용 조건의 종류 자체가 불명확하면, 일부 관계를 확인했다는 이유로 금지를 확정하지 않는다.
>
> **2. 요청·응답과 객체를 연결한다.**
>
> 요청 계정, 테넌트, 객체 종류, 객체 ID, 조회 시점, 응답에서 확인한 보호 데이터를 연결한다.
>
> 같은 숫자 ID라도 테넌트가 다르면 다른 객체로 취급한다. 연결이 불확실하면 보류한다.
>
> **3. 현재 근거로 결론이 결정되는지 검사한다.**
>
> 확인된 사실과 양립하는 정책 상태를 검토한다.
> - 가능한 상태 모두에서 허용되면 허용 근거가 충분하다.
> - 가능한 상태 모두에서 금지되면 금지 근거가 충분하다.
> - 허용·금지 상태가 모두 남아 있으면 추가 확인이 필요하다.
>
> 이 판단은 **사전에 정한 정책 범위 안에서만** 유효하다.
>
> **4. 결론을 바꿀 수 있는 질문을 선택한다.**
>
> 예를 들어 다음 후보 중 현재 사례에 필요한 것을 고른다.
> - 이 객체가 공개 상태인가?
> - 요청자가 명시적인 공유 대상인가?
> - 요청자의 관리 권한이 이 객체의 조직까지 포함하는가?
> - 현재 자료의 정책 버전이 요청 시점에 적용되는 버전인가?
>
> 초기 구현에서는 **허용·금지의 불확실성을 줄일 것으로 예상되는 정도와 확인 비용**을 이용해 선택한다. 해당 계산 원리는 일반적인 정보 선택 방법과 비교하며, 그 자체를 새 알고리즘이라고 주장하지 않는다.
>
> **5. 답변의 근거와 적용 가능성을 확인한다.**
>
> 사실의 값뿐 아니라 출처, 확인 시점, 정책 버전, 적용 객체·조직 범위를 기록한다.
>
> 같은 정책 사실을 여러 사례에 재사용할 수 있지만, 범위와 버전이 맞아야 한다. 정책 정리·매핑에 들인 초기 비용도 비용 평가에 포함한다.
>
> **6. 정책과 실제 관찰을 비교하고 종료한다.**
>
> 충분한 근거를 얻으면 결론을 낸다. 비용 한도에 도달하거나 근거가 충돌하면 보류하고, 필요한 추가 근거를 남긴다.
>
> ### 판정 기준
>
> | 판정 | 필요한 근거 | 관찰 결과 | 근거 부족·충돌 시 처리 |
> | --- | --- | --- | --- |
> | 위반 확정 | 해당 계정·객체·행위에 적용되는 금지 근거 | 대상 보호 데이터가 실제 반환됨 | 보류 |
> | 정상 확인: 허용된 조회 | 적용 가능한 허용 근거와 객체 연결 | 허용된 객체가 정상 반환됨 | 보류 |
> | 정상 확인: 금지된 조회의 차단 | 금지 근거, 완전한 응답 관찰, 차단 판별 기준 | 요청이 차단되고 보호 데이터가 반환되지 않음 | 보류 |
> | 판정 보류 | 정책·연결·응답 중 필요한 근거가 부족하거나 충돌 | 어떤 응답도 가능 | 사유와 필요한 추가 확인 기록 |
>
> `HTTP 200`만으로 위반을 확정하지 않는다. `HTTP 403`만으로 정상 차단을 확정하지도 않는다. 상태 코드와 함께 실제 응답 내용을 확인한다.
>
> 허용된 조회에서 데이터가 나오지 않는 등 기능 장애와 인가 문제를 구분하기 어려운 사례는 별도로 처리한다.

>
> | 비교군 | 역할 | 공정한 비교를 위한 조건 |
> | --- | --- | --- |
> | 계정 교체·응답 비교 | 정책 추가 확인 전의 성능 | 같은 요청·응답·계정 제공 |
> | AuthScope의 공개 자원 제외 절차를 반영한 비교 | 공개 자료 오탐 처리의 기존 효과 | 재구현이면 원 도구 실행과 구분해 표기 |
> | AuthProbe | 명세·다중 계정 기반 객체 조회 진단 | 지원 조건과 초기 객체 입력을 맞추고 버전 고정 |
> | 고정 순서 정책 확인＋단순 규칙 | 제안 방법의 가장 중요한 비교군 | 같은 근거 목록·출처·버전·확인 예산 제공 |
> | 일반적인 비용 기반 정보 선택＋동일 판정기 | 인가에 특화한 선택 절차의 효과 | 같은 사실과 비용을 사용하고 선택 절차만 변경 |
> | 확신도 기반 보류 방법 | 근거 충분성과 점수 기반 보류의 차이 | 동일 입력과 별도 검증 집합으로 임계값 설정 |
> | 전체 정책 제공＋명시적 규칙 | 정보를 충분히 제공했을 때의 성능 기준 | 정책 작성 비용을 포함하고 제한 입력 방법과 단일 순위로 섞지 않음 |
>
> ZAP의 Access Control Testing은 사용자·자원별 `Allowed`, `Denied`, `Unknown` 규칙을 이미 지원한다. 따라서 전체 정책 제공 비교군 또는 적용 가능한 부분의 규칙 기반 비교군으로 활용한다. [T1 공식 문서](https://www.zaproxy.org/docs/desktop/addons/access-control-testing/)
>
> EvoMaster의 오라클은 지원하는 행위와 전제가 다르므로, **조회 전용 범위에 직접 적용되지 않는 검사를 미탐으로 계산하지 않는다.**
>
> **평가에서 고정할 사항**
> - 같은 기본 사례의 변형은 학습·검증·평가 집합에 나눠 넣지 않는다.
> - 임계값과 질문 선택 기준은 평가 집합을 보기 전에 고정한다.
> - 정책이 없는 비교와 일부·전체 정책을 제공한 비교를 분리한다.
> - 근거 출처 확인, 버전 확인, 적응적 질문 선택을 각각 제거하는 비교를 수행한다.
> - 신뢰구간은 같은 기본 사례의 변형을 하나의 묶음으로 취급해 계산한다.
> - 합성 서비스에서의 결과를 실서비스 전반의 성능으로 일반화하지 않는다.
>
> 초기 계획에서는 **위반 재현율 하한 90%**를 사용할 수 있다. 이는 측정 결과나 안전 보장 기준이 아니라 연구 설계상의 제안 값이며, 본 평가 전에 근거와 함께 확정한다.
>
> ### 평가 지표
>
> 정답이 확정된 전체 평가 사례 수를 `N`이라 한다.
> - `TP`: 실제 위반을 위반으로 확정.
> - `FP`: 실제 정상을 위반으로 확정.
> - `FN`: 실제 위반을 정상으로 확인.
> - `TN`: 실제 정상을 정상으로 확인.
> - `UV`: 실제 위반이지만 보류.
> - `UN`: 실제 정상이지만 보류.
>
> 따라서 `N = TP + FP + FN + TN + UV + UN`이다.
>
> | 지표 | 측정 목적 | 계산식·분모 | 보류 사례 처리 |
> | --- | --- | --- | --- |
> | 판정률 | 결론을 낸 범위 확인 | `(TP+FP+FN+TN)/N` | 분모에 포함 |
> | 판정 사례 오류율 | 내린 결론의 정확성 확인 | `(FP+FN)/(TP+FP+FN+TN)` | 직접 포함하지 않으므로 같은 판정률에서 비교 |
> | 잘못된 위반 확정 비율 | 취약점 보고의 신뢰성 | `FP/(TP+FP)` | 판정률·재현율과 함께 제시 |
> | 전체 위반 재현율 | 실제 위반을 얼마나 찾아냈는지 | `TP/(TP+FN+UV)` | **보류한 실제 위반도 분모에 포함** |
> | 잘못된 정상 확인 비율 | 위반을 안전하다고 결론 내리는 위험 | `FN/(FN+TN)` | 위반 보류 비율을 별도 병기 |
> | 정상 예외 오탐률 | 공유·공개·관리자 사례의 오탐 | 해당 집단의 `FP / 실제 정상 사례 수` | 해당 집단의 보류율도 함께 제시 |
> | 정책 확인 비용 | 사람·시스템의 추가 부담 | 총 확인 횟수, 실제 작업 시간, 초기 설정 시간 | 보류까지 지출한 비용도 포함 |
> | 근거 부족 상태의 단정률 | 정보가 부족한데 결론을 낸 정도 | 근거 불충분으로 독립 판정된 사례 중 확정 판정 비율 | 결론이 우연히 맞았어도 별도 기록 |
>
> 분모가 0인 지표는 0%로 표시하지 않고 **계산 불가**로 표시한다.
>
> 판정률은 정책 질문에 사람의 답변이 포함될 수 있으므로 완전 자동화율과 구분한다. 추가 질문 없이 끝난 비율도 별도로 보고한다.
>

> **최종 연구 질문**
>
> > 전체 권한표 없이, 알려진 정책 규칙의 범위와 요청·응답·일부 관계 정보만으로 API 조회의 인가 위반을 어느 범위까지 판정할 수 있으며, 필요한 근거를 선택적으로 확인할 때 오류율·판정률·위반 재현율·정책 확인 비용은 어떻게 달라지는가?
>
> **예상 기여**
> - **방법:** 현재 판정을 위해 부족한 정책 사실을 식별하고, 비용을 고려해 확인하며, 근거 충돌을 기록하는 절차.
> - **평가:** 취약한 조회뿐 아니라 정상 공유·공개·관리자 예외와 잘못된 관계 추론을 포함한 비교 데이터 및 평가 절차.
> - **적용 범위:** 어떤 정책 정보가 없으면 결론을 낼 수 없는지, 어떤 조건에서는 단순 규칙으로 충분한지를 실험적으로 정리.
>
> 단순 규칙과 성능이 같다면 새 판정 알고리즘의 우월성을 주장하지 않는다. 그 경우에도 **입력 확보의 한계나 기존 평가 방식의 문제를 재현 가능하게 보여주는 결과**가 있는지 별도로 판단한다.
>
> **남은 불확실성**
> - 실제 서비스에서 독립적인 정책 근거를 어느 정도 확보할 수 있는가?
> - 소유·공유·역할 관계를 확인하는 실제 비용은 얼마인가?
> - 알려진 정책 규칙 밖의 예외를 어떻게 발견하거나 보류할 것인가?
> - 제안 방법의 효과가 추가 정보를 받은 효과와 구분되는가?
> - 기존 비용 기반 정보 선택보다 인가에 특화한 처리가 나은가?
> - 정상 반례를 포함했을 때 기존 도구의 성능 평가가 실제로 달라지는가?
> - 더 가까운 후속 연구와 구현이 있는지 추가 문헌 검토가 필요한가?

# 필요한 정책 근거를 선택적으로 확인하는 API 인가 진단

Notion에 작성한 **2번 가설**을 정리한 문서다. 통합 조사 보고서에서는 같은 주제를 H1로 부른다.

## 가설

소유자·공유 대상·공개 여부·관리자 권한을 처음부터 전부 조사하지 않고, **현재 요청의 권한을 판단하는 데 필요한 정보부터 확인한다.** 충분한 근거가 모이면 판정하고, 끝까지 확인하지 못한 요청은 보류한다.

이 방식은 같은 위반 재현율과 판정률, 오류 조건을 맞추는 데 필요한 확인 비용을 고정 순서나 일반적인 정보 선택 방식보다 줄일 수 있다.

여기서 비용은 사람의 확인 작업시간을 중심으로 측정한다. 질문 수, API 호출 수, 계산시간도 함께 기록한다. 서로 다른 단위를 한 값으로 더하지 않는다.

추가로, 다른 조직이나 다른 시점의 근거를 잘못 사용하는 문제도 확인한다. **질문을 잘 고르는 효과**와 **잘못된 근거를 걸러내는 효과**는 별도 실험으로 나눈다.

## 필요한 이유

다른 계정으로 조회가 성공했다고 해서 항상 권한 위반은 아니다. 공개 객체이거나, 공유받은 객체이거나, 해당 조직의 관리자라면 정상적인 조회일 수 있다. Sahin 등의 연구도 이런 예외 때문에 단순한 교차 계정 접근 규칙이 오탐을 만들 수 있다고 설명한다 [1].

이를 구분하려면 서비스가 허용하는 규칙과 요청자의 실제 관계를 알아야 한다. 그런데 모든 사용자와 객체의 권한 관계를 미리 조사하면 준비할 정보가 많아진다. 실제로 얼마만큼의 부담이 생기는지는 이번 연구에서 측정해야 한다.

예를 들어 관리자가 조회할 수 있는 객체라면, 요청자가 해당 조직의 관리자라는 사실만으로 허용을 판단할 수 있는 경우가 있다. 이때 소유자와 전체 공유 목록까지 확인할 필요가 있을까? 반대로 금지된 조회를 확정하려면 여러 허용 예외가 모두 해당하지 않는다는 근거가 필요할 수 있다.

그래서 **어떤 정보를 먼저 확인하면 빨리 판정할 수 있는지**, **정보를 얻지 못했을 때 어디까지 판단할 수 있는지**를 함께 조사하려는 것이다.

## 직접적인 선행논문

누락된 속성값이 있을 때 가능한 권한 결론을 평가한다.
- **Morisset, Willemse, Zannone — Cybersecurity 2019** [3]*A framework for the extended evaluation of ABAC policies*

가능한 속성값의 제약과 각 속성이 권한 결론에 미치는 영향을 다룬다.
- **Morisset, Ravidas, Zannone — FPS 2019, 출판 2020** [4]*On Attribute Retrieval in ABAC*

속성을 가져오는 과정의 오류와 취득 방법 선택을 다룬다.
- **Deshpande, Hellerstein, Kletenik — SODA 2014** [5]*Approximation Algorithms for Stochastic Boolean Function Evaluation and Stochastic Submodular Set Cover*

비용이 드는 정보를 어떤 순서로 확인해야 알려진 논리식의 답을 얻을 수 있는지 다룬다.
- **Zong, Lehtonen, Rintanen — 2026 프리프린트** [6]*Cost-Optimal Decision Diagrams for Stochastic Boolean Function Evaluation*

복합 논리식과 결합분포를 대상으로 비용 최적 결정 전략을 탐색한다.
- **Zhang, Fong — 2023 제출 프리프린트** [7]*Quantifying Policy Administration Cost in an Active Learning Framework*

정책 관리 과정에서 사람에게 하는 질문과 관리 부담을 다룬다.

## 차이점

정보가 부족할 때 보류하거나, 필요한 질문을 골라 비용을 줄이는 개념에는 위와 같은 선행연구가 있다. 이번 주제는 그 방법을 **실제 API 조회의 인가 진단에 적용했을 때 생기는 근거 확인 비용과 실패**에 초점을 둔다.

확인할 차이는 다음 세 가지다.
1. 검사 대상 API의 응답과 별도로 소유·공유·조직 권한을 확인할 수 있는가?
1. 자료를 가져오는 비용뿐 아니라 올바른 조직·객체·시점의 자료인지 검토하는 비용까지 포함해도 이점이 남는가?
1. 근거가 없거나 서로 충돌할 때, 실제 위반을 얼마나 보류하게 되는가?

이 차이가 학술적 기여가 되려면 기존 방법과 같은 입력으로 비교하고, 실제로 중요한 조건에서 차이가 나타나는지 보여줘야 한다.

## 주제 정의

> 서비스의 읽기 권한 규칙은 알고 있지만 개별 객체의 소유·공유·역할 관계는 일부만 아는 상황을 대상으로 한다. 다음에 확인할 정보를 선택하는 진단 방법을 만들고, 같은 위반 재현율·판정률·오류 조건을 달성하는 데 필요한 확인 비용과 근거 확보 실패를 측정한다.

예를 들어 “소유자, 공유받은 사용자, 공개 객체를 읽는 사용자, 해당 조직의 관리자는 조회할 수 있다”는 규칙은 미리 검토한다. 대신 모든 객체에 대해 그 조건의 참·거짓을 미리 채워 놓지는 않는다.

어떤 예외가 허용되는지조차 모르는 서비스는 이 실험의 기본 대상에 넣지 않는다. 정책 규칙을 알아내는 연구와, 알려진 규칙에 필요한 사실을 확인하는 연구는 구분한다 [8].

## 근거 정리

### 1. 정보가 빠져 있어도 결론을 낼 수 있는 경우가 있다

Crampton 등의 연구는 빠진 속성값을 보완했을 때 나올 수 있는 권한 결론을 다룬다 [2]. Morisset 등의 후속 연구는 가능한 값의 제약과 결론에 영향을 주는 속성을 다룬다 [3].

예를 들어 “공개 객체는 누구나 조회할 수 있다”는 정책이 있고 공개 상태가 확인됐다면, 소유자와 공유 대상이 누구인지 몰라도 허용 결론이 유지될 수 있다. 금지 규칙이 우선하는 서비스라면 그 규칙도 함께 확인해야 한다.

이 원리를 공통 판정 기준으로 사용한다. 정보가 덜 채워졌다는 이유만으로 무조건 보류하지 않고, **남은 가능성이 결론을 바꾸는지** 확인하는 것이다.

### 2. 어떤 질문을 먼저 할지 고르는 문제에도 직접 선행이 있다

SBFE는 규칙을 이미 알고 있고 개별 사실을 확인하는 데 비용이 드는 상황을 다룬다 [5]. 이번 주제와 가까운 문제다. 최근 연구에서는 복합 논리식과 사실 간 상관까지 고려한다 [6].

따라서 “필요한 질문을 먼저 한다”는 아이디어 자체를 새 기여로 내세우기는 어렵다. 기존 비용 순서와 정보 이득 방식, 작은 문제에서 계산한 최적 전략을 비교 기준으로 삼아야 한다.

이번 시제품에서는 **이번 질문으로 판정이 끝날 가능성을 예상 확인 비용으로 나눈 값**을 우선 사용한다. 어떤 질문도 즉시 판정을 끝낼 수 없다면, 허용·금지 사이의 불확실성을 더 줄이는 질문을 고른다. 답변 성공률과 비용은 개발 자료에서 추정한다. 평가 정답을 질문 순서에 사용하지 않는다.

정확한 선택 규칙과 예외 처리는 [상세 연구계획의 5절](https://app.notion.com/p/H1-%EC%84%A0%ED%83%9D%EC%A0%81-%EC%A0%95%EC%B1%85-%EA%B7%BC%EA%B1%B0-%EC%9D%B8%EA%B0%80-%EC%A7%84%EB%8B%A8-%EC%B6%94%EA%B0%80%EC%A1%B0%EC%82%AC-%EA%B0%9C%EC%A0%95%EC%95%88.md#5-%EC%A0%9C%EC%95%88-%EC%A0%88%EC%B0%A8%EC%99%80-%EA%B5%AC%EC%B2%B4%EC%A0%81-%EC%84%A0%ED%83%9D-%EA%B7%9C%EC%B9%99)에 정리했다. 현재 규칙은 비교해 볼 후보이며, 최적성을 보장하는 알고리즘으로 제시하지 않는다.

### 3. 정보를 가져오는 과정에서도 오류와 비용이 생긴다

*On Attribute Retrieval in ABAC*는 속성 취득 과정의 오류가 정책 평가에 미치는 영향과 취득 방법 선택을 다룬다 [4]. 정책 관리 비용 연구는 사람에게 하는 질문을 비용으로 모델링한다 [7].

실제 API 진단에서는 같은 이름의 객체라도 조직이 다를 수 있고, 조회 후 공유 관계가 바뀔 수 있다. 관리자 화면에 자료가 있다는 사실만으로 그 자료가 검사 대상 요청에 적용된다고 볼 수는 없다.

또한 “공유 목록에 B가 없다”는 판단에는 목록을 끝까지 확인했는지, 필터나 페이지 누락은 없는지 검토가 필요하다. 이 확인 시간도 비용에 넣는다.

같은 출처에서 여러 사실을 함께 얻거나 자료를 재사용하는 경우에도 비용을 기록한다. 공동 비용을 다루는 선행연구가 있으므로 [13], 묶음 조회나 캐시를 제안 방법에만 제공해서 성능 차이를 만들지 않는다.

### 4. 모르는 값은 거짓 값과 다르다

Bui와 Stoller는 속성이 실제로 없는 경우와 값을 모르는 경우를 구분해 정책을 학습한다 [9]. 이 구분은 진단에서도 필요하다.

공유 여부를 확인하지 못했다고 해서 “공유받지 않았다”로 처리하면 정상 조회를 위반으로 판단할 수 있다. 모르는 값은 그대로 미확인 상태로 둔다.

같은 사실에 서로 다른 값이 제시되면 기존 채택값을 철회하고 다시 미확인으로 둔다. 그 사실의 값이 어느 쪽이어도 결론이 같으면 판정할 수 있다. 결론이 달라지거나 정책 규칙 자체가 충돌하면 보류한다.

### 5. 기존 API 진단도 정책 입력과 정상 예외를 고려한다

Sahin 등의 연구는 관리자처럼 정상적인 교차 계정 접근이 있다는 점을 고려한다 [1]. ZAP도 사용자별 허용·금지·미확인 규칙과 URL 트리의 규칙 상속을 제공한다 [10].

AuthProbe는 목록 조회를 통해 객체 관계를 찾거나 명시적인 초기 객체를 입력받는다. 저자는 목록이 관계를 제대로 표현하는지와 테스트 객체 확보를 적용 한계로 설명한다 [11].

따라서 기존 도구가 모두 응답 코드만 보거나 모든 객체의 권한표를 일일이 작성하게 한다고 설명하면 비교가 부정확해진다. 실제 지원 기능을 반영한 상태에서 **독립 근거의 확보와 검증에 얼마가 드는지** 비교해야 한다.

### 6. 최근 사고는 진단의 필요성을 보여준다

개인정보위의 2026년 7월 자료는 로그인 여부만 확인하고 데이터 조회 권한을 확인하지 않는 문제와 구버전 API를 통한 조회 사례를 소개한다 [12].

이 자료는 객체 권한을 점검해야 하는 이유다. 질문 선택 방식의 비용 절감 효과나 사고 예방률은 이번 실험에서 별도로 확인해야 한다.

## 실제로 어떻게 판정할까

아래는 설명용 예시다. 실행 결과는 아니다. 정책은 “소유자·공유받은 사용자·공개 객체의 조회자·해당 조직 관리자에게 조회를 허용한다”로 정했다고 하자.

| 확인한 정보 | 실제 응답 | 판정 |
| --- | --- | --- |
| 요청자가 해당 조직의 관리자임을 확인 | 대상 객체가 반환됨 | 정상 허용. 나머지 관계는 결론에 필요하지 않을 수 있음 |
| 소유자 아님·공유받지 않음·공개 아님·해당 조직 관리자 아님을 모두 확인 | 대상 객체가 반환됨 | 권한 위반 |
| 공개 아님·소유자 아님만 확인. 공유·관리자 여부는 모름 | 대상 객체가 반환됨 | 보류. 정상 예외가 남아 있음 |
| 조회 당시 관계를 확인할 수 없음 | 대상 객체가 반환됨 | 보류. 현재 관계로 과거 권한을 대신 판단하지 않음 |

HTTP 200만으로 대상 데이터가 실제 반환됐다고 판단하지 않는다. 응답 내용과 객체 식별을 확인한다. 거부 응답도 정상 인증 상태와 서비스 계약을 함께 확인한다.

진단 흐름은 다음과 같다.
1. 검토된 정책과 현재 확보한 근거를 읽는다.
1. 남은 사실의 값에 따라 허용·금지 결론이 달라지는지 확인한다.
1. 달라진다면 다음에 확인할 정보와 출처를 고른다.
1. 답변의 객체·조직·정책 버전·조회 시점이 맞는지 검토하고 반영한다.
1. 결론이 정해지면 판정한다. 예산이나 확인 경로를 소진했는데도 결론이 남으면 보류한다.

## 비용이 줄지 않는 경우도 있다

다음처럼 네 조건 중 하나라도 참이면 허용하는 정책을 생각해 보자.

```
소유자 OR 공유받은 사용자 OR 공개 객체 OR 해당 조직 관리자
```

네 조건이 실제로 모두 거짓이고, 각각을 별도로 조회해야 하며, 다른 제약이나 재사용 정보가 없다면 금지를 확정하려고 네 가지를 전부 확인해야 한다. 확인하지 않은 조건이 하나라도 남으면 그 조건이 참인 정상 조회 가능성이 남기 때문이다.

**이 경우에는 질문 순서만 바꿔 취득 비용을 줄일 수 없다.**

반대로 어떤 허용 조건이 참이면 그것을 먼저 확인해 일찍 끝낼 수 있다. 그래서 정상 조회를 빨리 판정한 효과와 실제 위반을 적은 비용으로 찾은 효과를 나눠 봐야 한다. 이 구분도 SBFE의 충분 근거와 순차 검사 문제에 연결된다 [5].

## 실험 계획

### 무엇과 비교할까

| 비교 방법 | 확인할 점 |
| --- | --- |
| 정해진 순서대로 확인 | 단순한 실무 절차보다 이점이 있는가 |
| 예상 확인 비용이 낮은 순서 | 복잡한 선택 없이도 같은 결과를 얻는가 |
| 결론의 정보 이득/비용으로 선택 | 일반적인 정보 선택보다 이점이 있는가 |
| 정책에 영향을 크게 주는 사실부터 확인 | 속성 영향 연구를 바탕으로 한 선택과 어떻게 다른가 [3] |
| 작은 정책의 정확한 최적 전략 | 최적 비용과 얼마나 차이가 나는가 [5, 6] |
| 필요한 사실을 전부 확인 | 준비·검토 비용까지 포함했을 때 선택적 확인의 차이는 무엇인가 |

모든 방법에 같은 정책, 초기 정보, 출처 접근권, 검증 절차, 예산, 재사용 기능을 제공한다. 작은 문제의 정확한 최적 전략보다 낮은 기대 비용을 낸다고 주장하지 않는다.

### 실험을 세 가지로 나눈다
1. **질문 선택 실험**

참이고 적용 가능한 근거를 제공하고 질문 선택 방식만 바꾼다. 같은 판정 목표에 도달하는 비용을 비교한다.
1. **근거 검증 실험**

같은 선택 방식과 원자료를 사용하되 잘못된 조직·버전·시점의 근거를 검증하는 절차를 켜고 끈다. 잘못된 확정, 추가 비용, 실제 위반의 보류를 측정한다.
1. **실제 취득 실험**

사람이 자료를 찾아 확인하는 시간과 확보 실패를 측정한다. 미리 준비한 답변을 꺼내 보여주는 실험만으로 실제 사람의 작업시간이 줄었다고 결론 내리지 않는다.

### 무엇을 측정할까
- **확인 비용:** 준비·자료 취득·검토·충돌 해결·질문 선택의 능동 작업시간. 시스템 비용과 대기시간은 별도로 기록한다.
- **판정률과 보류율:** 전체 검사 사례 중 결론을 낸 비율과 남긴 비율.
- **전체 위반 재현율:** 실제 위반 중 찾아낸 비율. 보류한 실제 위반도 분모에 넣는다.
- **오탐과 정상 오확정:** 정상 조회를 위반으로 판단한 경우와 실제 위반을 정상으로 판단한 경우를 따로 센다.
- **근거 확보 실패:** 필요한 자료가 없거나, 답변받지 못하거나, 적용 범위를 확인하지 못한 비율.

평가 전에 목표 재현율·판정률과 허용 오류, 최대 예산을 정한다. 기록된 비용별 결과에서 목표를 처음 함께 달성한 비용을 비교한다. 이 계산은 평가자가 정답을 가지고 사후에 하며, 진단기의 질문 선택에는 정답을 제공하지 않는다.

예산 끝까지 목표에 도달하지 못한 방법도 결과에 남긴다. 성공한 조건만 골라 평균내지 않고 목표 달성률, 전체 비용 곡선과 최종 오류도 함께 보여준다.

### 정답은 어떻게 만들까

업무 정책과 초기 소유·공유·역할 상태를 API 구현과 별도로 작성한다. 그 정책에 비춰 실제 응답이 허용된 것인지 평가자가 확인한다.

현재 데모의 진단기와 모의 API는 같은 `domain.policy_for`를 사용한다. 이 구조만으로 실험 정답의 독립성을 확보했다고 볼 수 없다. 별도로 검토한 참조표와 판정 구현을 두고 공유 오류를 점검해야 한다.

먼저 24개 기본 사례로 질문 경로와 정답을 만들 수 있는지 확인할 계획이다. 같은 사례에서 근거를 가리거나 충돌을 넣은 파생본은 하나의 사례군으로 묶는다. 본 실험의 360개 기본 사례도 아직 계획 규모다. 정책 구조와 앱 구현을 분리해 평가하고, 같은 사례의 파생본을 학습과 평가에 나누어 넣지 않는다.

## 선행연구 공백과 남는 연구 질문

조사한 선행연구에는 누락 속성 평가 [2, 3], 속성 취득 오류 [4], 질문 비용과 최적 순서 [5–7], 미확인 값의 정책 학습 [9]이 있다. 기존 API 도구도 정상 예외와 정책 입력을 고려한다 [1, 10, 11].

이번 실험에서 남겨 둘 질문은 다음과 같다.
- 실제 API 진단에 필요한 독립 근거를 얼마나 확보할 수 있는가?
- 출처·조직·시점 검증을 포함해도 선택적 확인의 비용 이점이 남는가?
- 어떤 정책에서는 단순 순서로 충분하고, 어떤 조건에서 추가 선택이 유리한가?
- 근거를 확보하지 못할 때 실제 위반은 얼마나 보류되는가?

비용 순서나 일반 정보 선택과 차이가 없다면 선택 알고리즘의 우월성 주장을 줄인다. 실제 위반은 더 많이 놓치고 정상 조회만 빨리 처리했다면 주가설을 지지하는 결과로 보지 않는다.

연구의 기여는 이런 조건을 독립 정답과 취득 기록으로 보여주는 데서 나올 수 있다. 현재는 문헌 조사와 연구 설계 단계이며, 비용 절감·실제 적용률·학술적 신규성은 아직 실험으로 확인하지 않았다.
