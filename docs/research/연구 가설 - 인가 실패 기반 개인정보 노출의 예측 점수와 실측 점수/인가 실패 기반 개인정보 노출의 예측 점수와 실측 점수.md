# 인가 실패 기반 개인정보 노출의 예측 점수와 실측 점수

# 연구 가설: 인가 실패 기반 개인정보 노출의 예측 점수와 실측 점수

> 팀: AP-EYE (심재훈, 임성빈, 양유상, 곽민경)
> 최신화: 2026-09-30 (딥리서치 반영 · 차별점 문장 수정)

---

## 1. 가설

**타인 데이터를 조회하지 않고 산정한 "예측 노출 점수"는, 실제로 타인 토큰을 재전송해 확인한 "실측 노출 점수"의 우선순위를 충분히 재현한다. 따라서 재전송이 어려운 운영 환경에서도 예측 점수만으로 인가 실패의 대응 우선순위를 정할 수 있으며, 두 점수가 어긋나는 경우는 결함 유형을 진단하는 신호가 된다.**

## 2. 필요성

인가 실패를 확인하는 표준 방법은 다른 계정 토큰으로 재전송해 타인 데이터가 나오는지 보는 것이다. 그러나 운영 서비스에서 타인 데이터를 끌어오는 재전송은 법적·윤리적 부담이 커서 함부로 할 수 없다. 재전송 없이 "뚫리면 무엇이 얼마나 샐지"를 예측할 수 있고, 그 예측이 실측과 맞는다는 것이 검증되면 운영 환경에서도 안전하게 위험 우선순위를 매길 수 있다.

## 3. 가장 직접적인 선행논문

### ① Pan, Cohney, Murray, Pham. "EDEFuzz: A Web API Fuzzer for Excessive Data Exposures." ICSE 2024.
- **무엇을 했나**: 웹 API가 화면에 필요 없는 데이터까지 응답에 담아 보내는 "과다 노출(Excessive Data Exposure)"을 자동으로 찾는 최초의 퍼징 도구. 응답의 필드를 하나씩 지워서 재생한 뒤, 클라이언트 화면(DOM 트리)이 바뀌는지 원본과 비교한다. 화면에 아무 영향이 없으면 그 필드는 불필요하게 노출된 것으로 판정한다(변형 관계, metamorphic relation 활용).
- **결과**: Alexa 상위 200개 중 대상 가능한 69개에서 33,365개의 잠재 노출 필드를 찾았고, 통제 실험(호주 인기 웹사이트 8개)에서 참양성률 98.65%를 기록했다.
- **우리와 같은 점**: 응답을 **필드 단위로 비교**해 노출을 판정한다는 접근이 동일하다.
- **우리와 다른 점 (빈칸)**: (1) "화면에 안 쓰이니 불필요"만 판정하고, 그 필드가 **얼마나 민감한지·몇 명분이 샐지는 점수화하지 않는다.** (2) 한 번에 **하나의 API만** 대상으로 한다. (3) **인가 실패(타인 데이터 접근) 자체는 다루지 않는다** — 정상 사용자 응답의 불필요 필드만 본다.
- **AP-EYE의 위치**: EDEFuzz의 필드 단위 비교 아이디어를 빌리되, 판정 기준을 "불필요 여부"에서 "**민감도 × 규모**"로 바꾸고, 인가 실패 맥락(소유자 vs 타인 응답)에 적용한다.

### ② "The Tragedy of Convenience: Cascading User-Data Leakage from SMS-Delivered URLs." arXiv 2601.09232, 2026.
- **무엇을 했나**: 문자(SMS)로 전송되는 URL에 담긴 식별자가 예측 가능할 때, 한 사용자의 URL만 알아도 이웃 URL을 추측해 **다른 사용자들의 개인정보까지 연쇄적으로 새는** 문제를 실제 서비스에서 분석했다. 토큰이 `123456-AB` 형태의 순차 식별자임을 확인했다.
- **결과**: 한 서비스에서 순차 식별자를 선형으로 훑기만 해도 **최소 65만 명의 개인정보(PII)가 드러날 수 있다**고 밝혔다.
- **우리와 같은 점**: 순차·예측 가능 식별자가 **노출 규모를 좌우한다**는 문제의식이 동일하다. 노출이 개인정보로 이어진다는 점도 같다.
- **우리와 다른 점 (빈칸)**: 저자들은 실제 규모가 "식별자 공간 안의 유효 사용자 밀도"에 달렸다고 지적하면서도, **그 밀도를 추정하거나 대규모 열거로 확인하는 것은 "자동 토큰 변조와 대량 요청이 필요해 윤리적으로 부적절하다"며 명시적으로 시도하지 않았다.** 즉 규모 추정을 **의도적으로 공백으로 남겼다.**
- **AP-EYE의 위치**: 이 논문이 윤리 문제로 비워 둔 바로 그 지점을 메운다. **German Tank 추정으로 관찰된 ID만(대규모 열거 없이) 규모를 예측**하고, 통제된 격리 환경(crAPI·VAmPI)에서만 실제 레코드 수와 대조해 예측 정확도를 검증한다.

## 4. 기존 연구와 다른 점

실행 전 예측을 실측과 대조하는 방법론 자체는 인접 분야(DB 결합의 재식별 위험 방향 예측, CVE 영향 유형 예측)에 이미 존재한다. 그러나 **API 인가 실패로 노출될 개인정보의 규모와 내용을 재전송 없이 예측하고, 격리 환경 실측과 대조해 정확도를 검증한** 사례는 없다.

## 5. 선행연구 검토 

가설을 네 부분으로 나눠 각각 직접 관련 논문을 검색하고, 반증 사례(실행 전 예측을 실측과 대조한 연구)를 찾았다.

### (A) 재전송 없이 노출 판정 — EDEFuzz

**여기까지 풀었다**: EDEFuzz(ICSE 2024)는 응답 필드를 하나씩 지워 클라이언트 화면(DOM) 변화를 비교하는 변형 관계로, 화면에 영향 없는 불필요 노출 필드를 찾는다. Alexa 상위 200개 중 69개에서 33,365개의 잠재 노출을 찾았고, 통제 실험에서 참양성률 98.65%.

**부족한 점**: "UI에 안 쓰이니 불필요"만 판정. 필드가 얼마나 민감한지, 몇 명분이 샐지는 점수화하지 않음. 한 번에 하나의 API만, 인가 실패는 다루지 않음.

**우리가 채울 부분**: 필드 단위 비교 아이디어를 빌리되 "불필요 여부"가 아니라 "민감도 × 규모"로 점수화하고 인가 실패 맥락에 적용.

### (B) 노출 규모 추정 — SMS URL, WhatsApp 열거, German Tank

**여기까지 풀었다**:
- SMS URL 연구(2026): 순차 식별자로 연쇄 노출되는 문제를 분석. 한 서비스에서 선형 스캔으로 최소 65만 명 노출 가능이라고 밝힘.
- WhatsApp 열거 연구(2026): 실제로 30억 계정을 열거해 규모 실측이 가능함을 보임.
- German Tank 추정: 순차 번호 k개·최댓값 m으로 전체 개수를 N̂ = m(1+1/k)−1로 추정.

**부족한 점**: SMS URL 연구는 규모가 식별자 공간의 유효 사용자 밀도에 달렸다고 지적하면서도 "대규모 요청이 필요해 윤리적으로 부적절하다"며 밀도 추정을 명시적으로 포기. WhatsApp은 실측했으나 실제 대규모 열거를 수행(비침투 아님). German Tank는 보안·API 적용 사례 없음.

**우리가 채울 부분**: German Tank로 관찰된 ID만(대규모 열거 없이) 규모를 예측하고, 격리 환경에서만 실제 레코드 수와 대조. SMS URL 연구가 윤리 문제로 비워 둔 지점.

### (C) 실행 전 예측을 실측과 대조 — 인접 사례 (반증 검토)

**여기까지 풀었다**:
- **Uniqueness ratio predictor** (arXiv 2601.11550, 2026): 두 데이터셋 결합을 **실행하지 않고** 사전 고유성 값만으로 재식별 위험의 **방향**을 예측하고, 정답과 대조해 정확도를 측정. "실행 전 예측 → 정답 대조" 구조가 우리와 동일.
- **TRIAGE** (arXiv 2508.18439, 2026): CVE 설명으로 영향 유형을 예측하고 ground truth와 대조.

**부족한 점 (우리와의 차이)**:
- Uniqueness ratio는 대상이 **DB 결합**이고, 재식별 **방향**만 예측한다. 개인정보 노출의 규모·내용도, API 인가 실패도 아니다.
- TRIAGE는 대상이 **CVE 메타데이터**다. 노출 규모·내용이 아니다.
- 두 논문 모두 방법론(실행 전 예측 → 실측 대조)은 같지만, **적용 대상이 다르다.**

**우리가 채울 부분**: 이 방법론을 **API 인가 실패의 개인정보 노출 규모·내용**에 처음 적용한다. Uniqueness ratio 논문은 "실행하지 않고 사전 값만으로 위험을 추론"하는 접근이 학계에서 유효함을 보인 **방법론적 근거**로 인용한다.

### (D) 심각도 정량화 (점수 구조의 뿌리)

**여기까지 풀었다**: L-Severity(JCS 2016), M-Score(TDSC 2012)는 유출 심각도를 민감도 × 식별성 × 레코드 수로 정량화. ToolMinimize(2026)는 이를 LLM 에이전트에 자동 적용.

**부족한 점**: 전부 DB·에이전트 대상의 사후 측정. L-Severity의 식별성·규모 계산은 DB 전체 접근을 전제해 블랙박스 API에 적용 불가. ToolMinimize는 필드 조합 효과를 모델링하지 않았다고 스스로 명시.

**우리가 채울 부분**: 점수 구조를 차용하되 세 요소를 블랙박스 API 응답만으로 추정하고, 조합 효과를 식별성에 반영.

### 5-종합: 우리는 이 부분이 부족하다고 본다

| 구성요소 | 가장 가까운 연구 | 그 연구가 안 한 것 |
| --- | --- | --- |
| 필드 단위 노출 판정 | EDEFuzz (ICSE 2024) | 민감도·규모 점수화 없음, 인가 실패 대상 아님 |
| 노출 규모 추정 | SMS URL (2026) | 윤리 문제로 규모 추정 포기 |
| 규모 실측 | WhatsApp 열거 (2026) | 대규모 열거 수행 (비침투 아님) |
| **실행 전 예측 vs 실측 대조** | **Uniqueness ratio (2026), TRIAGE (2026)** | **DB 결합·CVE 대상. 개인정보 노출 규모·내용에 적용 안 됨** |
| 심각도 정량화 | L-Severity (2016) | DB 전제, 사후 측정 |

네 조각이 각기 다른 논문에 흩어져 있고, **이를 "재전송 없는 예측 → 격리 환경 실측 대조"로 합쳐 API 인가 실패의 개인정보 노출에 적용한 연구는 없다.**

## 6. 두 점수의 정의

### 점수 공식

`노출 점수 = E(악용 가능성) × Σ_카테고리 [ S(민감도) × log(N, 규모) ] × I(식별성)`

### 공식의 출처

이 공식은 특정 한 논문의 것을 그대로 쓴 것이 아니라, 검증된 유출 심각도 정량화 연구들의 요소를 **API 인가 실패에 맞게 재구성**한 것이다.

| 부분 | 출처 | 원문에서의 형태 |
| --- | --- | --- |
| Σ[ S × 규모 ] 골격 | **L-Severity** (Vavilis et al., JCS 2016) | 유출 심각도 = Σ(레코드별 민감도 × 식별 인자). 우리 공식의 뼈대 |
| I 식별성 | L-Severity의 distinguishing factor + **M-Score** (TDSC 2012) | 준식별자 조합으로 재식별 가능성을 나타내는 [0,1] 가중치 |
| log(N) 로그 규모 | **Breach Risk Magnitude** (Yasnoff, AMIA 2016) | BRM = log₁₀(접근 가능 레코드 수 ÷ 인증 단계 수) |
| E × 심각도 구조 | **Vavilis et al.** (Computers & Security 2015) | 위험 = 이상 확률 × 심각도 |

**정리**: L-Severity의 심각도 구조를 원본으로 삼아, (1) 규모 항을 BRM처럼 로그로 바꾸고, (2) 앞에 Vavilis 2015의 악용 가능성 E를 곱한 형태다.

**표현 주의 (심사 대비)**: "L-Severity 공식을 사용한다"가 아니라 "**L-Severity의 민감도×식별성×규모 구조를 차용하고, BRM의 로그 스케일과 Vavilis 2015의 악용 가능성 항을 결합해 API 인가 실패에 맞게 재구성한다**"로 기술한다. 우리 고유 기여는 이 세 요소를 **블랙박스 API 응답만으로 추정**한다는 점과, 예측·실측 두 시점으로 분리한다는 점이다.

**⚠️ 확정 전 검증 (L-Severity 2차 정독)**: 원문 공식과 나란히 대조해 다음 두 가지를 확인해야 한다.
- 원문의 Σ가 레코드 단위 합인지 카테고리 단위 합인지 (우리는 카테고리 단위로 쓰려 함 → 차이 지점)
- distinguishing factor의 정확한 값 범위·계산법 (우리 I와 대조)

### 예측 점수 vs 실측 점수

| 요소 | 예측 점수 (재전송 전) | 실측 점수 (재전송 후) | 요소 출처 |
| --- | --- | --- | --- |
| E 악용 가능성 | ID 형식으로 추정 (순차/UUID) | 재전송으로 실제 확인 | Vavilis 2015 |
| S 민감도 | 소유자 응답 필드 | 타인 응답 필드 | L-Severity |
| I 식별성 | 소유자 응답의 필드 조합 | 타인 응답의 필드 조합 | L-Severity, M-Score |
| N 규모 | German Tank 비침투 추정 | 격리 환경 실제 레코드 수 | German Tank, BRM |
| 타인 데이터 접근 | 안 함 → 운영 환경 가능 | 함 → 격리 환경 전용 | AuthProbe 윤리 설계 |

**두 점수가 달라지는 지점**
- E와 N은 정보원이 달라 실질적으로 달라질 수 있고, 이 차이가 예측 정확도 검증의 핵심이다.
- S·I는 인가 실패가 있으면 대부분 같은 것이 정상이라, 어긋나면 오차가 아니라 결함 유형 신호로 해석한다.

| S·I 비교 | 해석 |
| --- | --- |
| 예측 ≈ 실측 | 권한 확인 없이 객체 전체 노출 |
| 예측 > 실측 | 서버가 타인에게 일부 필드 가림 (부분 방어) |
| 예측 < 실측 | 타인에게 더 많이 줌 (과다 노출 버그) |

## 7. 검증 방법

| 항목 | 방법 |
| --- | --- |
| 우선순위 재현도 | 예측 점수 순위 vs 실측 점수 순위 상관 (Spearman, Kendall τ) |
| 규모 예측 정확도 | German Tank 추정치 vs 실제 레코드 수 오차, 관찰 ID 수에 따른 변화 |
| 악용 가능성 예측 | ID 형식 기반 예측 vs 재전송 결과 일치율 |
| 불일치 진단 | S·I 불일치를 부분 방어/과다 노출로 분류, 실제 결함과 대조 |
| 실용성 | 예측 상위 N%만 재전송했을 때 실측 고위험을 몇 % 잡는지 |
| 기준선 대비 | 고정 등급(AuthProbe식)·Bugcrowd VRT와 우선순위 구분력 비교 |

## 8. 해결 가능성
- **정답 있는 환경**: crAPI·VAmPI는 개인정보 필드와 전체 레코드 수를 알 수 있어 예측·실측을 모두 정답과 대조할 수 있다.
- **윤리 분리**: 예측은 타인 데이터에 손대지 않고, 실측은 격리 환경에서만 수행한다. SMS URL·WhatsApp 연구가 안았던 윤리 부담을 피한다.
- **방법론 선례**: Uniqueness ratio 연구가 "실행 전 사전 값만으로 위험을 추론"하는 접근의 타당성을 이미 입증했다.
- **구현 범위**: EDEFuzz(코드 공개)의 필드 비교, German Tank 공식(교재 수준)을 그대로 활용하고, 연구 역량은 두 점수의 산정·대조에 집중한다.
