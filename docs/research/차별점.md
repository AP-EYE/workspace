# 차별점

1. **인가 위반과 실제 개인정보 노출 범위를 연결한다는 점**
    Microsoft의 API 보안 속성 검사는 자원 접근이 보안 규칙을 지키는지를 다룹니다. 우리 설계는 여기에 **실제 반환된 개인정보와 정보주체별 관측 집계**를 연결합니다.

    예를 들어 우리 시스템이 제공하려는 결과는 다음과 같습니다.

    > “지수에게 민수의 정보를 제공하지 않는다는 정책이 있는데, 회원 API에서는 이름이, 상담 API에서는 상담 내용이 반환되었다. 두 응답은 같은 조직의 같은 회원에 관한 것으로 확인되며, 각각의 증거 기록은 이것이다.”

    이렇게 **요청자 → 업무 정책 → 실제 응답 → 정보주체 → 반환 항목 → 증거**를 연결하는 것이 프로젝트의 중심입니다. 사전 진단과 사후 조사도 이 기록을 함께 활용합니다.

    **현재 확인되는 것은 이러한 분석 구조입니다.** 연구 기여로 만들려면 여러 API에 흩어진 노출을 더 정확하게 집계하고, 조사자가 확인해야 하는 기록이나 시간을 줄이는지 측정해야 합니다.
1. **API 경계에서 확보할 수 있는 증거를 중심으로 분석한다는 점**
    Riverbed는 서버의 관리되는 실행 환경과 협력해 정책을 집행합니다. Sesame도 데이터와 정책을 함께 유지하도록 프로그램 구조에 통합합니다.

    우리 프로젝트는 **게이트웨이를 통과하는 요청·응답을 핵심 관측 대상으로 삼습니다.** 그래서 비교의 초점이 달라집니다.

    | 비교 항목 | Riverbed·Sesame 계열 | 우리 현재 설계 |
    | --- | --- | --- |
    | 중심 목적 | 데이터 처리 과정에서 정책 집행 | API 관측을 이용한 진단·조사 |
    | 필요한 통합 | 실행 환경 또는 프로그램 구조와의 통합 | API 수집 지점, 업무 정책, 필드·신원 매핑 |
    | 확인·통제 범위 | 각 시스템이 관리하는 내부 처리 과정 | 게이트웨이에 관측된 요청·응답 |

    여기서 **도입 비용을 줄일 가능성**이 있습니다. 하지만 “설치가 더 쉽다”는 것은 아직 측정해야 할 가설입니다. 내부 처리나 게이트웨이를 우회한 접근을 보지 못하는 한계도 함께 평가해야 합니다.

    가장 좋은 주장은 **“어느 정도의 서비스 변경으로, 어떤 범위를 얼마나 정확하게 관측할 수 있는가”**입니다.
1. **한국어 업무 문맥을 로컬 환경에서 분류한다는 점**
    Sherlock·Sato는 표 데이터의 의미 유형을 다루고, 의료 기록 연구는 영어 임상 문서를 다룹니다. 우리 프로젝트는 한국어 API의 필드명·설명·값을 함께 해석하는 조건에 초점을 맞춥니다.

    실제로 구분해야 할 사례는 이런 것들입니다.

    | 입력 | 구분해야 할 의미 |
    | --- | --- |
    | “당뇨 예방을 위한 식생활 안내” | 일반적인 건강 안내 |
    | “이 회원은 당뇨 진단을 받음” | 특정 개인에 관한 건강 정보 |
    | `order_id` | 주문을 구분하는 번호 |
    | `member_id` | 회원을 구분하는 번호 |

    **한국어와 로컬 실행은 현재 프로젝트의 적용 조건으로 설명할 수 있습니다.** 학술적 차별점은 그 조건에서 규칙·사전보다 오류를 줄이거나, 비슷한 정확도를 더 적은 자원으로 달성했을 때 생깁니다.

    “한국어를 지원한다”보다 **“한국어 업무 문맥을 추가했을 때 어떤 오분류가 얼마나 줄어드는가”**가 더 강한 연구 질문입니다.
1. **불완전한 기록에서도 확인된 노출과 미확인을 구분한다는 점**
    실제 조사에서는 응답 일부가 마스킹되거나 기록이 빠질 수 있습니다. 우리 시스템은 다음을 구분하려고 합니다.
    - 응답 증거와 정책이 있어 **위반을 확인할 수 있는 경우**
    - 실제 응답은 있지만 정책이 없어 **인가 여부를 판단하지 못하는 경우**
    - 요청 기록만 있어 **무엇이 반환됐는지 알 수 없는 경우**
    - 연결 키가 불명확해 **같은 사람의 기록인지 확정하지 못하는 경우**

    이 원칙은 CMU의 불완전 로그 연구와 겹칩니다. 우리의 연구 과제는 **그 원칙을 여러 API의 사람·항목별 노출 집계에 적용했을 때, 잘못된 확정과 과대·과소 집계를 얼마나 줄이는가**입니다.

    특히 내부 DB에서 확인한 관계와 실제 수신자가 가진 정보를 분리하는 것이 중요합니다. 조사자가 연결할 수 있다는 이유만으로 수신자도 같은 정보를 알아냈다고 단정하지 않아야 합니다.

**현재 차이와 앞으로 입증해야 할 차별점을 구분하면 이렇습니다.**

| 항목 | 현재 말할 수 있는 내용 | 추가 입증이 필요한 내용 |
| --- | --- | --- |
| 인가·노출 분석 연결 | 정책과 응답 증거를 연결하는 구조를 갖췄다 | 기존 방식보다 노출 범위를 정확하게 집계한다 |
| API 경계 중심 수집 | 게이트웨이 관측을 분석의 기반으로 사용한다 | 필요한 서비스 변경과 도입 비용이 더 적다 |
| 한국어 로컬 분류 | 해당 조건의 모델·규칙 비교를 수행하는 기반이 있다 | 문맥 활용으로 정확도·비용이 개선된다 |
| 불완전 증거 처리 | 근거가 부족하면 검토 상태로 남긴다 | 기록 누락·마스킹 상황에서도 잘못된 확정을 줄인다 |
| 조사 지원 | 기록을 연결해 증거 중심 보고서를 제공한다 | 분석가가 더 빨리, 더 정확하게 사건을 파악한다 |
