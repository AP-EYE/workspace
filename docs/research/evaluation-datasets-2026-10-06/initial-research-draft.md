# 태스크 2·4: 외부 평가 데이터셋과 AP-EYE 평가 목표

> **초기 조사본 보존용.** 이후 wger 공식 이미지의 취약·수정 GET 실행, 추가 인가 원문 및 한국어 공개 자료 감사를 반영한 [팀 공유 보고서](README.md)가 현재 판단과 실행 상태다. 아래의 후보 우선순위·미실행 표기는 작성 당시 기록이다.

조사일: 2026-10-06 · 범위: **읽기·조회 BOLA와 한국어 개인정보 탐지**

## 먼저 제안하는 결론

인가 진단은 **AuthProbe의 공개 합성 API와 VAmPI를 1차 재현 기준으로 사용하고, BACScan 논문에 나온 실제 애플리케이션의 읽기 취약점을 별도의 외부 검증군으로 확보**하는 구성이 적절하다. 앞의 두 대상은 이번에 직접 실행했다. BACScan의 실제 서비스 사례는 원문에서 이름·버전·평가 방법을 확인했지만 아직 재현하지 않았다.

한국어 개인정보는 **SPY에서 합성 생성 절차, K-LegalDeID와 Thunder-DeID에서 한국어 라벨·경계·평가 기준을 가져오되, 논문 점수를 우리 목표 정확도로 복사하지 않는다.** 바로 접근 가능한 한국어 합성 데이터 후보는 K-PII-Bench다. 다만 해당 후보의 논문 원문은 확인하지 못했으므로, 논문 근거와 공개 데이터 자산을 구분하고 품질 검증을 거쳐 사용해야 한다.

이번에 확인한 자료 중에는 우리 조건에 그대로 맞는 ‘실제 API + 정상/읽기 BOLA의 완전한 정답 + 한국어 PII’를 모두 제공하는 완성형 벤치마크가 없었다. 따라서 **인가와 PII를 각각 외부 기준으로 평가한 뒤, 두 기능을 결합한 평가를 추가**하는 편이 결과를 해석하기 쉽다. ‘그런 벤치마크가 전 세계에 없다’는 주장은 아니다.

원문 Table 1의 버전과 수치다. 이 표의 `RBAC`는 **Read-based Broken Access Control**이며, 흔히 쓰는 Role-Based Access Control과 다른 약어다.

여기서 애플리케이션 이름과 버전을 확인한 것과, 해당 버전의 취약점·수정 commit·PoC·정상 응답을 재현한 것은 다르다. **이번에 후자까지 완료했다고 보고하지 않는다.** 현재 공개 저장소의 코드만으로 논문과 동일한 44개 정답 패키지를 곧바로 재현할 수 있는지도 확인되지 않았다.

### 논문 성능 수치를 해석할 때의 주의점

- BACScan Table 2의 알려진 **읽기 20개**에서는 TP 15, FP 3, FN 5다. 정밀도 83.33%, 재현율 75%이며 **정상 전체가 없으므로 FPR은 계산할 수 없다.** Table 3의 읽기 재현율 87.80%는 발견 사례를 포함한 41개 중 36개라는 다른 분모다. 두 값을 같은 실험 성능처럼 섞으면 안 된다.
- EvoMaster의 52개 API 실험은 보안 오류 탐색 연구다. §5.4–5.5에서 8개 취약 API와 36개 WFD 실험에서 F206(Missed Authorization Checks)을 찾지 못했다고 설명한다. 이 수를 BOLA 정확도의 분모로 사용할 수 없다.
- AuthProbe의 8개 finding은 **BOLA 6 + IDOR/열거 관련 2**다. ‘BOLA 8개 탐지’라고 쓰지 않는다.

AuthProbe의 현재 공개 코드에서는 목록으로 발견한 ID와 타 계정의 응답 ID를 검사하는 경로를 확인했다. 논문의 설명과 현재 코드가 모든 단계에서 동일한지까지 검증한 것은 아니다. 따라서 정확한 표현은 **‘논문의 주요 finding 수를 공개 코드에서 재현’**이다.

VAmPI는 임시 복사본의 DB에 합성 사용자·책만 만들었다. 기존 책 handler의 `vuln` 설정만 전환했고 인가 쿼리는 수정하지 않았다. API 서버를 외부에 열지 않았다. 전체 VAmPI가 안전해졌다는 의미도 아니다.

**법률 논문 두 편은 문맥 전체를 처음부터 합성한 데이터가 아니다.** 공개된 비식별 실제 판결문의 가림 부분을 대체하는 방식이다. 우리는 사용자의 조건대로 평가에 실제 개인의 정보를 쓰지 않고, 이러한 생성·주석 원칙을 합성 값과 문맥에 적용한다. 원문을 재사용하려면 공개 여부 외에 해당 자산의 이용 조건도 확인해야 한다.

### 높은 F1을 그대로 가져오면 안 되는 이유

K-LegalDeID Table 1의 0.9923은 결합 데이터의 **유형+정확한 경계 일치 entity micro F1**이다. 같은 논문 Table 2에서는 Court+SNS로 학습하고 별도 Thunder-DeID에 적용했을 때 entity micro F1이 **0.3658**이었다. 데이터 영역과 가림 기준의 차이가 함께 있으므로 라벨 차이만이 원인이라고 단정할 수 없다. 그래도 **내부 점수만으로 한국어 API 응답 일반화를 주장할 수 없다는 직접적인 근거**가 된다. [원문 PDF pp.7–8](https://aclanthology.org/2026.eacl-long.103.pdf)

Thunder-DeID v3의 Table 2에서는 최상위 이진 **토큰** F1이 0.9808, 유형 분류 **토큰** micro F1이 0.9105다. K-LegalDeID의 entity F1과 평가 단위가 다르므로 숫자 크기로 모델 순위를 매기지 않는다. 공식 소개 페이지의 구버전 수치·모델 크기와도 섞지 않는다. [v3 PDF p.8](https://arxiv.org/pdf/2506.15266v3)

SPY는 작성자의 개인정보만 정답으로 간주하는 좁은 기준을 사용한다. 다른 사람의 개인정보도 보호해야 하는 AP-EYE에 이 기준을 그대로 적용하면 안 된다. ‘사람 이름으로 인식됨’, ‘보호 대상 개인정보임’, ‘현재 요청자가 볼 수 없음’은 서로 다른 라벨이다. [SPY §3.1·Limitations](https://aclanthology.org/2025.naacl-srw.23.pdf)

### AP-EYE용 한국어 합성 평가 데이터 생성안

아래는 **아직 실행하지 않은 설계안**이다.

1. **외부 자료를 먼저 고정한다.** K-PII-Bench의 revision·고정 split·라벨 매핑을 보존한다. SPY/K-LegalDeID/Thunder-DeID의 생성 원칙을 참고한 독립 합성 문맥은 보완 세트로 관리한다. 둘의 결과를 합쳐서 하나의 높은 점수만 보고하지 않는다.
2. **문맥 또는 template 원형을 먼저 분리하고 값을 나중에 채운다.** 같은 문장에 이름만 바꾼 증강본이 train/test에 동시에 들어가지 않도록 한다. 템플릿 ID 외에도 정규화한 문맥 유사도를 확인한다.
3. 1차 유형은 이름·한국 전화번호·이메일·주소·주민등록번호·계좌번호로 제안한다. 실제 적용 전 외부 자료의 상위/하위 라벨과 대응표를 고정한다. 여권·운전면허번호는 별도 확장군으로 구분할 수 있다.
4. placeholder를 치환할 때 **문자 시작/끝 offset과 유형을 함께 생성**한다. ‘홍길동에게’에서는 ‘홍길동’만 PERSON으로 표시한다. 공백·하이픈·조사·Unicode 정규화를 바꾸면 offset도 다시 계산한다. 모델이 추측한 라벨을 정답으로 재사용하지 않는다.
5. 번호만 많이 넣지 말고 주문번호·가격·버전·상품명 같은 **정상 음성 사례**를 넣는다. 개인정보처럼 생겼지만 정책상 공개되는 대표 연락처도 별도 맥락으로 평가한다. 형식 검사에 실패한 식별자와 개인정보가 아닌 값은 같지 않으므로 라벨 기준을 분리한다.
6. 독립 검토자가 일부를 이중 주석하고 불일치를 조정한다. 자동 offset 검사와 의미상 PII 여부 검토를 별도로 기록한다. K-PII-Bench 표본에는 등록번호 자리에 종교명이 들어가는 문맥 불일치도 보여, offset 일치만으로 품질을 보증하지 않는다.
7. 도메인·template·가능하면 생성기까지 다른 외부 시험군을 둔다. JSON 필드 단독과 한국어 자유서술 필드를 따로 평가한다. 합성 값은 실인물과 연결하지 않으며 실제 전화·계정으로 확인 요청을 보내지 않는다.

## 4. 태스크 4 — 한 줄 정의

**현재 근거로 작성한 잠정 제출 문장:**

> 기존 Akto는 트래픽 기반 API 식별, 민감정보 분류, 인증 정보를 바꾸는 BOLA 테스트까지 제공한다. 우리는 정상 공유·공개 조회와 비인가 객체 조회가 혼재하고 한국어 개인정보가 포함된 응답에서 부족한 객체·권한 근거 기반 판정과 한국어 개인정보 분류를 개선하고, AuthProbe·VAmPI의 취약·수정 대상과 품질 검증을 거친 K-PII-Bench 및 독립 한국어 합성 데이터에서 BOLA 오탐률·재현율·판정 커버리지와 개인정보 분류 F1로 평가한다.

이 문장의 ‘부족한 부분’은 개선 가설이다. **전체 Akto와 동일 조건으로 비교하여 우월성을 입증했다는 뜻이 아니다.** 실제 서비스 일반화 주장은 BACScan 사례 중 재현된 읽기 BOLA를 외부 시험군에 넣은 뒤에만 가능하다. K-PII-Bench 채택은 원문 발표 여부와 별도로 데이터 품질 검증을 통과해야 한다.

Akto에 이미 BOLA 기능이 있으므로 ‘기존 Akto는 BOLA를 못 한다’는 문장은 부정확하다. 조사한 [인증 교체 템플릿](https://github.com/akto-api-security/tests-library/blob/ce2267da7e28927876b41d944e63bdde10e41e00/Broken-Object-Level-Authorization/BOLAByChangingAuthToken.yaml)과 [응답 비교 구현](https://github.com/akto-api-security/akto/blob/42e88a247fb2a0532ec8d7a8ba6261b794ee3f8d/libs/utils/src/main/java/com/akto/testing/Utils.java#L381)을 기준으로, 공개·공유 정책과 응답 내 개별 객체의 연결을 보강하는 문제로 설명한다. 템플릿의 응답 유사도 90은 정확도 90%가 아니다.

## 5. 비교군과 평가 단위

| 실험 | 비교 대상 | 평가 단위와 공정한 비교 조건 |
|---|---|---|
| 읽기 BOLA | 고정 버전 Akto 원본 / AuthProbe / AP-EYE 개선판 | 같은 API 상태·계정·객체·트래픽 seed·요청 예산. 정책 설정이나 수동 정보 입력량을 함께 기록. AuthProbe용 endpoint 설정도 공개 |
| PII 필드 분류 | Akto 원본 민감정보 분류 / 한국어 규칙 보강 / 제안 방식 | 같은 JSON leaf 값·키·라벨 체계. 원본 Akto가 내는 필드 타입과 비교 |
| 자유서술 PII 경계 탐지 | 고정 설정 Presidio / 한국어 규칙 / 한국어 NER 또는 제안 방식 | 같은 문자 span gold. 언어 모델·recognizer·threshold·지원 유형 고정. 지원하지 않는 유형도 명시 |
| 개선 원인 분리 | 제안 방식에서 객체 관계 근거 제거 / 정책 근거 제거 / 한국어 모듈 제거 | 동일 입력으로 각 구성요소가 바꾼 FP·FN·보류를 비교하는 ablation |

Akto의 필드 분류 결과를 그대로 문자 span 예측처럼 취급하면 비교가 불공정하다. **필드 분류 실험과 span 추출 실험을 분리**하고, 어떤 출력을 어떤 단위로 변환했는지 공개한다. 기본 영어 Presidio의 한국어 미지원 성능만 낮게 보여주는 비교도 피하고, 한국어 recognizer를 구성한 규칙 기준선을 함께 둔다.

인가 정답 한 건은 `(앱 버전, 요청자, 대상 객체, 읽기 연산, 정책 상태)`로 정의한다. 목록은 endpoint 성공 여부 외에 **각 응답 객체/비공개 필드의 노출**도 확인한다. 같은 객체에 대한 유사 요청을 수백 개 만들어 독립 사례 수를 부풀리지 않는다.

정답은 서버의 소유권/공유 정책, 취약·수정 코드, fixture로 작성한다. 탐지 결과에서 역으로 정답을 만들지 않는다. 제안 도구가 이용할 수 있는 정책 정보와 평가자만 볼 수 있는 정답을 분리하고, 비교군에도 동등한 허용 정보를 제공한다.

## 6. 지표와 목표 수치를 정하는 방법

| 개선하려는 부분 | 주 지표 | 함께 보고할 것 |
|---|---|---|
| 정상 공개·공유를 BOLA라고 판단하는 문제 | **FPR = FP / 전체 정상 사례 수** | 정상 유형별 FP 수. 정밀도 `TP/(TP+FP)`와 혼동하지 않음 |
| 실제 비인가 조회를 놓치는 문제 | **종단 재현율 = 탐지한 BOLA / 전체 정답 BOLA** | 발견 실패·검사 실패·보류로 남은 양성도 미탐에 포함하여 분해 |
| 모두 보류하여 수치만 좋아지는 문제 | **판정 커버리지 = 정상 또는 BOLA로 판정한 수 / 평가 사례 수** | 보류율, 커버리지별 위험, 확정 판정 집합의 FPR. 정답 자체 불명확한 사례는 별도군 |
| 한국어 유형 분류 | **필드/유형별 precision·recall·macro F1** | 지원 유형별 표본 수, micro F1, JSON 필드와 자유서술 결과 분리 |
| 한국어 경계·조사 처리 | **유형+문자 경계 exact-match entity F1** | 유형별 recall, 조사/공백/하이픈별 결과. token F1·overlap F1은 보조 지표 |
| 실제 노출 방지 효과 | **정답 민감 문자열 중 탐지·처리되지 않고 남은 비율** | 완전 누락과 일부 문자만 남는 누출 구분, 과도한 마스킹 비율 |

숫자는 아래 순서로 정한다.

1. 외부 대상·버전·정답·negative 유형을 고정한다.
2. 개발 세트에서 Akto와 비교군을 실행해 `R₀(재현율), F₀(FPR), C₀(커버리지), M₀(유형별 F1)`를 얻는다.
3. 개선판의 사전 목표를 **같은 재현율·커버리지에서 FPR 감소** 또는 **같은 FPR 예산에서 재현율 증가**로 정한다. PII는 고정된 정밀도 조건에서 유형별 재현율 개선을 확인한다.
4. 최소 개선 폭·허용 저하 폭·신뢰구간·반복 seed 수를 개발 세트에서 정하고, 보지 않은 시험 세트에 적용하기 전에 동결한다. 독립 단위가 앱이면 앱 단위, 원문이면 원문 단위로 불확실성을 계산한다.

**지금 확정할 수 있는 숫자:** AuthProbe 기능 회귀 확인에서 기존 BOLA **6/6** 탐지와 수정 대상 **0건 경고**를 유지해야 한다. 이것은 작은 회귀 기준이다. 전체 Akto의 FPR·재현율과 한국어 성능을 아직 측정하지 않았으므로, ‘오탐률 5% 이하’, ‘한국어 정확도 95%’ 같은 최종 목표를 지금 만들어 넣지 않는다. **최종 목표 수치는 TBD이며, 위 기준선 측정 후 확정**한다.
