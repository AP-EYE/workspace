# 양유상 볼라 논문 조사

### ① Rennhard et al., 2022 — 탐색 누락과 오탐을 가장 직접적으로 다룬 논문
**Automating the Detection of Access Control Vulnerabilities in Web Applications**

*SN Computer Science*, 2022. DOI: `10.1007/s42979-022-01271-1`

**ai 요약:** 두 사용자로 웹 애플리케이션을 탐색하고 한 사용자의 요청을 다른 사용자로 재실행한 뒤 응답을 비교합니다. 재실행으로 받은 내용이 두 번째 사용자가 이미 정상 탐색 중 받은 내용인지도 확인해 오탐을 줄입니다. 

**우리 가설과 직접 연결되는 사례:** Misago에서는 모든 사용자가 다른 사용자의 프로필을 볼 수 있지만, 상대방이 접근 가능한 게시판에 글을 작성해야 프로필 링크가 나타납니다. 저자들은 이 때문에 발생하던 오탐을 줄이려고 **각 테스트 사용자가 공개 글을 하나씩 작성하도록 테스트 데이터를 준비**했습니다. Discussion에서는 합법적으로 접근 가능한 내용을 크롤러가 놓치거나 링크가 없으면 오탐이 발생할 수 있다고 명시합니다.

**알 수 있는 사실:**

"허용 객체의 탐색 누락이 오탐을 만든다"는 문제는 이미 알려져 있습니다. 차별성은 **그 누락을 더 잘 탐색해서 보완하는 것과, 객체 설정 근거로 보완하는 것 중 무엇이 어떤 비용에서 유리한지**에 두어야 합니다.

**해당 논문 파트:** `Test Application 3: Misago`, `Discussion — Fundamental assumptions`.

### ② FlowWatcher, CCS 2015 — '설정 근거를 별도로 추적한다'는 발상의 중요한 선행연구
**FlowWatcher: Defending against Data Disclosure Vulnerabilities in Web Applications**

Muthukumaran et al., CCS 2015. DOI: `10.1145/2810103.2813639`

**ai 요약:** 웹 애플리케이션 앞의 프록시가 HTTP 트래픽을 보면서 **의도된 사용자–데이터 접근 정책을 별도로 추적**하고, 그 정책을 위반하는 데이터 노출을 차단합니다. 사람이 작성한 규칙으로 객체 생성, 사용자·그룹 관계, 공유 등 정책 변화를 추적합니다.

**우리와 겹치는 부분:** 단순히 "다른 사용자의 응답과 비슷하다"가 아니라, **데이터를 누가 볼 수 있어야 하는지에 관한 별도 근거**를 사용합니다. 공개·공유와 정책 변화도 다룹니다. 평가에 제시된 정책은 애플리케이션별 9–43줄이며, 저자들은 평가용 규칙들을 하루에 작성했다고 보고합니다. 따라서 "명시적 정책은 항상 전체 권한표이고 작성 비용이 매우 크다"는 전제도 그대로 두기 어렵습니다.

**우리에게 의미하는 것:**

가능한 차이는 **배포 프록시와 애플리케이션 전반의 정책 추적 없이, 소수 테스트 객체에 한정한 진단을 수행한다**는 점입니다. 다만 이것이 실제로 더 적은 준비 비용을 요구하는지는 측정해야 합니다.

**직접 읽을 부분:** §3 정책 표현, §4 데이터 추적, §5.2 사례, Appendix A. 특히 "설정 변경을 어떤 규칙으로 권한 변화에 연결하는가"를 보세요.

### ③ BACScan, CCS 2025 — 반드시 넘어야 하는 공개 필터 기준선
**BACScan: Automatic Black-Box Detection of Broken-Access-Control Vulnerabilities in Web Applications**

Liu et al., CCS 2025. DOI: `10.1145/3719027.3744825`

**가볍게 요약하면:** 수정 취약점에는 실제 데이터 변화의 피드백을 사용하고, 읽기 취약점에는 다중 세션 탐색과 응답 유사도 판정을 사용합니다. 읽기 검사에서는 **두 세션의 탐색 결과에 URL과 내용이 동일하게 나타난 페이지를 공개 페이지로 걸러냅니다.** 여기서 논문의 RBAC는 *Read-BAC*를 뜻합니다. [Yuan Zhang](https://yuanxzhang.github.io/paper/bacscan-ccs25.pdf)

**우리 가설과의 연결:**

사용자가 정정한 내용이 맞습니다. 공유 객체도 양쪽 탐색에 같은 URL·내용으로 나타나면 필터링될 수 있습니다. 따라서 비교 질문은 다음이어야 합니다.
> "공유를 처리할 수 있는가?"가 아니라, **"실제로 허용된 객체가 한쪽 탐색 결과에 없을 때도 올바르게 판단하는가?"**

이는 해당 필터의 동작에서 도출한 **우리의 검증 질문**입니다.

논문은 읽기 검사에서 총 8개의 오탐을 보고하지만, 주요 원인 설명은 응답 유사도 알고리즘과 고정 임계값의 한계입니다. **이 8개를 공개·공유 객체의 탐색 누락 때문이라고 인용하면 안 됩니다.** [Yuan Zhang](https://yuanxzhang.github.io/paper/bacscan-ccs25.pdf)

**직접 읽을 부분:** §4.2.2, §5.2의 False Positives/False Negatives, §6. 비교 실험은 수정 검사까지 포함한 전체 성능이 아니라 읽기 검사끼리 맞춰야 합니다.

### ④ AuthProbe, 2026 — 가장 가까운 API 읽기 검사이지만, 목록을 권한 근거로 삼음
**AuthProbe: Specification-Driven, Multi-Identity Detection of Broken Object-Level Authorization in Recruitment API**

Jay Barach, arXiv `2607.20574`, 2026.

**가볍게 요약하면:** OpenAPI에서 목록·개별 조회 API를 찾고, 각 계정의 목록에 나온 객체들을 기록합니다. 이후 다른 계정으로 개별 조회를 시도합니다. §III에서는 **목록에 객체가 나타난다는 것을 해당 계정이 읽을 자격이 있다는 근거**로 정의합니다. Algorithm 2는 공격자 자신의 목록에도 나온 객체를 제외하므로, 공통 목록에 나타난 공유 객체를 무조건 위반으로 보는 방식은 아닙니다. [arXiv](https://arxiv.org/pdf/2607.20574)

**꼭 구분할 부분:** 초록은 소유자 조회와의 응답 비교를 강조하지만, Algorithm 2와 식 (1)의 핵심 확인식은 **성공 상태·객체 형태·요청 객체 ID 일치**입니다. 이를 "전체 본문이 일치해야 확정한다"로 요약하면 부정확합니다. [arXiv](https://arxiv.org/pdf/2607.20574)

**우리에게 의미하는 것:**

핵심 비교점은 **목록에서 관찰되지 않은 객체를 비허용으로 취급하는 가정**입니다. 실제로 읽어도 되지만 목록에서 빠지는 객체를 넣어 비교할 수 있습니다.

또한 목록이 없을 때 명시적 시드를 입력하는 대안을 제공합니다. "목록 API가 없으면 검사 불가능"이 아니라 "자동 발견이 제한되고 추가 입력이 필요하다"가 맞습니다. [arXiv](https://arxiv.org/pdf/2607.20574)

**직접 읽을 부분:** §III, §V-B와 Algorithm 2, §VIII 및 Threats to validity.

### ⑤ EvoMaster 보안 검사, 2026 — 문제의식은 지지하지만, 단순 규칙의 대표로 쓰면 안 됨
**Enhancing REST API Fuzzing with Access Policy Violation Checks and Injection Attacks**

Sahin, Zhang, Arcuri, arXiv `2604.00702`, 2026.

**가볍게 요약하면:** REST API 퍼징에 여러 보안 판정 규칙을 추가합니다. §3.3은 관리자·모더레이터·가족 공유 같은 사례를 들어 **타인의 리소스 접근을 일괄 금지하면 오탐이 생긴다**고 설명합니다. 이 부분은 현재 문제의식을 직접 뒷받침합니다. [arXiv](https://arxiv.org/html/2604.00702v1)

**주의할 점:** 해당 절의 실제 방법은 단순한 읽기 BOLA 판정이 아닙니다. 같은 객체에 대해 PUT·PATCH·DELETE 사이에서 관찰되는 허용·거부의 불일치를 이용합니다. 또한 §3.2에는 판정이 불충분하면 `inconclusive`로 남는 경우도 있습니다. 따라서 "기존 연구는 성공 코드만 보고 확정하며 보류가 없다"는 근거로 사용할 수 없습니다. [arXiv](https://arxiv.org/html/2604.00702v1)

**우리에게 의미하는 것:**

이 논문은 **명세 없이 권한 의도를 알아내는 어려움**을 설명하는 근거로 적합합니다. 우리는 읽기 권한을 수정·삭제 권한이나 기존 거부 응답에서 추론하지 않고, 해당 객체의 설정 근거로 제한해 판단하는 방향입니다.

**직접 읽을 부분:** §3 도입부, §3.2, §3.3. 특히 저자들이 규칙을 적용할 수 없다고 판단하는 조건을 확인하세요.

### ⑥ RESTler 보안 규칙, ICST 2020 — 단순 비교 기준선의 출처
**Checking Security Properties of Cloud Service REST APIs**

Atlidakis, Godefroid, Polishchuk, ICST 2020. DOI: `10.1109/ICST46399.2020.00046`

**가볍게 요약하면:** 상태를 가진 REST API 요청 시퀀스를 생성하고, 보안 속성을 검사합니다. 사용자 네임스페이스 검사에서는 유효한 요청을 다른 인증 토큰으로 재실행해 성공하면 사용자 간 격리가 깨진 것으로 보고합니다. [Patrice Godefroid](https://patricegodefroid.github.io/public_psfiles/icst2020.pdf)

**우리 가설과의 연결:** 사용자 간 객체가 분리되어야 한다는 환경에서는 합리적인 규칙입니다. 하지만 공개·공유를 허용하는 객체에 그대로 적용할 때 어떤 오탐이 생기는지가 우리의 비교 대상입니다.

**우리에게 의미하는 것:**

단순 기준선의 출처로는 좋지만, 이것만 이겨서는 최신 연구 대비 차별성이 충분하지 않습니다. 또한 **객체를 생성한 뒤 다른 계정으로 재실행하는 절차 자체도 이미 존재**하므로, 테스트 객체 생성이나 토큰 교체 자체를 새 기여로 잡으면 안 됩니다. [Patrice Godefroid](https://patricegodefroid.github.io/public_psfiles/icst2020.pdf)

**직접 읽을 부분:** §III의 사용자 네임스페이스 속성과 해당 검사기 설명. 실험에서는 "논문의 규칙을 재현한 기준선"인지, 특정 버전의 실제 도구인지 구분해야 합니다.

### ⑦ MST-wi, TSE 2023 — '설정 변화에 따른 기대 결과'를 설계할 때 유용
**Metamorphic Testing for Web System Security**

Bayati Chaleshtari et al., *IEEE Transactions on Software Engineering*, 2023. arXiv `2208.09505`.

**가볍게 요약하면:** 입력을 바꿨을 때 출력 사이에 성립해야 하는 관계를 검사합니다. 예를 들어 같은 요청의 사용자를 바꾸었을 때, 권한 관계에 따라 응답이 달라져야 한다는 식입니다. 이를 표현하는 언어와 76개의 보안 관계를 제시합니다. [arXiv](https://arxiv.org/pdf/2208.09505)

**우리 가설과의 연결:** 권한 우회 예시는 단순 사용자 교체만 하지 않습니다. 상위 권한 사용자인지, GUI로 해당 내용에 도달할 수 있는지 같은 **관계의 적용 전제**를 둡니다. 즉, 변형 테스트도 "언제 그 관계가 성립해야 하는가"라는 근거가 필요합니다. [arXiv](https://arxiv.org/pdf/2208.09505)

**우리에게 의미하는 것:**

우리 방식도 다음과 같은 관계로 정리할 수 있습니다.
> 같은 객체를 비공개 → B에게 공유 → 공유 해제로 바꾸면, B의 기대 읽기 권한도 그 설정에 맞춰 바뀐다.

새로움은 상태를 바꾸는 행위보다 **그 전제가 성립함을 어떻게 확인하고, 확인하지 못하면 어떻게 보류하는가**에 있습니다.

**직접 읽을 부분:** §4와 Figure 2. 관계식보다 먼저, 관계를 적용하기 위한 조건들을 보세요.

### ⑧ Links2CPN, 2025 — '공격 시도 탐지'와 '실제 위반 확정'을 구분할 근거
**Automated broken object-level authorization attack detection in REST APIs through OpenAPI to colored petri nets transformation**

Santos Filho, Rodríguez, Feitosa, *International Journal of Information Security*, 2025. DOI: `10.1007/s10207-024-00970-5`

**가볍게 요약하면:** OpenAPI의 연결 정보를 상태·데이터 흐름 모델로 변환하고, 서버 요청·응답 로그가 그 흐름을 벗어나는지 검사합니다. Juice Shop과 Memos를 평가에 사용하며, Memos 사례는 메모 보관 처리의 PATCH 취약점입니다. [Springer](https://link.springer.com/article/10.1007/s10207-024-00970-5)

**우리 가설과의 연결:** 논문은 평가 과정에서 **공격 시도를 탐지하는 것과 성공한 공격을 판정하는 것이 다르다**는 문제를 보여줍니다. 실제 공격 성공을 기준으로 평가하면 추가적인 판정 규칙이나 전문가 검토가 필요하다고 설명합니다. 또한 입력 OpenAPI의 `links`와 요청·응답 본문을 포함한 로그에 의존합니다. [Springer](https://link.springer.com/article/10.1007/s10207-024-00970-5)

**우리에게 의미하는 것:**

우리의 "확정"은 요청이 수상하다거나 예상 흐름을 벗어났다는 뜻이 아니라, **금지된 조회로 보호 데이터가 실제 전달되었다는 실행 증거**여야 합니다.

**직접 읽을 부분:** §2.2의 명세 요구사항, §4.2, §5.2의 공격 시도/성공 구분, §5.3의 Memos 평가.

## 4. ZAP 관련 주장은 별도로 고쳐야 합니다
논문은 아니지만, **현재 차별성 주장을 검증하는 데 가장 중요한 도구 문서**입니다.

ZAP Access Control Testing은 사용자별 자원에 대해 `Allowed`, `Denied`, **`Unknown`**을 설정할 수 있습니다. 또한 URL 트리의 상위 규칙을 하위 경로에 상속하므로, 모든 객체·경로의 권한을 하나씩 전부 작성해야 하는 구조라고 설명하면 부정확합니다. [ZAP](https://www.zaproxy.org/docs/desktop/addons/access-control-testing/)

물론 ZAP의 `Unknown`은 **입력 정책이 알려지지 않았다는 상태**이므로, 우리가 설계하는 세 가지 출력 판정과 완전히 같다고 단정할 필요는 없습니다. 그러나 이것만으로도 다음 두 주장은 약해집니다.
- "기존 도구는 전체 권한표가 필수다."
- "소수 권한 입력과 모르는 상태의 분리가 우리만의 차별성이다."

따라서 비교 대상에는 **동일한 테스트 객체에만 수동 접근 규칙을 넣은 ZAP 또는 동등한 명시적 정책 판정기**를 포함해야 합니다.

여기서 중요한 질문은 다음입니다.
> **같은 객체의 정답을 사람이 직접 넣는 방식과 비교했을 때, 우리의 설정 근거 수집·검증 절차가 실제로 무엇을 덜 하게 해 주는가?**

이를 설명하지 못하면 제안 방법이 "작은 권한표를 다른 형식으로 작성한 것"으로 보일 수 있습니다.

## 5. 남아 있는 공백을 우리가 어떻게 해결할지
### 5.1 연구 질문을 세 가지로 분리하는 것이 좋습니다

| 연구 질문 | 실제로 검증할 내용 |
|---|---|
| **RQ1. 설정 근거의 효과** | 같은 객체와 요청을 검사할 때, 객체 설정 근거를 추가하면 공개·공유 객체의 오탐이 얼마나 줄어드는가? 특히 탐색이 불완전할 때 차이가 커지는가? |
| **RQ2. 근거의 신뢰성과 한계** | 공유 목록 불완전, 상속 권한, 설정 변경 등에서 잘못 확정하지 않고 보류할 수 있는가? 그 때문에 놓치는 실제 위반은 얼마나 되는가? |
| **RQ3. 비용 대비 실용성** | 사람이 준비할 수 있는 시간과 객체 수가 제한될 때, 탐색 개선이나 수동 정책 입력보다 유리한 판정 범위·재현율을 얻는가? |

**"공개 여부를 주면 오탐이 줄어든다"만 보여주는 결과는 예상 가능한 결과입니다.** 연구로서 더 중요한 것은 그 정보를 적은 비용으로 얻고, 잘못되거나 오래된 근거를 식별하며, 얻지 못한 부분의 손실까지 측정하는 일입니다.

### 5.2 '객체 라벨'보다 '검증 가능한 설정 기록'을 입력으로 삼기
제가 제안하는 최소 기록 단위는 다음과 같습니다.

| 항목 | 필요한 이유 |
|---|---|
| 객체 ID와 소유 계정 | 어느 객체에 관한 근거인지 연결 |
| 공개 범위와 허용 대상 | 소유자와 실제 읽기 허용자를 구분 |
| 적용 연산·엔드포인트 | 읽기 허용을 수정·삭제 허용으로 확대하지 않음 |
| 설정을 만든 요청 및 소유자 측 확인 결과 | 사람이 적은 라벨과 실제 설정이 일치하는지 확인 |
| 설정 시점·상태 버전 | 공유 해제 등으로 오래된 근거가 된 경우 식별 |
| 보호 데이터 식별값 | HTTP 성공이나 ID 반환이 아니라 실제 보호 데이터 전달을 확인 |

여기서 **독립적인 근거**는 "서버와 완전히 무관한 정보"라는 뜻보다, **검사 대상 조회의 성공·실패를 보고 금지 여부를 거꾸로 정하지 않는다**는 뜻으로 정의하는 편이 정확합니다.

예를 들어 "B로 조회했더니 403이었으므로 B는 금지 대상"이라고 정의하면, 처음부터 잘못 200을 반환하는 취약점을 놓칠 수 있습니다. 반면 객체를 비공개로 만들고 그 설정을 별도 절차로 확인했다면, 검사 대상 조회와 분리된 금지 근거가 됩니다.

### 5.3 `private`와 '공유 목록에 B 없음'만으로는 부족할 수 있음
설계상 다음과 같은 가능성을 처리해야 합니다.

B가 관리자이거나, 허용된 그룹의 구성원이거나, 상위 폴더·조직에서 권한을 상속받거나, 공유 목록이 일부만 반환된 경우입니다. 이런 가능성이 남아 있다면 **목록에서 B가 보이지 않는다는 사실은 완전한 금지 증명이 아닙니다.**

초기 연구에서는 다음처럼 범위를 제한하는 것이 현실적입니다.
> "테스트 계정은 동일한 일반 사용자 역할이며, 조직·그룹·상위 객체의 권한 상속과 별도 공유 링크가 없음을 확인한 객체에서만 금지 판정을 확정한다."

지원하지 않는 권한 모델을 억지로 추론하지 않고 보류해야 합니다. 이후 지원 범위를 넓힐 때마다 준비 비용과 재현율이 어떻게 변하는지를 측정하면 됩니다.

### 5.4 두 계정으로 가능한 범위를 명확히 하기
A를 소유자, B를 검사자로 두고 **서로 다른 객체 또는 초기화 가능한 상태**를 사용하면 비공개, B에게 공유, 공유 해제 상태를 두 계정으로 비교할 수 있습니다.

반면 **동일한 공유 상태에서 소유자·공유받은 사용자·공유받지 않은 사용자를 동시에 비교**하려면 세 계정이 필요합니다. 비로그인 공개와 로그인 사용자 공개를 구분하려면 익명 요청도 별도로 필요합니다.

따라서 "항상 두 계정이면 모든 공유 모델을 검증한다"가 아니라, **두 계정으로 구성 가능한 정책 상태를 연구 범위로 정의한다**고 쓰는 것이 좋습니다.

### 5.5 '확정'은 객체 전체나 API 전체가 아니라 특정 실행에 한정하기
판정 단위를 다음처럼 잡으세요.
> **계정 × 객체 × 조회 연산 × 정책 상태/시점**

그리고 출력은 다음 의미로 제한하는 것이 안전합니다.

**위반 확인:** 금지 근거가 유효하고, 해당 조회로 보호 데이터가 실제 전달됨.

**이번 검사에서 위반 미관찰:** 유효한 검사 조건에서 해당 위반이 관찰되지 않음.

**판정 보류:** 권한 근거, 설정 최신성, 실행 유효성 또는 데이터 전달 증거가 부족함.

특히 만료된 인증 정보로 받은 401, 서버 오류, 객체 삭제 등은 객체 수준 인가가 정상이라는 증거가 아닙니다. 한 번의 비위반 결과를 "이 객체·엔드포인트는 안전하다"로 확대하지 않아야 합니다.

## 6. 실험은 '같은 입력에서 판정 근거만 바꾸는 비교'가 핵심입니다
### 6.1 비교 기준선

| 기준선 | 판정에 사용하는 정보 | 비교 목적 |
|---|---|---|
| 단순 재실행 규칙 | 다른 계정으로 재실행했을 때의 성공 여부 | 기존 예비 결과와 연결 |
| AuthProbe형 규칙 | 계정별 목록, 개별 조회의 성공·객체·ID 확인 | 목록 기반 허용 추정과 비교 |
| BACScan/Rennhard형 규칙 | 양쪽 탐색 결과, 공개 필터, 응답 비교 | 공개 필터가 있는 강한 관찰 기반 방식과 비교 |
| 부분 정책 입력 방식 | 동일 객체에 사람이 명시한 허용·금지 규칙 | 설정 근거 수집·검증이 단순 수동 입력보다 유리한지 확인 |
| 제안 방식 | 검증된 객체 설정 기록, 보호 데이터 전달 증거, 보류 | 추가 근거의 효과와 비용 측정 |

여기서 **실제 도구 실행**과 **논문의 판정 규칙 재현**을 구분해야 합니다. 판정 규칙만 구현했다면 "BACScan 전체 도구보다 우수하다"가 아니라 "BACScan의 해당 읽기 판정 규칙과 비교했다"고 써야 합니다.

### 6.2 반드시 필요한 비교: 시드 효과와 설정 근거 효과 분리
제안 방식에만 테스트 객체 ID를 주면, 성능 차이가 **권한 근거 때문인지 객체를 쉽게 발견했기 때문인지** 구분되지 않습니다.

따라서 첫 실험은 모든 방식에 같은 계정·객체 ID·요청 집합을 제공하고, **설정 근거를 제공하는지 여부만 바꾸는 비교**로 구성하는 것이 좋습니다. 이후 실제 탐색까지 포함한 전체 과정의 성능을 별도로 측정하세요.

탐색 누락 실험도 두 종류를 나누면 해석이 명확해집니다. 하나는 링크 부재나 정상적인 목록 필터처럼 **앱 자체에서 발생하는 누락**, 다른 하나는 관찰 기록 일부를 제외해 만드는 **통제된 누락 조건**입니다. 후자는 필터의 민감도를 분석하는 실험이지, 실제 도구 전체의 성능을 그대로 나타내는 실험은 아닙니다.

### 6.3 우선 넣을 실험 조건

| 조건 | 확인할 질문 |
|---|---|
| 공개·공유 객체가 양쪽 탐색에 모두 나타남 | 기존 공개 필터가 정상적으로 잘 작동하는 조건에서도 불필요한 우위를 주장하지 않는가? |
| 허용 객체가 한쪽 탐색에만 나타남 | 설정 근거가 관찰 누락에 따른 오탐을 줄이는가? |
| 비공개 객체의 인가 검사 제거 | 실제 위반을 탐지하는가, 보류로 많이 놓치지는 않는가? |
| 공유 부여·해제 후 재검사 | 오래된 설정 기록을 그대로 사용하는 오류가 없는가? |
| 권한 상속 또는 불완전한 공유 정보 | 근거가 부족한데도 금지로 확정하지 않는가? |
| ID·공개 요약만 반환되고 보호 본문은 비공개 | 성공 코드나 객체 ID만으로 정보 유출을 과대 판정하지 않는가? |

평가 정답은 제안 판정기가 읽는 필드를 그대로 복사해 만들지 말고, **별도 검토한 정책 의미와 취약·수정 버전의 실제 동작**으로 확인해야 합니다. 그렇지 않으면 "우리 입력과 우리 출력이 일치한다"만 측정할 위험이 있습니다.

### 6.4 지표: 보류를 숨기지 않는 분모가 중요함
재현율은 사용자가 정한 원칙대로 다음처럼 두는 것이 좋습니다.

$$
\text{재현율} = \frac{\text{위반으로 확인한 실제 위반}}{\text{전체 실제 위반}}
$$

**보류한 실제 위반과 검사하지 못한 실제 위반도 분모에서 빼지 않습니다.**

오탐률 역시 실제 위반이 아닌 평가 사례 전체 중 잘못 위반으로 판단한 비율인지, 판정한 사례만 대상으로 한 비율인지 명시해야 합니다. 보류 제외 지표를 추가한다면 별도 이름으로 보고하는 편이 좋습니다.

또한 같은 평가 집합에서 모든 사례가 판정 또는 보류 중 하나라면,

$$
\text{판정 범위} = 1 - \text{보류율}
$$

입니다. 두 지표를 독립적인 성과처럼 강조하기보다는 **대상 발견 범위, 근거 확보 범위, 최종 판정 범위**를 구분해야 합니다.

준비 비용에는 객체 생성 시간뿐 아니라 앱별 설정 해석, 필드 연결, 공유 상태 확인, 초기화, 변경 후 재검증 시간을 포함하세요. 최종적으로는 **같은 준비 시간에서 어느 방식이 더 적은 오탐과 더 높은 재현율을 얻는가**를 비교하는 것이 가장 설득력 있습니다.

## 7. 현재 예비 결과는 이렇게 해석하는 것이 맞습니다
### Gitea 8/18, Memos 3/6
현재 제공된 수치는 **단순 규칙을 개선할 필요성을 보여주는 예비 관찰**입니다. 제안 판정기의 효과를 보여주는 결과는 아직 아닙니다.

또한 18과 6이 무엇인지 명시해야 합니다. **전체 정상 접근 수**라면 오탐률의 분모로 사용할 수 있지만, **도구가 발생시킨 경고 수**라면 경고 중 오탐 비율, 즉 정밀도와 연결되는 다른 지표입니다.

### APIs.guru 9.5% 조사
원자료와 전체 탐색 코드를 받지 않았으므로 수치를 독립적으로 재현 확인한 것은 아닙니다. 제공된 절차만 놓고 보면 9.5%는 **선택한 명세 집합에서 특정 필드 이름이 검출된 비율**입니다.

따라서 "미표시 객체를 확정할 수 있는 API 비율의 엄밀한 상한"으로 쓰기는 어렵습니다. 다른 이름으로 권한을 표현하는 경우를 놓칠 수 있고, 이름이 일치해도 충분한 권한 근거가 아닐 수 있기 때문입니다.

더 중요한 점은 **핵심 제안 방식은 공격 대상 조회 응답에 `visibility` 필드가 없어도 성립할 수 있다는 것**입니다. 소유자의 객체 생성·설정 과정에서 근거를 확보한다면 됩니다. 이 조사는 핵심 방법의 적용 가능성을 결정하는 자료보다, **미표시 객체까지 확장하는 부가 기능의 한계 조사**로 분리하는 편이 연구가 선명해집니다.

## 최종 판단
현재 방향에서 피해야 할 주장은 **"공개·공유를 처음 구분한다", "권한 입력이 없다", "보류를 처음 도입한다"**입니다. 공개 필터, 부분적인 정책 입력, 설정에 따른 권한 추적은 각각 선행연구와 도구에 존재합니다. [Yuan Zhang](https://yuanxzhang.github.io/paper/bacscan-ccs25.pdf)

대신 확보해야 할 기여는 **검증 가능한 설정 근거를 만드는 절차**, **탐색 누락·공유 변화에서의 효과를 분리한 실험**, **그 효과를 준비 비용과 놓치는 위반까지 포함해 설명하는 결과**입니다.

가장 먼저 할 실험은 **현재 Gitea·Memos의 동일 객체·동일 요청 집합에 대해, 공개 필터 기준선과 부분 정책 입력 기준선을 추가하고 설정 근거의 유무만 바꾸는 비교**입니다. 여기서 차이가 확인되어야, 지금의 가설을 "단순 규칙의 오탐을 줄이는 구현"에서 "판정 근거의 비용 대비 효과를 검증하는 연구"로 발전시킬 수 있습니다.
