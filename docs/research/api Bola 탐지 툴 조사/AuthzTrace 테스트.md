# AuthzTrace 테스트

AuthzTrace 0.6.0을 직접 설치해서 돌려 봤습니다. 실제 Memos가 아니라, Memos 0.9.0 서버 코드의 조회 규칙 두 개만 흉내 낸 가짜 API를 대상으로 했습니다.

### 실험 구성
**가짜 API** (mock_memos.py)
- 개별 조회 `GET /api/memo/{id}`: PRIVATE는 작성자만, PROTECTED는 로그인 사용자, PUBLIC은 누구나 조회 가능
- 목록 조회 `GET /api/memo?creatorId=&visibility=`: 두 모드로 돌렸습니다
	- **vuln**: 0.9.0 코드처럼 `visibility` 인자가 공개 범위 필터를 그대로 덮어씀 → 남의 비공개 메모가 나옴
	- **fixed**: 남의 메모에는 덮어쓰기를 막은 가상의 수정본

**데이터**: alice의 PUBLIC·PROTECTED·PRIVATE 메모 각 1개, bob의 PRIVATE 메모 1개. 메모 본문에 표식 문자열을 넣었습니다.

**계약** (authztrace.yaml): 계정은 alice, bob, 비로그인(anon) 3개. 검사는 총 18개가 만들어졌습니다.

### 결과
**1. 같은 사용자의 공개·비공개 메모를 구분할 수 있나 → 가능하지만 리소스를 쪼개야 함**
- 계약 형식상 리소스 하나에 소유자당 객체를 하나만 적을 수 있습니다(`ids: {alice: 1}`).
- 그래서 alice의 메모 3개를 공개 범위별로 리소스 3개로 나눠 적었습니다(`allow: [all]`, `[authenticated]`, `[owner]`).
- 이렇게 하면 개별 조회 12개 검사가 모두 정확하게 통과했습니다. bob이 alice의 PUBLIC·PROTECTED 메모를 보는 건 정상으로, PRIVATE 메모는 403으로 판정됐습니다.

**2. 실제 누출 경로를 잡나 → 잡음 (vuln 모드)**
- bob, anon이 목록 조회로 남의 PRIVATE 메모를 받은 4건을 모두 BOLA로 판정했습니다.
- 판정 메모에 "표식 누출"도 함께 표시됐습니다.

**3. 목록 API에서는 고친 서버도 BOLA로 판정 (fixed 모드) ← 가장 중요한 발견**
- 고친 서버에서 bob은 `200 {"data": []}`, 즉 빈 목록을 받습니다. 비공개 메모는 하나도 새지 않았습니다.
- 그런데 AuthzTrace는 같은 4건을 **똑같이 BOLA로 판정**했습니다. 차이는 판정 메모에 "표식 누출"이 붙느냐뿐이고, 분류(category)는 둘 다 `bola`입니다.
- 원인을 코드에서 확인했습니다. 거부돼야 할 계정이 2xx를 받으면 본문을 보기 전에 바로 BOLA로 분류합니다(`engine.py`의 `_grade_deny`). 표식 검사는 상태 코드가 거부 코드일 때만 판정을 바꿉니다.
- 즉 **"응답 200만으로는 판단할 수 없다"는 README의 문제의식이 목록 API에서는 그대로 다시 생깁니다.** 정책 설정(`allow_status`, `deny_status`)이 전역이라 이 엔드포인트만 따로 우회하는 방법도 찾지 못했습니다.

**4. 설정 오류 하나가 전체 검사를 멈춤**
- 첫 fixed 실행에서 제 가짜 API 실수로 목록 조회 허용 검사 2건이 실패했습니다.
- 그러자 목록과 무관한 개별 조회의 거부 검사까지 **전부 건너뛰었습니다**(9건 SKIP, 종료 코드 2). 사전 확인이 리소스별이 아니라 실행 전체 단위입니다.

### 이전 설명 정정
`over_restrictive`를 "허용돼야 하는데 막힘"이라고 설명했는데 틀렸습니다. 코드를 보면 다음과 같습니다.
- 허용돼야 할 계정이 막히면 → `setup`(설정 오류)
- 거부돼야 할 계정이 계약의 거부 코드 목록에 없는 비성공 코드(예: 500)를 받으면 → `over_restrictive` (경고)

거부 상태 코드 기본값 401·403·404는 이번에 코드(`config.py`)에서 기본값으로 확인했습니다.

### 브리핑에 주는 의미
- 개별 객체 조회에서는 AuthzTrace가 우리 판정 절차와 사실상 같은 결과를 냅니다. 차별성 문제는 그대로입니다.
- 다만 **목록·검색처럼 "성공 + 빈 결과"가 정상인 엔드포인트**에서는 상태 코드 우선 판정이 오탐을 냅니다. 브리핑 판정 절차 2단계("응답 안에서 해당 객체 ID와 합성 표식을 찾아 실제 대상 객체 반환 확인")는 이 경우를 구분합니다. 실제 Memos의 의심 경로도 바로 이 목록 경로입니다.
- 이 차이는 차별성 근거로 쓸 수 있는 후보입니다. 단, 가짜 API 1개에서 본 결과라 실제 Memos 0.9.0에서 다시 확인해야 합니다.

### 한계
- 실제 Memos가 아니라 핸들러 로직 일부만 흉내 낸 가짜 API입니다. 인증도 단순 토큰으로 바꿨고, 경로의 `/api` 접두사도 제가 정한 것입니다.
- Memos에는 특정인 공유 기능이 없어 공유(`allow: [owner, carol]`)는 실행하지 않았습니다.

결과 파일은 authztrace.yaml, mock_memos.py, result_vuln.json, result_fixed.json입니다(노션에는 첨부되지 않음, 위치 TBD). 다음 단계로 실제 Memos 0.9.0을 띄워서 같은 계약을 돌려 볼 수 있습니다.
