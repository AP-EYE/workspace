# 후보 순서 검증 결과

확인일: 2026-10-05. 담당: 심재훈. [10월 4일 조사](2026-10-04-akto-deep-analysis.md)의 세 후보를 순서대로 검증했다. 원본 커밋은 동일한 302dad92e1549b7a84ce73eded447ad5d18124f0이다.

**결과: URL 컨텍스트의 코드 수정 후보는 유지한다. 한국어 정형 개인정보와 금지 표식 기반 목록 검사는 기존 설정으로 처리되므로 새 엔진 개발 근거에서 제외한다. 목록 판정 연구는 독립 권한 증거와 객체 연결을 일반화하는 범위로 좁힌다.**

작업은 로컬에서 진행했다. 커밋·push·GitHub 이슈 생성·PR 게시나 업데이트는 하지 않았다.

## 1. URL 컨텍스트: 실제 DAO·MongoDB에서 재현

처음 조사와 달리 원본 FilterAction 전체 클래스, querySti, SingleTypeInfoDao, MongoDB를 연결했다. querySti는 모의 반환값이 아니라 실제 DB fixture를 읽었다.

- MongoDB: 7.0.4, 컨테이너 이미지 digest `sha256:d14158139a0bbc1741136d3eded7bef018a5980760a57f0014a1d4ac7677e4b1`.
- 접속: 별도 실험 컨테이너의 127.0.0.1:27105, 실험 계정 DB 20261005. 기존 MongoDB를 사용하지 않았다.
- Java 8, Maven 3.9.11. 원본 생성 코드 준비 후 libs/utils와 선행 모듈을 빌드했다.
- 실제 실행한 JUnit 테스트 1개가 8개 fixture를 검사했고 실패·오류 0이었다. 전체 테스트 모음의 통과는 아니다.
- 같은 클래스의 원본, 덮어쓰기만 제거한 버전, 분기 보완 후보를 각각 별도 클래스 디렉터리에 컴파일하여 같은 테스트를 실행했다. 원본 운영 소스는 변경하지 않았다.
- [원본 결과](evidence/2026-10-05-url-baseline.json), [한 줄 제거](evidence/2026-10-05-url-remove_overwrite_only.json), [수정 후보](evidence/2026-10-05-url-candidate.json), [원본·변형 해시](evidence/2026-10-05-url-provenance.json).

아래 값은 getPrivateResourceCount의 privateCount이며 BOLA 판정·유출 객체 수가 아니다.

| DB 관측·입력 | 원본 | 덮어쓰기만 제거 | 분기 보완 후보 |
|---|---:|---:|---:|
| 공개 관측 10/10, 저장된 값 있음 | 2 | 1 | 0 |
| 비공개 관측 10/0, 저장된 값 있음 | 2 | 1 | 1 |
| 비공개 관측, 값 집합 비어 있음 | 2 | 2 | 1 |
| 비공개 관측, 값 집합 null | 2 | 2 | 1 |
| 관측 수 0 | 2 | 2 | 1 |
| STI 없음 | 2 | 1 | 1 |
| URL 변수 2개: 공개 1개+비공개 1개 | 4 | 2 | 1 |
| 변수 없는 고정 URL | 0 | 0 | 0 |

원본은 공개 관측값을 조회했어도 새 STI로 덮어쓴 뒤 입력 URL 값을 반환했다. 한 줄만 제거한 버전은 공개 값을 fallback에서 여전히 셌다. 수정 후보는 공개 값은 제외하고, 비공개 값은 중복 카운트하지 않으며 저장된 값을 보존했다.

[검토용 패치](reproduction/url-private-context-candidate.patch)는 세 동작만 보완한다.

1. 조회 결과를 새 객체로 덮어쓰지 않는다.
2. Akto 기준에서 공개로 분류된 STI는 URL private 후보에서 제외한다.
3. 이미 센 비공개 값에 대해 fallback에서 다시 증가시키지 않는다.

**STI 없음·관측 수 0은 원본의 보수적인 후보 선택을 유지했다.** 이는 실제 비공개라는 정답도, AP-EYE의 보류 판정 구현도 아니다. Akto의 공개성 임계값을 변경하지 않았다. payload 분기, 전체 토큰 교체·API 선택·HTTP 재전송·UI는 이번 통합 테스트에 포함하지 않았다.

패치는 연구용 후보다. 업스트림 제출 전 본문·query·역할 컨텍스트와 기존 회귀 테스트, 실제 템플릿에서의 대상 선택·변조값 사용을 추가 확인해야 한다. 고유 타입 값의 선택이 권한 위반 객체를 보장하는지도 별도 문제다.

## 2. 한국어 정형 개인정보: 기존 설정으로 runtime 분류 확인

두 사용자 정의 유형을 실험 DB에 저장하고 원본 fetchCustomDataTypes로 읽은 뒤 원본 KeyTypes.findSubType으로 분류했다. UI 클릭을 대신해 DAO로 등록했으므로 UI·인증·등록 API까지 통합한 결과는 아니다. [입력 12개 결과](evidence/2026-10-05-korean-settings.json).

| 사례 | 기본 분류 | 설정 후 |
|---|---|---|
| 주민등록번호 키+합성 하이픈 형식 | GENERIC | 사용자 정의 주민번호 형식 |
| rrn 키+합성 13자리 | INTEGER_32 | 사용자 정의 주민번호 형식 |
| 휴대전화 키+010-1234-5678 | GENERIC | 사용자 정의 국내 전화번호 |
| phone 키+01012345678 | INTEGER_32 | 사용자 정의 국내 전화번호 |
| order_id의 같은 숫자 형식 | INTEGER_32 | 기존 분류 유지 |
| +821012345678 | PHONE_NUMBER | 기존 분류 유지 |
| 마스킹된 값·짧은 번호·번호가 포함된 문장 | GENERIC | 전용 유형으로 분류하지 않음 |

주민번호 설정은 키·값 AND와 합성 형식만 확인한다. 유효 번호·법적 등급·성능을 입증하지 않는다. 전화번호 설정도 010 형식만 대상으로 하며 다른 국내 번호 전체를 포함하지 않는다. 정규식은 [실행 소스](reproduction/ExistingSettingsAudit.java)에 기록했다. 시험 유형은 실행 뒤 실험 DB에서 삭제했다.

### 추가로 확인한 제한: 큰 rawMessage 입력

원본 KeyTypes.process에 유효한 JSON 문자열을 전달했다. rawMessage 길이 2에서는 국내 전화번호가 사용자 정의 유형으로 분류됐지만 길이 8193에서는 GENERIC으로 분류됐다. 이 메서드는 8192보다 큰 rawMessage에서 상세 유형 검사를 생략한다.

한 필드 값이 동일해도 rawMessage 매개변수 길이에 따라 결과가 달라진다는 재현이다. 모든 수집 경로에서 rawMessage가 항상 전체 응답을 뜻하는지, 실제 긴 응답을 얼마나 놓치는지, 성능상 이유가 무엇인지는 확인하지 않았다. 이 제한은 실제 traffic 경로와 외부 개인정보 평가 입력에서 우선 확인할 후속 후보다.

따라서 한국어 정형 패턴 부족은 설정 기준선으로 해결하고, 큰 입력에서 상세 검사 생략과 문장·키 의미의 문맥 분류는 따로 비교한다.

## 3. 목록 응답: 실제 YAML validate와 기존 본문 조건 비교

외부 tests-library의 고정 템플릿을 YAML로 읽고 원본 ConfigParser·Filter.isEndpointValid에서 validate 노드를 실행했다. 10월 4일에는 길이·유사도 조건을 재구성했지만 이번에는 원본 검증 엔진을 사용했다.

비교 설정은 2xx와 response_payload.contains_all의 protected-marker다. **기본 90% 조건에 추가한 설정이 아니라 이 실험의 validate 조건을 대체한 설정**이다. [설정](evidence/2026-10-05-marker-validate-config.json), [9개 결과](evidence/2026-10-05-list-validation-settings.json).

| 응답 사례 | 기본 validate | 기존 contains_all 설정 |
|---|---|---|
| 빈 배열·빈 객체 | 미통과 | 미통과 |
| 동일한 빈 목록 래퍼 | 통과 | 미통과 |
| 동일한 허용 공유 객체 | 통과 | 미통과 |
| 동일한 금지 표식 객체 | 통과 | 통과 |
| 빈 목록으로 필터링 | 미통과 | 미통과 |
| 다른 허용 객체만 반환 | 미통과 | 미통과 |
| 금지 객체+허용 객체의 혼합 목록 | 미통과 | 통과 |
| 두 객체의 ID·본문 연결 교환 | 통과 | 미통과 |

표는 validate 노드 결과이며 제품의 최종 BOLA 경보가 아니다. api_selection_filters, 역할·공개 설정, 토큰 교체, 대상 서버의 권한 정책은 실행하지 않았다. 표식 설정은 사람이 알고 있는 금지 표식을 넣은 합성 사례에서만 검사했다.

**혼합 목록 탐지 기능을 새로 만드는 것만으로는 차별화가 부족하다.** 기존 설정으로도 고정 표식을 확인할 수 있었다. 기존 설정을 비교 대상에서 빼면 개선 성능을 과장할 수 있다.

다음 비교는 기본 템플릿, 객체 표식·역할 등을 설정한 기존 Akto, 개선 판정을 포함해야 한다. 개선이 필요한 후보는 API마다 표식을 직접 지정하지 않고 객체 ID·본문의 연결과 독립 접근 권한 증거를 사용하며 모르는 경우 보류하는 부분이다. 아직 구현하거나 성능을 평가하지 않았다.

## 다음 진행 기준

- URL 패치는 로컬 회귀·HTTP 재전송까지 검증한 뒤 제출 여부를 별도로 결정한다. 게시 허락 없이 외부 이슈·PR을 만들지 않는다.
- 한국어 평가는 기존 설정을 기준선으로 포함하고 큰 입력 제한과 문맥 분류를 분리한다.
- 목록 판정 개선은 외부 평가 대상과 객체별 권한 정답 확보가 선행한다. AP-EYE #6의 데이터셋 조사 결과를 연결하기 전 목표 수치를 정하지 않는다.
- 이번 8×3 URL 사례, 한국어 12개, 목록 9개는 진단용 합성 입력이다. 외부 평가 성능·오탐률·재현율로 보고하지 않는다.
